# 공모주 투자 수익 관리 서비스 로드맵

이번에 가장 먼저 시작할 Epic은 **로그인 계정과 인증·인가(`account-authentication`)**다. 이 로드맵은 `docs/work-plan-ipo-investment.md`의 도메인 관계와 MVP 범위를 기준으로, 의존관계·리스크·사용자 가치를 함께 고려해 Epic 단위로 재배열한 구현 순서다. 각 Epic은 `feature/[epic-slug]` 브랜치에서 단일 PR로 리뷰 가능한 크기를 목표로 하며, 구현 전 해당 Epic의 조사·기획·아키텍처·테스트 게이트를 통과해야 한다. `work-plan-ipo-investment.md` 37장에서 제외된 기능은 구현 대상에 포함하지 않는다.

우선순위 표기는 P0를 보안·금융 정합성 등 선결 위험, P1을 MVP 핵심 가치, P2를 핵심 흐름 이후의 표현·확장 작업으로 사용한다. 표의 순서는 실제 착수 순서다.

## 2. Epic별 상세

### 1. 로그인 계정과 인증·인가

- **Epic 이름:** 로그인 계정과 인증·인가
- **epic-slug:** `account-authentication`
- **목적 한줄:** 로그인 계정을 안전하게 관리하고, 이후 모든 투자 데이터가 계정 단위로 격리되도록 보안 경계를 만든다.
- **포함 범위:** 계정 등록·인증·로그아웃, 인증 상태 관리, 계정별 데이터 접근 권한, 다른 계정 데이터 접근 차단, 인증 오류 처리, 민감정보 로그 마스킹, 계정 소유의 투자자·계좌·투자 기록 연결 기준.
- **제외 범위:** 투자자·증권계좌 도메인 구현, 증권사 연동, 투자 기록 CRUD, 개인정보 외부 전송.
- **의존하는 선행 Epic:** 없음.
- **우선순위 근거:** 모든 도메인 데이터의 소유자와 접근 범위를 결정하는 가장 낮은 의존 계층이다. 인증과 인가가 없으면 이후 CRUD와 조회 API를 안전하게 만들 수 없으며, 금융·개인정보 노출 위험이 가장 크다. 사용자 입장에서도 여러 투자자를 관리하려면 계정 격리가 먼저 보장되어야 한다.
- **진행 전 필요한 조사:** 인증 방식과 세션/JWT 선택 기준, 비밀번호 저장·해시 정책, 인가 구조, 개인정보 최소 수집, 계좌정보 저장·마스킹 방침, 로그 금지 항목, 계정 삭제와 투자 기록 보존 정책을 조사한다. 구체적인 인증 라이브러리나 정책 값은 조사 문서에서 확정한다.

### 2. 투자자 관리

- **Epic 이름:** 투자자 관리
- **epic-slug:** `investor-management`
- **목적 한줄:** 한 로그인 계정이 본인·가족 등 여러 실제 투자자를 등록하고 소유 관계를 유지할 수 있게 한다.
- **포함 범위:** `Investor` 도메인, 계정별 투자자 목록, 투자자 등록·수정·비활성화, 투자자 식별자와 표시 이름, 중복 방지, 계정 간 데이터 격리, 투자자가 아직 계좌를 갖지 않은 상태 처리.
- **제외 범위:** 증권사와 증권계좌 등록, 조직·회사·관리자 권한, 투자자 간 공유, 실제 계좌 인증.
- **의존하는 선행 Epic:** 1 `account-authentication`.
- **우선순위 근거:** 청약·배정·매도의 소유 주체를 정의하는 도메인 기반이다. 인증 다음으로 투자자를 먼저 안정화하면 이후 모든 기록이 투자자·계좌 관계를 명확히 참조할 수 있다. 복잡한 권한 시스템은 제외해 단일 PR 범위로 제한한다.
- **진행 전 필요한 조사:** 투자자 표시 이름과 식별 정보의 범위, 개인정보 최소 수집, 투자자 삭제·비활성화와 기존 기록 보존 정책, 가족 구성원 정보를 어디까지 저장할지를 조사한다.

### 3. 증권사 기준정보 관리

- **Epic 이름:** 증권사 기준정보 관리
- **epic-slug:** `securities-firm-catalog`
- **목적 한줄:** 증권계좌가 참조할 증권사 기준정보를 일관되게 등록·조회할 수 있게 한다.
- **포함 범위:** `SecuritiesFirm` 도메인, 증권사 이름과 안정적 식별자, 기준정보 등록·수정·조회, 중복 증권사 방지, 기준정보와 금융 기록의 참조 관계, 기준정보의 삭제 또는 비활성화 정책.
- **제외 범위:** 증권사 자동 연동, 증권사 API를 통한 계좌 조회, 수수료 정책 자동 반영, 투자 기록 CRUD.
- **의존하는 선행 Epic:** 1 `account-authentication`.
- **우선순위 근거:** 증권계좌가 특정 증권사를 참조해야 하므로 계좌 Epic의 선행 조건이다. 기준정보는 도메인 기록과 분리해 관리해야 하며, 외부 연동을 포함하면 범위가 커지므로 수동 기준정보 관리만 먼저 제공한다.
- **진행 전 필요한 조사:** 증권사 기준정보의 소유 범위, 수동 등록과 외부 출처 활용 여부, 기준정보 변경 시 기존 계좌 기록의 처리 방식, 삭제 정책과 감사 로그 수준을 조사한다. 외부 데이터 제공처나 연동 방식은 이 Epic에서 확정하지 않는다.

### 4. 증권계좌 관리

- **Epic 이름:** 증권계좌 관리
- **epic-slug:** `securities-account-management`
- **목적 한줄:** 투자자마다 하나 이상의 증권계좌를 등록하고, 청약 기록이 사용할 계좌를 안전하게 선택할 수 있게 한다.
- **포함 범위:** `SecuritiesAccount` 도메인, 투자자·증권사·계좌 관계, 계좌 등록·수정·비활성화, 계좌별 목록과 기본 계좌 지정, 계좌 번호 검증·마스킹, 동일 투자자의 중복 계좌 방지, 계정 소유 범위 검증.
- **제외 범위:** 증권사 자동 연동, 실제 계좌 잔고·거래 내역 가져오기, 자동 주문, 조직·회사 권한.
- **의존하는 선행 Epic:** 2 `investor-management`, 3 `securities-firm-catalog`.
- **우선순위 근거:** `Subscription`이 투자자와 증권계좌를 함께 참조하므로 청약 Epic의 직접 선행 조건이다. 증권사 기준정보와 계좌 기록을 분리하면 기준정보 변경과 금융 기록 보존을 독립적으로 검토할 수 있다.
- **진행 전 필요한 조사:** 계좌번호 전체 저장 여부, 마스킹과 상세 조회 권한, 계좌 삭제·비활성화 시 기존 청약 기록 처리, 기본 계좌 규칙과 동시성 처리를 조사한다.

### 5. 공모주 기준정보 관리

- **Epic 이름:** 공모주 기준정보 관리
- **epic-slug:** `ipo-catalog`
- **목적 한줄:** 청약 기록이 참조할 공모주의 식별 정보와 청약·상장 관련 기준정보를 일관되게 등록하고 조회할 수 있게 한다.
- **포함 범위:** `IPO` 도메인, 기업명·공모주명·공모가·청약 시작일·청약 종료일·상장일 등 계획서에 제시된 기준 필드, 상태 표현, 중복 공모주 방지, 등록·수정·조회, 계정 또는 서비스 범위 결정, 이후 청약에서 사용할 안정적 식별자.
- **제외 범위:** 외부 데이터 자동 수집, 사이트 스크래핑, 실시간 주가, 자동 주문, 공모주 추천, 배정 결과 예측.
- **의존하는 선행 Epic:** 1 `account-authentication`.
- **우선순위 근거:** `Subscription`이 특정 공모주를 참조해야 하므로 청약 Epic의 직접 선행 조건이다. 증권사·계좌 관리와 병렬로 설계할 수 있지만, 외부 데이터의 신뢰성과 약관 리스크가 있어 먼저 조사 게이트를 둔다. 수동 등록만으로도 MVP의 기록 목적을 검증할 수 있다.
- **진행 전 필요한 조사:** IPO 데이터의 필요 필드, 공식·공개 데이터 제공처 후보와 이용 약관, 호출 제한·상업적 이용 가능 여부, 데이터 신뢰성과 갱신 기준, 자동 수집이 불가능할 때의 수동 입력·CSV·관리자 등록 대안을 조사한다. 특정 API나 스크래핑 방식을 여기서 확정하지 않는다.

### 6. 청약 기록

- **Epic 이름:** 청약 기록
- **epic-slug:** `subscription-management`
- **목적 한줄:** 특정 투자자와 증권계좌가 특정 공모주에 청약한 사실을 검증 가능한 기록으로 저장한다.
- **포함 범위:** `Subscription` 도메인, 투자자·증권계좌·IPO 연결, 청약 수량·금액·일시·증거금·환불 금액·상태, 청약 상태 전이, 중복 청약 방지, 수량·금액·소유 관계 검증, 청약 기록 목록과 상세 조회.
- **제외 범위:** 배정 결과 등록, 자동 청약·주문, 증권사 API 연동, 배정 확률·예측, 세금·수익 계산.
- **의존하는 선행 Epic:** 2 `investor-management`, 4 `securities-account-management`, 5 `ipo-catalog`.
- **우선순위 근거:** 서비스의 핵심인 “어떤 투자자가 어떤 계좌로 어떤 공모주에 참여했는가”를 처음 기록하는 유스케이스다. 이후 배정·매도·수익 계산이 모두 이 기록에 의존하므로 도메인 불변조건과 동시성 문제를 이른 단계에 검증해야 한다.
- **진행 전 필요한 조사:** 청약 상태 목록과 전이 규칙, 증거금과 환불 금액의 기록 의미, 동일 청약 중복 방지, 청약 기록 수정 가능 범위와 동시성 처리를 조사한다. 구체적인 금융 규칙은 조사 결과를 사람의 결정 후 반영한다.

### 7. 배정 결과 관리

- **Epic 이름:** 배정 결과 관리
- **epic-slug:** `allocation-management`
- **목적 한줄:** 청약 결과로 실제로 배정된 수량과 배정 관련 정보를 기록하고, 이후 분할 매도의 기준을 만든다.
- **포함 범위:** `Allocation` 도메인, `Subscription` 대 `Allocation` 관계, 배정 수량·배정 일시·배정 관련 정보, 청약 수량과 배정 수량 검증, 배정 상태와 잔여 수량, 중복 배정 방지, 배정 기록 목록과 상세 조회.
- **제외 범위:** 자동 배정 데이터 수집, 배정 확률·예측, 매도 기록, 세금·수익 계산, 미매도 주식의 평가손익 계산.
- **의존하는 선행 Epic:** 6 `subscription-management`.
- **우선순위 근거:** 청약만으로는 실제 투자 결과를 알 수 없으며, 모든 매도는 배정 수량을 초과할 수 없다는 불변조건을 여기서 확립해야 한다. 청약과 배정을 별도 Epic으로 나눠 상태 전이와 정합성 테스트를 독립적으로 리뷰할 수 있다.
- **진행 전 필요한 조사:** 균등·비례 등 배정 방식의 표현 범위, 청약에서 배정으로 가는 전이 규칙, 배정 관련 정보의 필수 범위, 배정 수량과 잔여 수량의 동시성 처리를 조사한다.

### 8. 분할 매도 기록

- **Epic 이름:** 분할 매도 기록
- **epic-slug:** `sale-management`
- **목적 한줄:** 한 배정 결과에 여러 번의 매도를 기록하고, 누적 수량이 배정 수량을 초과하지 못하게 한다.
- **포함 범위:** `Sale` 도메인, `Allocation` 대 `Sale` 일대다 관계, 매도 수량·가격·금액·일시, 누적 매도 수량과 미매도 수량 계산, 배정 수량 초과 차단, 분할 매도 순서, 매도 기록 수정·삭제 정책, 수량·금액 검증.
- **제외 범위:** 자동 매매·증권사 주문, 실시간 주가 연동, 세금 공식의 최종 적용, 평가손익, 투자 추천.
- **의존하는 선행 Epic:** 7 `allocation-management`.

## 3. 지금 시작할 Epic 1개와 그 이유

가장 먼저 시작할 Epic은 **로그인 계정과 인증·인가(`account-authentication`)**다. 이 Epic은 다른 모든 투자 데이터의 소유자와 접근 경계를 정의하므로, 인증 없이 투자자·청약·수익 API를 먼저 만들면 이후 데이터 격리와 보안 수정 비용이 커진다. 동시에 계정 인증·인가는 투자자 관리보다 범위가 작아 단일 PR로 검토할 수 있으며, 구현 전에 인증·개인정보·보안 조사와 Phase 0 산출물을 완료하는 조건을 둔다.

## 4. 아직 결정되지 않아 사람 확인이 필요한 사항

- 인증 방식(세션/JWT 등), 비밀번호 저장 정책, 인가 모델, 개인정보와 계좌번호의 저장·마스킹 범위를 어떻게 할지.
- 증권사 기준정보와 IPO 기준정보를 수동 등록만으로 운영할지, 외부 데이터 제공처를 도입할지. 도입한다면 제공처·약관·갱신 주기와 자동 수집 범위를 어떻게 할지.
- 청약·배정의 상태 목록, 균등·비례 배정 표현, 증거금·환불금 처리, 중복 청약과 동시성 처리 규칙을 어떻게 할지.
- 수수료·세금·기타 비용의 적용 범위와 사용자 입력/정책 데이터 운영 방식을 어떻게 할지.
- 실현수익·수익률의 투자금 기준, 증거금·환불금·보유기간 반영, 금액 정밀도와 반올림 규칙을 어떻게 할지.
- 미매도 주식의 평가손익과 은행 이자 비교를 MVP에 포함할지, 포함한다면 별도 Epic으로 분리할지. 현재 로드맵에는 포함하지 않는다.
- 금융 기록의 수정 이력·감사 로그·삭제 정책을 어디까지 MVP에 적용할지.
- 대시보드의 총투자금·총수익·총수익률 정의, 기간 귀속 기준, 부분 매도와 미매도 주식의 표시 방식을 어떻게 할지.
- 웹 클라이언트의 반응형·접근성 수준과 주요 E2E 검증 범위를 어디까지로 할지.
