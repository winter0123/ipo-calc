# 공모주 투자 수익 관리 서비스 로드맵

> 기준일: 2026-09-22, PR #139 병합 이후. 제품 요구사항의 진실 소스는 `docs/work-plan.md`, 세션 단위 실제 현황은 `docs/current-status.md`, Epic별 세부 구현 순서는 각 `docs/breakdown/[epic-slug].md`다. 이 문서는 세 문서를 연결해 **무엇을 언제·어떤 게이트로·어디까지 병렬 구현할지** 정한다.

## 1. 제품 목표와 MVP 경계

사용자가 하나의 로그인 계정으로 여러 투자자와 증권계좌의 공모주 청약, 배정, 분할 매도, 비용, 실현수익을 기록하고 투자자·증권사·기간별로 조회하는 서비스가 MVP 목표다.

MVP에 포함하는 흐름은 다음과 같다.

```text
Account → Investor → SecuritiesAccount → IPO → Subscription
        → Allocation → Sale → Cost → Realized Profit
        → Investment History / Dashboard → Web UI
```

다음은 MVP 범위 밖이다: 자동 청약·주문(매매 실행), 실시간 시세·미실현 평가손익, 투자 추천, 자동 세금 신고, 외부 데이터 스크래핑. 세금·수수료는 사용자가 기록한 값 또는 승인된 규칙만 사용하며 추측 계산하지 않는다.

### 1.1 스코프 확장 (2026-09-29 사용자 결정)

MVP 1차 완료(Epic 1~16) 이후 사용자 사용성 문제 제기로 스코프를 확장한다. 아래 세 가지를 Epic 17 이후로 추가하며, 상세 조사·기획·설계는 착수 전에 별도 Phase 0을 거친다.

1. **공모주 청약 일정 자동 동기화**: `docs/research/ipo-schedule-sync.md` 7절(2026-09-29 확정)에 따라 **금융감독원 OpenDART DS006(증권신고서-지분증권) API를 기본 소스**로 청약일·공모가·주간사를 확보하고, OpenDART가 못 주는 상장예정일·배정일·환불일은 **`api.ustockplus.com`(네이버 u+stock 백엔드, 비공식)**으로 보완하는 하이브리드로 간다. 38.co.kr·네이버 화면 직접 크롤링은 저작권·이용약관 리스크로 기각. 배치 주기는 향후 3개월치를 1일 1회 갱신(제안).
2. **증권사 조회 전용(read-only) 연동 — 파일럿 1개사부터**: 사용자가 "일단 증권사 하나만 시범적으로 해보자"고 결정함에 따라, 우선 **한국투자증권(KIS Developers REST API)** 한 곳만 파일럿으로 연동한다. **원칙은 예외 없이 조회 전용**이다 — 매수/매도/정정/취소 등 주문 실행 권한은 어떤 브로커·어떤 상황에서도 요청하거나 사용하지 않는다. 계좌 잔고·체결(매매)내역·수수료를 조회해 매도 기록·비용 기록의 자동 채움(또는 자동 등록) 가능성을 조사한다. 파일럿 검증 후 다른 브로커로 확장할지는 별도 결정.
3. **사후 등록 UX/UI 전면 개선**: 현재 청약/배정/매도/비용을 사람이 화면에서 하나씩 입력하는 흐름의 사용성이 나쁘다는 사용자 피드백. 위 1·2번(일정 선택, 자동 조회 연동)과 맞물려 입력 폼 자체를 다시 설계한다. 추가로 다음 조회 화면을 신설한다: ① 청약/상장/환불일이 모두 표시되는 달력 뷰, ② 로그인 시 등록된 모든 증권계좌 목록이 먼저 보이고 계좌 선택 시 그 계좌의 투자 내역이 나오는 화면(현재처럼 증권사 ID를 직접 입력하지 않음), ③ 월별로 공모주 투자 손익을 집계해 이번 달 수익을 한눈에 보는 페이지.

착수 전 필요한 것: 각 항목의 `docs/research/` 조사 문서(외부 API 실제 스펙, 인증 흐름, 데이터 정규화 전략), 이어서 spec·architecture, 그다음 Epic 마스터 표(5절)에 E17~E19로 편입한다.

## 2. 실행 원칙

1. Epic은 roadmap의 우선순위·의존성을, SF는 breakdown의 순서·AC를 따른다.
2. Phase 0(research/spec/architecture)와 breakdown이 승인되지 않은 Epic은 코드 작업을 시작하지 않는다.
3. 의존하지 않는 백엔드·프론트엔드·planning 작업은 병렬이 기본이다. 같은 브랜치에서 앞 SF의 코드를 이어 쓰는 경우만 순차다.
4. 각 SF는 독립 PR·검증·병합 단위다. Epic 마지막 SF가 아니면 `Part of #<Epic Issue>`만 쓰며 `Closes #`를 쓰지 않는다.
5. 실제 테스트·build·diff·PR 병합 검증 전에는 완료로 표시하지 않는다.

## 3. 의존성 맵과 병렬 트랙

```text
E1 인증
├─→ E2 투자자 ─┐
├─→ E3 증권사 ├─→ E4 증권계좌 ─┐
├─→ E5 IPO ──────────────────────┼─→ E6 청약 → E7 배정 → E8 매도
└─────────────────────────────────┘                  ├─→ E9 비용 → E10 수익 계산 → E12 대시보드 API
                                                       └─→ E11 투자 내역 조회 API

E1 + E2 + E3 + E4 ─→ E13 웹 계정·투자자·계좌 설정
E5 + E6 + E7 + E13 ─→ E14 웹 IPO·청약·배정 입력
E8 + E9 + E10 + E13 + E14 ─→ E15 웹 매도·비용·수익 확인
E11 + E12 + E13 + E14 + E15 ─→ E16 웹 조회·대시보드
```

중요한 정정: E11은 E9/E10의 수익·비용 데이터를 반환하지 않으며, breakdown 기준으로 E7·E8이 병합되면 착수할 수 있다. 따라서 E8 완료 뒤 E9와 E11은 별도 backend worktree에서 병렬 착수 가능하다. E12는 E10의 `ProfitCalculator`가 main에 병합된 뒤에만 시작한다.

| 트랙 | 지금부터의 순서 | 병렬화 조건 |
|---|---|---|
| Backend A | E8 SF-5 → E9 → E10 → E12 | E8 완료 뒤 E9와 E11 병렬 가능. E12는 E10 완료 뒤 |
| Backend B | E8 SF-5 → E11 | E8 병합 후 E9/E10을 기다리지 않음 |
| Frontend | E15 breakdown·계약 검토 → 구현·통합 → E16 | E15의 실제 API 연동은 E8/E9/E10 완료 뒤, 화면 구조·테스트 설계는 승인된 계약으로 선행 가능 |
| Planning | E15 breakdown → E16 breakdown → 계약/보안 드리프트 점검 | 다른 파일을 쓰면 기존 planning worktree에서 병렬 가능 |

5. **알려진 부채(별도 우선순위 결정 필요)**: 접근성 위반 32건 수정(`docs/qa/accessibility-report.md`), checkstyle 남은 532건(Javadoc 위주).

## 6. Epic별 실행 카드

### E1. 로그인 계정과 인증·인가 — `account-authentication`

- **목표**: 계정 등록·인증·로그아웃과 계정별 데이터 격리의 보안 경계를 제공한다.
- **핵심 완료 조건**: 인증 상태, 다른 계정 데이터 차단, 민감정보 로그 금지, 인증 오류 처리가 테스트로 검증돼 있다.
- **상태**: 완료·병합. 이후 모든 계정 소유 도메인의 회귀 기준이다.

### E2. 투자자 관리 — `investor-management`

- **목표**: 한 계정이 본인·가족 등 여러 투자자를 등록·수정·비활성화한다.
- **핵심 완료 조건**: 계정 간 격리, 중복·삭제/비활성화 정책, 투자자가 계좌 없이 존재할 수 있는 상태가 검증돼 있다.
- **상태**: 완료·병합.

### E3. 증권사 기준정보 관리 — `securities-firm-catalog`

- **목표**: 증권계좌가 참조하는 증권사 기준정보를 등록·수정·조회한다.
- **핵심 완료 조건**: 안정적 식별자, 중복 방지, 비활성화와 기존 기록 참조 정책이 검증돼 있다.
- **상태**: 완료·병합.

### E4. 증권계좌 관리 — `securities-account-management`

- **목표**: 투자자·증권사와 연결된 계좌를 안전하게 등록·수정·비활성화한다.
- **핵심 완료 조건**: 계좌번호 암호화·마스킹, 기본 계좌 규칙, 2단계 소유권 검증, 중복 방지가 검증돼 있다.
- **상태**: 완료·병합.

### E5. 공모주 기준정보 관리 — `ipo-catalog`

- **목표**: 청약이 참조할 IPO의 공모가·일정·상태를 수동 기준정보로 관리한다.
- **핵심 완료 조건**: 중복 방지, 등록·조회·수정·비활성화·CSV 입력이 검증돼 있다. 자동 수집은 범위 밖이다.
- **상태**: 완료·병합.

### E6. 청약 기록 — `subscription-management`

- **목표**: 투자자·계좌·IPO의 청약 사실과 증거금·환불금·상태를 기록한다.
- **핵심 완료 조건**: 소유 관계, 수량·금액, 중복 청약, 취소 상태가 검증돼 있다.
- **상태**: 완료·병합.

### E7. 배정 결과 관리 — `allocation-management`

- **목표**: 청약 결과의 배정 수량과 잔여 수량을 기록해 이후 매도의 상한을 만든다.
- **핵심 완료 조건**: 청약 수량을 넘는 배정 차단, 중복 배정 방지, 매도에 필요한 참조 관계가 검증돼 있다.
- **상태**: 완료·병합.

### E8. 분할 매도 기록 — `sale-management`

- **목표**: 하나의 배정에 여러 매도를 기록하고 누적 매도수량이 배정수량을 넘지 않게 한다.
- **SF 순서**: SF-1 엔티티/Repository/마이그레이션 → SF-2 등록·누적수량 검증 → SF-3 목록/상세 → SF-4 수정·자기 자신 제외 재검증 → SF-5 취소/논리 삭제.
- **가장 큰 위험**: 등록·수정에서 `Σ ACTIVE Sale.quantity ≤ Allocation.allocatedQuantity` 불변식이 깨지면 금융 기록 정합성이 무너진다. SF-4는 자기 자신을 합계에서 제외하는 회귀 테스트가 필수다.
- **현재 상태**: SF-1~SF-4 병합 완료. SF-5는 취소 성공, 404, 취소 행 목록 제외를 검증한 뒤 병합한다.
- **완료 뒤**: E9와 E11을 병렬로 열고 E14의 실제 데이터 통합 계약을 다시 확인한다.

### E17. 공모주 청약 일정 자동 동기화 — `ipo-schedule-sync` (신설, 2026-09-29)

- **목표**: 공모주 청약/공모가/주간사 일정을 외부 소스에서 자동으로 가져와 IPO 기준정보(E5)를 채우고, 사용자는 청약 등록 시 목록에서 선택만 하면 되게 한다.
- **데이터소스(확정, `docs/research/ipo-schedule-sync.md` 7절)**: 기본 = 금융감독원 OpenDART `DS006`(증권신고서-지분증권) API(공식·무료) — 청약기일·납입기일·공모가·주간사. 보완 = `api.ustockplus.com`(네이버 u+stock 백엔드, 비공식) — 상장예정일·배정일·환불일. 38.co.kr·네이버 화면 직접 크롤링은 저작권·약관 리스크로 기각.
- **핵심 설계 과제**:
  1. OpenDART는 회사고유번호 기준 조회라 "앞으로 청약할 전체 종목 목록"을 얻으려면 DS001 공시검색으로 먼저 대상 회사를 찾는 2단계 구조가 필요하다.
  2. 두 소스의 종목 식별자 체계가 다르다(OpenDART=회사고유번호, ustockplus=종목코드) — 매핑 로직 필요.
  3. ustockplus는 비공식 API이므로, 그 호출이 실패해도 OpenDART 데이터만으로 서비스가 정상 동작해야 한다(상장예정일 등은 null 허용, 사용자 수동 보완 가능).
  4. 기존 수동 입력 IPO 데이터와 자동 동기화 데이터가 충돌하지 않아야 한다(자동 동기화가 사용자 직접 입력을 덮어쓰지 않음).
- **명시적 비범위**: 실시간 시세, 청약 경쟁률 실시간 갱신, 브로커별 청약 한도 계산.
- **다음 작업**: spec 작성 — IPO 엔티티 확장 필드, 배치 스케줄러 설계(제안: 향후 3개월치 1일 1회), 재시도/알림 정책, 두 소스 병합 규칙을 확정한다.
- **상태(2026-09-30)**: SF-1(엔티티·마이그레이션)~SF-4(일일 스케줄러) 병합 완료, 휴장일 DB+월간 배치(D-6) 병합. **SF-2(ustockplus)는 사용자가 편입을 확정**(2026-09-30)해 #206 클라이언트·#211 `IpoScheduleMergeService`·#200 스케줄러로 연결돼 있다. 비공식 API라 차단·스펙 변경 시 상장예정일·배정일·환불일은 수동 입력으로 돌아간다. **SF-5(`GET /ipo-schedule`)는 폐기**: 자동 동기화된 공모주는 `ipos`에 저장되므로 기존 `GET /ipos`를 청약 등록 폼과 달력이 그대로 쓴다. 금융위 주식발행정보는 사후 정보라 미도입(D-7).

### E18. 증권사 조회 전용 연동 — `broker-readonly-api-pilot` (신설, 2026-09-29)

- **목표**: 한국투자증권(KIS Developers REST API) 1개사를 파일럿으로 조회 전용 연동해, 매도(Sale) 기록의 자동 채움 가능성을 검증한다.
- **원칙(예외 없음)**: 매수/매도/정정/취소 등 주문 실행 권한은 어떤 상황에서도 요청·사용하지 않는다. 코드 레벨 5단 강제 장치(조회 메서드만 선언 / 아웃바운드 HTTP를 GET으로 제한 / base URL 고정+allowlist / 시크릿 백엔드 전용 / 호출 감사 로그)로 보장한다(`docs/research/broker-readonly-api-pilot.md` 4.3절).
- **핵심 설계 과제(구조적 병목, 4.4절)**: 브로커 체결내역을 우리 내부 `allocation_id`/`subscription_id`로 번역할 매칭 키가 현재 스키마에 없다. `ipos.stock_code`가 NULL 허용이라 종목코드 매칭도 항상 되는 게 아니다. 이 매칭 규칙(또는 `sales`에 `external_transaction_id` 컬럼 추가 여부)을 spec에서 확정해야 착수할 수 있다.
- **1차 범위**: Sale(매도) 자동 채움만. Cost(비용)는 청약비용과 매도비용 개념이 달라 이중 차감 위험이 있어 1차 제외.
- **신규 테이블(설계안)**: `securities_firms`에 `api_supported`/`api_provider`/`api_readonly_only` 등 컬럼 추가, `securities_account_api_credentials`(계좌 1:1, 앱키/시크릿 암호화 저장) 신설.
- **명시적 비범위**: 주문·매매 실행, 키움 등 타 브로커 확장(파일럿 검증 후 별도 결정), 실시간 시세 연동.
- **다음 작업**: spec 작성 전 Master가 KIS Developers 공식 GitHub·API 포털 원문에서 체결내역 응답 필드(수수료·세금 등), rate limit, 모의투자 환경 여부를 확인해야 한다(`docs/research/broker-readonly-api-pilot.md` 9절 미확인 10건).
- **상태(2026-09-30)**: KIS 게이트 조사 완료(`docs/breakdown/broker-readonly-api-pilot.md` 게이트 조사 결과). 키 권한 분리 확인은 불필요(조회 전용 = 쓰기 코드를 만들지 않는 것, 사용자 결정). 토큰은 만료시각까지 캐시. **남은 결정**: 매도 자동 채움에 기간별매매손익현황(일자×종목 집계) 사용 여부, 실계좌 1회 조회 승인. 그 뒤 spec 작성.

## 7. Epic 착수·완료 게이트

### 7.1 착수 전 체크

각 Epic/SF 시작 전 다음을 확인한다.

- 관련 `research`, `spec`, `architecture`, `breakdown` 문서가 존재하고 승인됨
- roadmap의 선행 Epic이 실제 main에 병합됨
- GitHub Issue와 Orca 티켓이 생성되고 상태가 일치함
- 수정할 파일·읽을 파일·변경 금지 파일·검증 명령이 task spec에 명시됨
- 활성 워커 수와 파일 충돌 가능성을 확인함

### 7.2 SF 완료 체크

- 해당 AC를 테스트로 확인하고, 실제 테스트·lint·typecheck·build·`git diff --check` 결과를 기록함
- 계정 소유권, 입력 검증, 논리 삭제, 금액·수량 불변식을 리뷰함
- PR 본문의 Issue 키워드가 Epic 진행 상태와 맞음
- 병합을 `gh pr view`로 확인하고 worker terminal을 정리함
- `work-log`, `current-status`, `docs/daily-log/YYYY_MM_DD.md`, 필요 시 `setup-history`를 갱신함

## 9. 로드맵 변경 규칙

- 제품 요구사항·금융 계산·보안 경계를 바꾸는 경우 먼저 `work-plan`과 관련 spec/architecture를 갱신하고 사용자 승인을 받는다.
- Epic 의존성을 바꾸는 경우 breakdown·실제 코드·API 계약을 함께 대조한다. 단순히 "순서가 편하다"는 이유로 선행 게이트를 무시하지 않는다.
- SF가 8개를 넘거나 리뷰 가능한 단위가 아니면 Epic 경계를 재검토한다.
- 매 SF/Epic 병합 뒤에는 이 roadmap의 상태와 `current-status.md`를 함께 갱신한다.
