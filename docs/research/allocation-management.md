# 배정 결과 관리 (allocation-management) 조사 문서

## 조사 목적
Epic 7 `allocation-management` 구현에 앞서, 배정 방식 표현 범위, 청약에서 배정으로 가는 상태 전이 규칙, 배정 관련 정보의 필수 범위, 배정 수량과 잔여 수량의 동시성 처리 원칙을 조사하여 안전한 금융 데이터 관리 기반을 마련한다.

## 조사 대상
- `Allocation` 도메인 엔티티의 구조 및 필수 필드
- `Subscription`에서 `Allocation`으로의 상태 전이 규칙
- 균등·비례 등 배정 방식의 표현 방법 및 계산 로직 위치
- 배정 수량과 잔여 수량의 동시성 처리 원칙
- 중복 배정 방지 메커니즘

## 확인한 내용

### 1. 균등·비례 등 배정 방식의 표현 범위
**work-plan-ipo-investment.md 12장(Allocation 도메인)**:
- 청약 후 실제 배정 결과를 관리한다.
- 예시: 청약 수량: 100, 배정 수량: 3
- 또한 균등/비례 배정 등의 세부 정보가 실제 서비스 요구사항에 필요한지 조사한다.
- Allocation은 Subscription과 연결된다 (Subscription → Allocation).

**roadmap.md Epic 7 상세 (진행 전 필요한 조사)**:
- 균등·비례 등 배정 방식을 도메인에서 어떻게 표현해야 하는가
- 계산 로직을 이 서비스가 직접 하는가, 아니면 결과값만 기록하는가
- work-plan 12장은 "배정 결과를 관리"라고 했지 "배정 계산"이라고 하지 않았음에 주의

**확인한 내용**:
- 배정 방식은 서비스가 직접 계산하는 것이 아닌, 외부(증권사)로부터 결과를 받아서 기록하는 도메인으로 설계되어야 함
- 배정 방식 자체(균등, 비례, 추첨 등)는 메모 필드나 코드로 저장하여 추적 가능하게 해야 함
- 실제 배정 계산 로직은 외부 프로세스(증권사 또는 수동 입력)를 통해 결정되며, 이 서비스는 결과만 저장
- **사람 결정 필요**: 배정 방식 표현 방법(Enum vs String vs 별도 테이블)과 배정 관련 메모 필드의 필요성은 비즈니스 요구사항에 따라 결정되어야 함

### 2. 청약에서 배정으로 가는 상태 전이 규칙
**work-plan-ipo-investment.md 21장(상태값 설계)**:
- 각 도메인의 상태값은 문자열을 무분별하게 사용하지 않는다.
- 예시 상태: 청약 예정, 청약 진행 중, 청약 완료, 배정 완료, 일부 매도, 전량 매도, 보유 중
- 실제 상태 목록은 사용 시나리오와 데이터 모델링을 바탕으로 정의한다.
- 상태 전이가 가능한 경우 전이 규칙도 문서화한다.

**roadmap.md Epic 7 상세 (진행 전 필요한 조사)**:
- 청약(Subscription)에서 배정(Allocation)으로 가는 상태 전이 규칙은 무엇인가

**확인한 내용**:
- Subscription의 상태 전이: 청약대기 → 청약완료 → 배정대기 → 배정완료 (구독 관리 조사 결과 참고)
- Allocation 도메인의 자체 상태는 최소한 다음과 같이 고려될 수 있음:
  * 배정대기 (배정 결과 대기 중)
  * 배정완료 (배정 결과 확정)
  * 취소 (배정 취소됨 - 가능한 경우에 한함)
- 상태 전이 규칙 예시:
  * Subscription: 배정대기 → Allocation: 배정대기 (배정 처리 시작 시)
  * Subscription: 배정완료 → Allocation: 배정완료 (배정 결과 확정 시)
  * Subscription: 취소 → Allocation: 취소 (청약 취소 시 배정도 취소 - 가능한 경우에 한함)
- **사람 결정 필요**: 최종 상태 목록과 전이 규칙은 금융 규정 및 비즈니스 로직에 따라 결정되어야 하며, 배정 취소 가능 여부와 조건은 별도 확인이 필요함

### 3. 배정 기록에 필수로 남겨야 할 정보
**work-plan-ipo-investment.md 12장(Allocation 도메인)**:
- 배정 수량·배정 일시·배정 관련 정보
- 청약 수량과 배정 수량 검증
- 배정 상태와 잔여 수량
- 중복 배정 방지

**roadmap.md Epic 7 상세 (진행 전 필요한 조사)**:
- 배정 기록에 필수로 남겨야 할 정보는 무엇인가(배정 수량 외에 배정일, 배정 방식 메모 등 추가 정보가 필요한가)

**확인한 내용**:
- 필수 정보:
  * 배정 수량 (Integer, 필수)
  * 배정 일시 (Timestamp, 필수)
  * 청약 참조 (Foreign Key to Subscription, 필수)
- 선택적 लेकिन 권장 정보:
  * 배정 방식 메모 (String, 균등/비례/추첨 등 기록용)
  * 배정 단가 (Decimal, 공모가 기준이 아니거나 할증이 있는 경우)
  * 비고 (String, 특별사항 기록용)
- 검증 규칙:
  * 배정 수량 ≤ 청약 수량 (데이터 무결성 원칙)
  * 배정 수량 ≥ 0
- **사람 결정 필요**: 배정 방식 메모의 형식(Enum vs 자유 텍스트)과 배정 단가 기록 필요성은 비즈니스 요구사항에 따라 결정되어야 함

### 4. 배정 수량과 잔여 수량의 동시성 처리 원칙
**work-plan-ipo-investment.md 45장(동시성)**:
- 향후 여러 요청이 동시에 발생할 가능성을 고려한다.
- 특히 다음은 데이터 정합성이 중요하다:
  - 잔여 배정 수량 계산
  - 매도 수량 검증
  - 수익 계산
- 동시에 여러 매도 요청이 들어오는 경우를 어떻게 처리할지 설계 단계에서 검토한다.

**roadmap.md Epic 7 상세 (진행 전 필요한 조사)**:
- 배정 수량과 잔여 수량(이후 매도에서 차감될 값)의 동시성 처리는 어떤 원칙을 따라야 하는가

**확인한 내용**:
- 잔여 수량 계산: 잔여수량 = 배정수량 - 총매도수량
- 동시성 문제 시나리오:
  * 동일한 배정에 대한 여러 동시 매도 요청으로 인한 잔여수량 음수 값 생성 가능성
  * 매도 요청 처리 중 배정 정보 변경으로 인한 정합성 문제
- 동시성 제어 방법 후보:
  * 낙관적 락 (Optimistic Locking): 버전 컬럼을 사용하여 충돌 감지 (배정 엔티티에 버전 필드 추가)
  * 비관적 락 (Pessimistic Locking): SELECT FOR UPDATE를 통한 레코드 잠금
  * 트랜잭션 격리 수준: 적절한 격리 수준 설정 (READ_COMMITTED 이상 권장)
  * 애플리케이션 레벨 락: 분산 락 또는 뮤텍스 사용 (성능 고려 시)
- 잔여 수량 검증 로직은 서비스 계층에서 트랜잭션 내에서 수행해야 함
- **사람 결정 필요**: 구체적인 동시성 제어 방식은 성능 요구사항과 데이터 정합성 중요도에 따라 결정되어야 함

## 제약사항
1. **금융 규정 준수**: 배정 프로세스는 자본시장법 및 관련 금융 규정을 준수해야 함

4. **work-plan 36장**: 데이터 변경 시 수정 가능한 범위와 변경 추적 필요 고려
5. **work-plan 45장**: 동시성 처리 시 데이터 정합성 보장 필요
6. **금융 데이터 특성상 증거와 추정 금지**: 특히 배정 관련 사항은 사람의 결정 필요
7. **subscription-management 조사 결과**: 선행 Epic의 청약 상태 및 전이 규칙에 의존함

1. **Allocation 엔티티 설계**: 배정 수량, 배정 일시, 청약 외부 키, 배정 방식 메모, 배정 단가, 비고, 상태 컬럼, 버전 컬럼(동시성 제어용), 생성/수정 타임스탬프 포함 계획
2. **상태 관리**: Subscription과의 연계된 상태 전이 로직 구현 필요
3. **데이터 무결성**: 배정 수량 ≤ 청약 수량 검증 로직 및 중복 배정 방지 메커니즘 구현 필요
4. **변경 추적 기능**: 수정 가능한 필드에 대한 변경 이력 테이블 또는 감사 로그 구현 필요 (work-plan 36장)
5. **동시성 제어 메커니즘**: 트랜잭션 관리 및 락 전략을 서비스 계층에 적용 필요 (work-plan 45장)
6. **검증 로직**: 서비스 계층에서 배정 수량 검증 및 잔여 수량 계산 로직 구현 필요
7. **테스트 전략**: 상태 전이 테스트, 중복 방지 테스트, 동시성 테스트, 배정 수량 검증 테스트 등 필요

## 결론
배정 결과 관리 도메인은 청약 결과를 기록하는 핵심 금융 도메인으로, 배정 방식 표현, 상태 전이, 데이터 무결성, 변경 추적, 동시성 제어가 모두 중요한 요소이다. 조사 결과, 확인해야 할 사항은 많으나 금융 규정과 비즈니스 로직에 따른 사람의 결정이 필요한 사항이 다수 존재한다. 본 조사에서는 후보를 제시하고 불확실한 점을 명시했으며, 후속 기획 단계에서 정확한 정의가 이루어져야 한다. 특히 배정 방식 표현 방법, 최종 상태 목록 및 전이 규칙, 동시성 제어 방식은 금융 데이터의 정확성을 위해 사람의 명확한 결정이 선행되어야 구현을 진행할 수 있다. work-plan 12장이 명시한 것처럼 이 서비스는 "배정 결과를 관리"하는 도메인으로 설계되어야 하며, 배정 계산 로직은 외부에서 제공된 결과를 기록하는 역할에 한정해야 한다.
