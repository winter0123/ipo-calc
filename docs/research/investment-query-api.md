# 투자 내역 조회 API (investment-query-api) 조사 문서

## 조사 목적
Epic 11 `investment-query-api` 구현에 앞서, 사용자가 자신의 청약·배정·매도·비용·수익 기록을 투자자·증권사·계좌·공모주·기준 기준으로 안전하게 조회하는 API의 설계 원칙을 조사한다. 특히 필터와 기간의 기준 시점, 집계 단위, 페이지네이션·정렬 규칙, 미매도 기록 표시 방식, 인가 및 오류 규격을 중점적으로 조사한다.

## 확인한 내용 (1~5번 질문 각각에 대한 답)

### 1. 필터와 기간의 기준 시점은 무엇으로 삼아야 하는가 (청약일/배정일/매도일 중 어느 것 기준)?
- **청약 기록 기반**: `Subscription` 엔티티의 청약 일시를 기준으로 기간 필터 적용 가능
- **배정 기록 기반**: `Allocation` 엔티티의 배정 일시를 기준으로 기간 필터 적용 가능  
- **매도 기록 기반**: `Sale` 엔티티의 매도 일시를 기준으로 기간 필터 적용 가능
- **비용 기록 기반**: 비용 발생 일시를 기준으로 기간 필터 적용 가능
- **수익 인식 시점**: 매도 일시를 기준으로 실현수익 인식 (매도 시점에 비용 차감 후 수익 확정)
- **검토 결과**: 투자 내역 조회 API의 경우 사용자가 주로 보는 것은 "내가 언제 어떤 주식을 샀고 팔았는가"이므로 **매도 일시를 기본 기준으로** 하되, 청약일·배정일도 필터 옵션으로 제공하는 방식이 적절함
- **참고**: sale-management.md에서 매도 순서 표현 방법으로 "매도 일시 기준 순서 자동 정렬"을 고려 중이라고 명시됨

### 2. 투자자·증권사·계좌별 결과의 집계 단위는 어떻게 나눠야 하는가?
- **투자자별 집계**: 한 계정 내 여러 투자자(본인·가족 등)를 구분하여 집계
- **증권사별 집계**: 동일한 증권사의 여러 계좌를 합산하여 집계 (securities-firm-catalog 참조)
- **계좌별 집계**: 개별 증권계좌 단위로 집계 (securities-account-management 참조)
- **공모주별 집계**: 개별 IPO 단위로 집계 (ipo-catalog 참조)
- **검토 결과**: 투자자 → 증권사 → 계좌 → 공모주 순의 계층적 집계 구조를 지원해야 함
- **참고**: dashboard-aggregation-api 에pic에서는 "전체·투자자별·증권사별·기간별 투자금, 수익, 수익률, 참여 건수"를 집계 대상이라고 명시됨

### 3. 페이지네이션·정렬 규칙은 어떤 방식이 적절한가?
- **페이지네이션 방식**: offset/limit 기반 또는 cursor 기반 페이지네이션 고려
- **정렬 기본 기준**: 매도 일시 내림차순 (최신 매도가 먼저 표시됨)
- **추가 정렬 옵션**: 
  * 청약 일시 오름/내림차순
  * 배정 일시 오름/내림차순  
  * 수익률 오름/내림차순
  * 투자금 오름/내림차순
- **페이지 크기**: 기본 20개, 최대 100개로 제한 권장
- **검토 결과**: sale-management.md에서 "매도 일시 기준 순서 자동 정렬"을 고려 중이라고 언급되어 있으므로, **매도 일시 DESC를 기본 정렬로** 하고 cursor-based 페이지네이션을 적용하는 것이 성능과 일관성 면에서 적절함

### 4. 미매도 기록(아직 매도 안 된 배정)의 표시 방식은?
- **미매도 수량 계산**: 잔여수량 = 배정수량 - Σ(매도수량)
- **표시 방식 옵션**:
  * 미매도 수량을 별도 필드로 포함하여 표시
  * 매도 기록이 없는 배정은 "매도 없음" 상태 표시
  * 미매도 수량이 0인 경우 "전량 매도" 표시
  * 미매도 수량이 배정수량과 같은 경우 "미매도" 표시
- **참고**: sale-management.md에서 "잔여수량 = 배정수량 - Σ(매도수량)" 계산식을 명시하고 있음
- **참고**: allocation-management.md에서 "배정 수량과 잔여 수량" 개념을 다룸
- **검토 결과**: 투자 내역 조회 API에서는 각 배정 레코드에 **미매도 수량을 포함하여 표시**하고, 미매도 수량이 0인지 여부로 매도 완료 상태를 판단하는 방식이 적절함

### 5. 조회 API의 인가(계정 소유 범위 검증)·응답 오류 규격은 어떻게 정해야 하는가?
- **인가 검증**: 
  * 요청자의 계정 ID와 조회 대상 투자자/계좌/공모주의 소유 관계 검증 필수
  * 다른 계정의 데이터 접근 완전 차단 (account-authentication Epic 기반)
  * 투자자별, 계좌별, 공모주별 필터 적용 시 소유권 사전 검증 필요
- **응답 오류 규격**:
  * 400 Bad Request: 잘못된 파라미터 (예: 유효하지 않은 날짜 형식)
  * 401 Unauthorized: 인증되지 않은 요청
  * 403 Forbidden: 인증되었으나 접근 권한 없음 (다른 계정 데이터 접근 시도)
  * 404 Not Found: 요청된 리소스가 존재하지 않음
  * 422 Unprocessable Entity: 검증 오류 (예: 시작일이 종료일보다 늦음)
  * 500 Internal Server Error: 서버 내부 오류
- **오류 응답 형식**: 
  ```json
  {
    "errorCode": "VALIDATION_ERROR",
    "message": "시작일은 종료일보다 앞서야 합니다",
    "details": {"field": "startDate", "value": "2024-01-15"}
  }
  ```
- **검토 결과**: account-authentication Epic에서 계정별 데이터 접근 권한을 담당하므로, 투자 내역 조회 API에서는 **인증된 사용자의 계정 ID를 기준으로 자동으로 소유권 검증**을 수행하고, 명시적인 투자자/계좌 필터가 있을 경우에도 해당 소유권 추가 검증을 수행해야 함

## 제약사항
1. **데이터 무결성**: 조회 시점의 일관된 스냅샷 제공 필요 (동시성 이슈 고려)
2. **성능 요구사항**: 대용량 데이터셋에서도 응답 시간 보장 필요
3. **보안**: 계정 간 데이터 완전 격리 필수
4. **금융 데이터 특성**: 추정치 대신 실제 기록된 값만 제공
5. **작업 범위**: 대시보드 집계 전용 응답은 별도 Epic 12에서 처리
6. **의존성**: Epic 1~10 (모든 기록 도메인)이 선행되어야 함

## 불확실한 점
| # | 불확실한 점 | 영향도 | 비고 |
|---|-------------|--------|------|
| 1 | 기간 필터의 기본 기준 시점 (청약일/배정일/매도일 중 어느 것) | 높음 | 사용자 시나리오 조사 후 결정 필요 |
| 2 | 페이지네이션 방식 (offset/limit vs cursor) | 중간 | 데이터 volume과 동시성 고려 후 결정 |
| 3 | 미매도 기록의 구체적 표시 형식 | 낮음 | 별도 필드 vs 상태 플래그 조합 방식 결정 필요 |
| 4 | 정렬 옵션의 구체적 범위 및 기본 정렬 순서 | 낮음 | 사용자 요구사항 및 화면 설계 반영 필요 |
| 5 | 오류 응답의 세부 코드 체계 및 메시지 언어 정책 | 낮음 | 서비스 전체 일관성 고려 후 결정 |

## 결론
투자 내역 조회 API는 사용자가 자신의 투자 기록을 다차원적으로 필터링하고 조회할 수 있도록 하는 핵심 인터페이스이다. 조사 결과, 매도 일시를 기간 필터의 기본 기준으로 하되 청약일·배정일도 옵션으로 제공하고, 매도 일시 DESC를 기본 정렬로 하는 cursor-based 페이지네이션 방식을 적용하는 것이 적절할 것으로 판단된다. 미매도 기록은 배정별 잔여 수량을 포함한 형태로 표시하고, 계정 소유 범위 검증은 인증된 사용자의 계정 ID를 기준으로 자동 수행하며, 명시적 필터에 대해서도 추가 소유권 검증을 수행해야 한다. 단, 기간 필터의 최종 기준 시점과 페이지네이션 구체 방식은 추가적인 사용자 시나리오 조사 후 확정되어야 한다.
