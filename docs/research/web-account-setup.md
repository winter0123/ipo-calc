# 조사 문서: 웹 계정 설정 (Epic 13 Phase 0)

## 조사 목적

웹 기반 계정 설정 흐름(로그인, 회원가입, 투자자 등록, 증권계좌 등록)의 프론트엔드 구현을 위해 세션 기반 인증 처리 방식, 화면별 API 계약, 계좌번호 마스킹 및 입력 표현 표준, 접근성 및 반응형 디자인 기준, 주요 설정 흐름의 E2E 테스트 범위를 조사하고 spec/architecture 단계에서 결정해야 할 사항을 정리한다.

## 확인한 내용

### 1. 프론트엔드에서 세션 기반 인증을 어떻게 처리해야 하는가?

세션 기반 인증에서 프론트엔드는 로그인 성공 시 서버에서 발급한 세션 쿠키(JSESSIONID)를 자동으로 저장하고 후속 요청에 포함시켜야 한다. 이는 브라우저의 쿠키 저장 메커니즘을 통해 자동 처리되며, 프론트엔드는 수동으로 토큰을 관리할 필요가 없다. 로그아웃 시에는 서버의 로그아웃 엔드포인트를 호출하여 세션을 무효화하고, 쿠키를 삭제해야 한다. 세션 타임아웃 상황에 대비하여 401 응답을 처리하고 로그인 페이지로 리다이렉트하는 메커니즘이 필요하다.

### 2. 화면별 API 계약은 어떤 것이 필요한가 (로그인/회원가입/투자자 등록/증권계좌 등록)?

- **로그인**: `POST /auth/login` (email, password) → 200 OK (세션 쿠키 설정) 또는 401 Unauthorized — account-authentication Epic에서 이미 구현된 실제 엔드포인트(spec.md AC-004~007)
- **회원가입**: `POST /accounts` (email, password, name) → 201 Created (accountId, email 반환) 또는 409 Conflict(중복 이메일)/400 Bad Request — account-authentication Epic에서 이미 구현된 실제 엔드포인트(spec.md AC-001~003)
- **투자자 등록**: 경로 미정 — investor-management Epic(2)이 아직 구현 전이므로 후보로만 제시(예: `POST /investors`), 유효성 검사 실패 시 400 Bad Request
- **증권계좌 등록**: 경로 미정 — securities-account-management Epic(4)이 아직 구현 전이므로 후보로만 제시(예: `POST /securities-accounts`), 계좌번호 형식 검증 실패 시 400 Bad Request

모든 API는 인증이 필요한 경우 401 응답을 반환하며, 프론트엔드는 이를 처리하여 로그인 페이지로 리다이렉트해야 한다.

### 3. 계좌번호 마스킹과 상세 입력 표현은 어떻게 해야 하는가?

계좌번호는 보안을 위해 화면에 표시할 때 일부만 마스킹해야 한다(예: 앞 2자리 + \*\_\_\_\_\_ + 뒤 4자리 형태). 입력 시에는 자동으로 하이픈 또는 스페이스를 삽입하여 가독성을 높이되, 서버 전송 시에는 숫자만 전달해야 한다. 계좌번호 형식 검증은 프론트엔드에서 1차 수행하고(길이, 숫자만 허용), 서버에서 2차 검증해야 한다(은행별 형식 규칙 적용). 오류 표시는 필드 옆에Inline 형태로 보여주며, 성공 시에는 마스킹된 형태로 표시하여 재확인 가능하게 해야 한다.

### 4. 접근성·반응형 기준은 무엇을 따라야 하는가?

접근성은 WCAG 2.1 AA 기준을 따라야 하며, 주요 항목으로는 충분한 색 대비 비율(4.5:1), 키보드 내비게이션 지원, ARIA 라벨 및 역할 적절히 사용, 폼 라벨과 입력 요소의 명확한 연결, 에러 메시지의 스크린 리더 접근성 등이 있다. 반응형 디자인은 모바일-first 접근법을 따라야 하며, 최소 320px 폭부터 지원하고, 브레이크포인트는 640px(모바일), 768px(태블릿), 1024px(데스크톱)을 기준으로 구성 요소의 레이아웃을 조정해야 한다. 텍스트 크기는 사용자 설정을 존중하여 rem 단위를 사용해야 한다.

### 5. 주요 설정 흐름의 E2E 테스트 범위는 어디까지인가?

주요 설정 흐름의 E2E 테스트 범위는 사용자 여정 전체를 커버해야 한다: 신규 사용자의 회원가입 → 로그인 → 투자자 등록 → 증권계좌 등록 → 대시보드 접근까지의 플로우. 또한 오류 케이스 테스트도 포함해야 한다: 잘못된 로그인 자격 증명, 중복 이메일 회원가입 시도, 유효하지 않은 계좌번호 입력, 필수 입력값 누락 등. 세션 지속성 테스트(페이지 새로고침 후 로그인 상태 유지)와 로그아웃 후 접근 차단도 검증해야 한다. 테스트는 실제 사용자 시나리오를 시뮬레이션하여 데이터베이스 상태 변경을 포함해야 하며, 외부 API 호출은 모킹하지 않고 실제 엔드포인트를 호출해야 한다.

## 결론

프론트엔드에서의 세션 기반 인증은 쿠키 기반 자동 처리를 활용하고, 로그인/로그아웃/세션 타임아웃 상황을 적절히 처리해야 한다. 계좌번호는 보안을 위해 마스킹하여 표시하고 입력 시에는 서식 지원을 제공하며, 모든 흐름은 WCAG 2.1 AA 접근성과 반응형 디자인 원칙을 따라야 한다. 주요 설정 흐름의 E2E 테스트는 성공 케이스와 오류 케이스를 모두 커버하여 사용자 여정 전반을 검증해야 한다.
