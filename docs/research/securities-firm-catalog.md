# 증권사 기준정보 관리 조사

## 조사 목적
증권사 기준정보(SecuritiesFirm)의 도메인 범위, 식별자 체계, 변경 처리 정책 및 삭제 정책을 조사하여 안전한 금융 데이터 관리 기반을 마련한다.

## 조사 대상
- 증권사 기준정보 도메인 모델
- 식별자 체계 (내부 ID vs 외부 표준코드)
- 기준정보 변경 시 참조 관계 처리 전략
- 삭제 정책 및 감사 로그 요구사항

## 확인한 내용

### 질문 1: 증권사 기준정보의 소유 범위
증권사 기준정보는 최소한 다음과 같은 필드가 필요하다:
- 증권사명 (필수)
- 사업자등록번호 (선택적, 중복 방지 및 외부 연동 시 유용)
- 증권사 코드 (선택적, 금융투자협회 표준코드 등)
- 연락처 정보 (주소, 전화번호 등 - 선택적)
- 등록일자 및 수정일자 (감사 목적)

그러나 금융 데이터의 특성과 서비스 범위를 고려할 때, 증권사명과 안정적 식별자만으로도 MVP의 핵심 기능인 증권계좌와의 참조 관계를 구축할 수 있다. 추가적인 사업자 정보는 외부 연동이 필요한 경우에만 확장한다.

### 질문 2: 수동 등록과 외부 출처 활용을 위한 식별자 체계
수동 등록 방식으로 시작하되 향후 외부 출처 활용을 고려한 하이브리드 식별자 체계를 권장한다:
- 내부 식별자 (Primary Key): 서비스 내부에서 생성되는 UUID 또는 시퀀스 기반 ID
- 외부 식별자 (Alternative Key): 금융투자협회 표준코드 등 외부 표준코드를 저장할 수 있는 별도 필드
- 중복 방지: 외부 식별자가 있는 경우 해당 값으로 유니크 제약 적용, 없는 경우 내부 식별자만으로 유일성 보장

이 approach는 수동 등록으로 시작하되 외부 데이터 통합 시 표준코드를 활용할 수 있는 유연성을 제공한다.

### 질문 3: 기준정보 변경 시 기존 기록 처리 방식
증권사명 변경 시 기존 증권계좌 및 청약 기록과의 참조 관계를 유지하기 위해 다음과 같은 전략을 제안한다:
- 참조 무결성 유지: SecuritiesAccount와 SecuritiesFirm 간의 외부 키 관계 유지
- 변경 이력 테이블: SecuritiesFirmNameHistory 테이블을 통해 과거 이름 변경 내역 기록
- 표시 로직: 현재 이름이 아닌 기록 시점의 이름을 보여주는 로직 구현 (조인 시 시점 기반 이름 선택)
- 대안: 별도 이력 관리 없이 현재 이름만 저장하고, 기록 시점의 이름은 별도 계산 필드로 제공 (성능 고려)

변경 이력 관리 방식을 채택하면 금융 데이터의 추적 가능성을 보장하면서도 복잡한 시점 기반 쿼리를 피할 수 있다.

### 질문 4: 증권사 기준정보의 삭제 정책
금융 데이터의 특성과 데이터 무결성 요구사항을 고려한 삭제 정책:
- 물리 삭제 금지: 계좌가 연결된 증권사는 삭제 불가 (참조 무결성 위반 방지)
- 논리 삭제 활성화: `is_active` 또는 `deleted_at` 컬럼을 통한 소프트 삭제
- 감사 로그 요구사항: 삭제 시도 이력 기록 (who, when, reason)
- 제한적 삭제 조건: 연결된 증권계좌가 전혀 없는 경우에만 물리 삭제 허용 (극히 예외적 상황)
- 대안적 접근: 삭제 대신 비활성화 처리하고, 신규 계좌 생성 시 비활성화된 증권사 선택 방지

작업 계획서 22~23장에 따라 금융 기록은 단순한 CRUD처럼 처리하지 않고 수정 이력 및 감사 로그를 고려해야 한다.

## 제약사항
- 외부 데이터 제공처(금융투자협회 등)의 이용 약관 및 기술적 접근성은 이번 조사에서 확인하지 않음
- 특정 증권사 목록이나 표준코드 체계를 확정하지 않음 (향후 별도 조사 대상)
- 구현 단계에서의 성능 최적화 고려 사항은 이 문서에서 다루지 않음

## 불확실한 점
- 금융투자협회 표준코드의 실제 존재 여부 및 활용 가능성
- 증권사명 변경 빈도 및 실제 사업자 등록번호 변경 사례
- 외부 데이터 연동 시 중복 처리 로직의 복잡도
- 감사 로그의 상세 수준 (누가, 언제, 무엇을 변경했는지 vs 단순히 변경 사실만 기록)

## 개발에 미치는 영향
- 도메인 모델 설계 시 식별자 체계를 이중 구조로 준비해야 함
- 참조 무결성을 유지하면서도 변경 이력을 관리할 수 있는 쿼리 전략 필요
- 삭제 대신 비활성화 패턴을 채택한 서비스 레이어 로직 구현 필요
- 테스트 시 참조 무결성 제약 조건과 소프트 삭제 로직을 모두 검증해야 함

## 결론
증권사 기준정보는 내부 식별자와 외부 표준코드를 모두 지원하는 이중 구조로 설계하고, 변경 시 이력 테이블을 통해 과거 내역을 추적하며, 삭제 대신 비활성화 처리하여 금융 데이터의 추적 가능성과 참조 무결성을 동시에 보장해야 한다. 수동 등록으로 시작하되 외부 데이터 연동 가능성을 열어둔 하이브리드 접근 방식이 가장 적절하다.
