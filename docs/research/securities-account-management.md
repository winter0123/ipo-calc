# 증권계좌 관리 (securities-account-management) 조사 문서

## 조사 목적

Epic 4 `securities-account-management` 구현에 앞서, 계좌번호 저장 정책, 마스킹 및 상세 조회 권한, 삭제 시 참조 무결성, 기본 계좌 지정 및 동시성 처리 원칙을 조사하여 안전한 금융 데이터 관리 기반을 마련한다.

## 조사 대상

- `SecuritiesAccount` 도메인 엔티티의 계좌번호 속성 처리 방안
- 계좌번호 마스킹 정책 및 상세 조회(전체 노출) 권한 조건
- 계좌 삭제·비활성화 시 기존 `Subscription` 기록과의 참조 유지 방식
- 투자자당 기본 계좌 지정 규칙 및 동시 계좌 변경 요청 처리 원칙

## 확인한 내용

### 질문 1: 계좌번호를 전체 저장해야 하는가, 마스킹 저장(예: 뒷 4자리만 평문, 나머지 마스킹)이 적절한가 — 개인정보/금융정보 보호 관점에서.

**work-plan-ipo-investment.md 46장(로그)**:
- "계좌번호 전체"는 무조건 로그로 출력하지 않는다.
- 필요한 경우 마스킹한다.

**work-plan-ipo-investment.md 28장(인증과 개인정보), 29장(보안 기본 원칙)**:
- "개인정보 최소 수집", "민감한 계좌정보 저장 여부", "로그에 민감정보 출력 금지"
- 계좌번호는 별도 `SecuritiesAccount` 도메인에서 관리, 마스킹 처리 (투자자 관리 조사 문서에서 유사 내용 확인)

**개인정보보호법 제3조(개인정보보호 원칙), 제15조(개인정보의 수집·이용)**:
- 최소 수집 원칙: 처리 목적 달성에 필요한 최소한의 개인정보만 수집
- 계좌번호는 금융 거래 기록과의 참조를 위해 필요하나, 전체 노출보다는 마스킹 표기가 충분할 수 있음

**결론**:
- 계좌번호는 식별 및 참조를 위해 내부 식별자(Primary Key)로 관리하고, 실제 계좌번호 값은 암호화하거나 엄격한 접근 제어를 적용하여 저장한다.
- 화면 표시 또는 API 응답에서는 마스킹 처리(예: 뒷 4자리만 노출)를 기본으로 하며, 전노출이 필요한 경우는 엄격한 인가 절차를 거친다.
- 로그에는 절대 계좌번호 전체를 출력하지 않고, 마스킹 처리된 형태만 남긴다.

### 질문 2: 마스킹된 계좌번호를 상세 조회(전체 노출)할 수 있는 권한은 누구에게, 어떤 조건으로 부여해야 하는가?

**work-plan-ipo-investment.md 22장(데이터 무결성)**:
- 금융 데이터이므로 잘못된 데이터가 들어가지 않도록 해야 한다.
- 단, 구체적인 인가 로직은 명시되지 않음.

**투자자 관리 조사 문서 (docs/research/investor-management.md) 질문 2 답변 유사 내용**:
- 개인정보 최소 수집 원칙에 따라 계좌번호는 별도 `SecuritiesAccount` 도메인에서 관리·마스킹.
- 로그/감사로그 마스킹 대상: 계좌번호는 별도 마스킹 (work-plan 29장, 46장)

**개인정보보호법 제15조 제1항, 제18조(목적 외 이용·제공 제한)**:
- 처리 목적: "투자자별 청약·배정·매도·수익 기록 관리 및 조회"
- 계좌번호 전체 노출은 해당 목적에 직접 필요하지 않을 수 있으며, 최소한의 정보(마스킹)로 충분할 가능성이 높음.

**결론**:
- 계좌번호 전체 노출은 계좌 소유자(해당 투자자의 로그인 계정) 또는 시스템 관리자에게만 제한적으로 허용해야 한다.
- 허용 조건: (1) 요청자가 해당 계좌의 소유 투자자를 가진 로그인 계정인 경우, (2) 추가 인증 단계(예: 재인증)를 거친 경우, (3) 감사 로그에 접근 기록이 남는 경우.
- 일반적인 조회 API에서는 마스킹된 계좌번호만 반환하고, 전노출 전용 엔드포인트는 별도로 설계하여 엄격한 인가 처리를 적용한다.

### 질문 3: 계좌 삭제·비활성화 시 기존 청약 기록(Subscription)과의 참조는 어떻게 유지되는가(work-plan 23장 삭제 정책 참고)?

**work-plan-ipo-investment.md 23장(삭제 정책)**:
- "금융 기록은 단순한 CRUD처럼 처리하지 않는다."
- "물리 삭제, 논리 삭제, 수정 이력, 감사 로그" 검토 필요.
- "각 도메인별로 삭제 정책을 결정한다" — 투자자(기준정보 성격)와 매도/청약(금융 기록 성격) 구분.

**투자자 관리 조사 문서 (docs/research/investor-management.md) 질문 3 답변**:
- 금융실명법 제4조(금융거래 비밀보장), 전자금융거래법 제22조(거래기록 보존): 금융거래 기록: 5년 이상 보존 의무.
- 일반적 설계 관행: 금융 기록(Subscription, Allocation, Sale, Cost)은 **물리 삭제 금지**, 논리 삭제만 허용.
- Investor 구체적 정책: 물리 삭제 절대 금지, 비활성화(Soft Delete) 허용, 기존 기록 조회/수익 계산은 정상 동작.

**SecuritiesFirm 관리 조사 문서 (docs/research/securities-firm-catalog.md) 질문 4 답변**:
- 물리 삭제 금지: 계좌가 연결된 증권사는 삭제 불가 (참조 무결성 위반 방지)
- 논리 삭제 활성화: `is_active` 또는 `deleted_at` 컬럼을 통한 소프트 삭제
- 감사 로그 요구사항: 삭제 시도 이력 기록 (who, when, reason)

**결론**:
- `SecuritiesAccount`는 금융 기록과의 참조 관계에서 `Subscription` 등 금융 도메인과 유사한 삭제 정책을 적용한다.
- 물리 삭제는 금지하고, 논리 삭제(Soft Delete)를 사용한다(`deleted_at` 타임스탬프, `status` 컬럼).
- 비활성화 시: 신규 청약/매도 기록 생성은 차단하되, 기존 기록은 정상적으로 조회 및 수익 계산에 포함된다.
- 참조 무결성을 위해 외래 키 제약 조건은 `ON DELETE RESTRICT` 유지하여, 참조 중인 계좌는 삭제조차不可能하게 한다(비활성화만 허용).

### 질문 4: "기본 계좌" 지정 규칙(투자자당 여러 계좌 중 하나를 기본으로 지정하는 경우)과 동시에 여러 요청이 기본 계좌를 바꾸려 할 때의 동시성 처리 일반 원칙은 무엇인가?

**work-plan-ipo-investment.md 45장(동시성)**:
- "잔여 배정 수량 계산", "매도 수량 검증", "수익 계산" 등은 데이터 정합성이 중요하다.
- 동시에 여러 매도 요청이 들어오는 경우를 어떻게 처리할지 설계 단계에서 검토한다.
- 명시적 기본 계좌 관련 내용은 없음.

**투자자 관리 조사 문서 (docs/research/investor-management.md) 질문 5 답변 유사 내용**:
- 1 Account : N Investor 관계에서 동일 계정 내 투자자 이름 중복 허용 여부 검토.
- 중복 허용 + UI에서 투자자 식별자(UUID) 기반으로 구분 권장.
- 비활성화된 투자자 이름은 `deleted_at`이 NULL이 아닌 레코드는 중복 검사에서 제외(재활성화·재사용 허용).

**일반적 설계 관행 (금융 시스템)**:
- 기본 계좌 지정은 투자자당 정확히 하나만 허용해야 함.
- 변경을 위한 트랜잭션 내에서 기존 기본 계좌의 기본 플래그를 해제하고 새 계좌에 설정하는 원자적 işlem이 필요.
- 동시성 제어를 위해 낙관적 락(version 컬럼) 또는 비관적 락(SELECT FOR UPDATE)을 적용하여 한 번에 하나의 요청만 처리하도록 보장.

**결론**:
- 투자자당 기본 계좌는 `is_default` 블린 컬럼으로 관리하며, 데이터베이스 수준에서 부분 유니크 제약 조건(`WHERE is_default = TRUE`)을 통해 투자자당 하나만 참으로 설정할 수 있도록 한다.
- 기본 계좌 변경 요청은 트랜잭션 내에서 기존 기본 계좌의 플래그를 해제하고 새 계좌에 설정하는 로직을 수행하며, 이를 위해 투자자 레코드를 잠그거나 버전 검사를 적용하여 동시성 문제를 방지한다.
- 동시에 여러 요청이 들어올 경우, 먼저 온 요청만 성공하고 이후 요청은 오류(기본 계좌 변경 중 또는 이미 기본 계좌가 지정됨)를 반환한다.

## 제약사항

1. **개인정보보호법 준수**: 계좌번호는 개인정보에 해당하므로 최소 수집 목적 외 이용 금지, 보유·이용 기간 준수.
2. **금융실명거래 및 비밀보장에 관한 법률**: 계좌번호는 금융거래 정보로 간주되어 비밀 보장 의무가 있음.
3. **work-plan 23장**: 금융 기록은 단순한 CRUSH처럼 처리하지 않는다 → 물리 삭제 금지, 논리 삭제만 허용.
4. **work-plan 46장**: 로그에 계좌번호 전체 출력 금지, 필요한 경우 마스킹 처리.
5. **work-plan 9장**: 증권사와 계좌는 별도 도메인으로 관리 → 계좌번호는 `SecuritiesAccount` 속성으로 관리하며, 증권사 식별자는 외부 키로 참조.
6. **MVP 범위(work-plan 37장)**: 자동 증권사 연동, 실제 계좌 잔고·거래 내역 가져오기 제외 → 계좌번호는 수동 입력 기반으로 관리.

## 개발에 미치는 영향

1. **SecuritiesAccount 엔티티 설계**: 내부 식별자(UUID 또는 시퀀스 ID), 증권사 외부 키, 계좌번호(암호화 저장 고려), `is_active` 또는 `deleted_at` 컬럼, `is_default` 컬럼, 감사 필드(`created_at`, `updated_at`) 포함.
2. **계좌번호 마스킹 로직**: 서비스 계층에서 계좌번호 전체를 반환하지 않는 기본 조회 메서드 제공, 전노출 전용 메서드는 별도로 설계하여 인가 검증 필수.
3. **삭제 정책 구현**: 물리 삭제 금지, `deleted_at` 컬럼을 통한 소프트 삭제 구현, 외래 키 제약 조건은 `ON DELETE RESTRICT` 유지.
4. **기본 계좌 처리**: 투자자당 하나만 `is_default = TRUE`를 유지하는 부분 유니크 인덱스 추가, 트랜잭션 내 기본 계좌 변경을 위한 서비스 메서드 구현.
5. **동시성 처리**: 기본 계좌 변경을 위한 서비스 메서드에 투자자 레코드 버전 확인(낙관적 락) 또는 `SELECT FOR UPDATE` 적용.
6. **테스트 전략**: 계좌번호 마스킹 테스트, 소프트 삭제 후 기존 기록 조회 테스트, 기본 계좌 변경 동시성 테스트(다중 요청 시 하나만 성공), 인가 우회 시도 차단 테스트.

## 결론

1. **계좌번호 저장**은 내부 식별자로 분리하고, 실제 값은 암호화하거나 엄격한 접근 제어를 적용하여 저장하며, 화면/API에서는 마스킹 처리(예: 뒷 4자리)를 기본으로 한다. 로그에는 절대 계좌번호 전체를 출력하지 않는다.
2. **계좌번호 전체 노출**은 계좌 소유자 또는 시스템 관리자에게만 엄격한 인가(재인증 등) 후에 제한적으로 허용하며, 일반적인 조회에서는 마스킹된 계좌번호만 반환한다.
3. **계좌 삭제·비활성화**는 물리 삭제를 금지하고 논리 삭제(Soft Delete)를 적용하여 기존 `Subscription` 등 금융 기록과의 참조 무결성을 유지하며, 비활성화 계좌는 신규 기록 생성을 차단하되 기존 기록은 정상적으로 활용한다.
4. **기본 계좌 지정**은 투자자당 하나만 참으로 설정할 수 있는 데이터베이스 수준 제약을 활용하고, 변경을 위한 트랜잭션 내 원자적 업데이트 및 낙관적 락 또는 pessimistic 락을 적용하여 동시성 문제를 방지한다.
