# 청약 기록 (subscription-management) 조사 문서

## 조사 목적
Epic 6 `subscription-management` 구현에 앞서, 청약 상태 목록 및 전이 규칙, 증거금과 환불 금액 기록 방식, 중복 청약 방지 메커니즘, 청약 기록 수정 가능 범위, 동시성 제어 원칙을 조사하여 안전한 금융 데이터 관리 기반을 마련한다.

## 조사 대상
- `Subscription` 도메인 엔티티의 상태값 및 전이 규칙
- 증거금 및 환불 금액의 저장 의미 및 기록 방식
- 동일 투자자·계좌·공모주에 대한 중복 청약 방지 메커니즘
- 청약 기록의 수정 가능 필드 및 변경 추적 방법
- 동시에 여러 청약 요청이 들어올 때의 동시성 제어 필요성

## 확인한 내용

### 1. 청약 상태 목록과 전이 규칙
**work-plan.md 21장(상태값 설계)**:
- 각 도메인의 상태값은 문자열을 무분별하게 사용하지 않는다.
- 예시 상태: 청약 예정, 청약 진행 중, 청약 완료, 배정 완료, 일부 매도, 전량 매도, 보유 중
- 실제 상태 목록은 사용 시나리오와 데이터 모델링을 바탕으로 정의한다.
- 상태 전이가 가능한 경우 전이 규칙도 문서화한다.

**roadmap.md Epic 6 상세 (진행 전 필요한 조사)**:
- 청약 상태 목록과 전이 규칙을 조사하되, 구체적인 금융 규칙은 조사 결과를 사람의 결정 후 반영한다.
- 예시 제시: 청약대기→청약완료→배정대기→배정완료 등

**확인한 내용**:
- 청약 도메인의 상태는 청약 생명주기를 나타내며, 최소한 다음과 같은 상태가 고려될 수 있음:
  * 청약대기 (Subscription 대기 중)
  * 청약완료 (청약 신청 완료)
  * 배정대기 (배정 결과 대기 중)
  * 배정완료 (배정 결과 확정)
  * 취소 (청약 취소됨)
- 전이 규칙 예시 후보:
  * 청약대기 → 청약완료 (청약 신청 시)
  * 청약완료 → 배정대기 (청약 마감 후 배정 처리 시작 시)
  * 배정대기 → 배정완료 (배정 결과 확정 시)
  * 청약완료 → 취소 (청약 취소 요청 시, 배정 이전까지 가능)
  * 배정완료 → 취소 불가 (배정 확정 후 취소 제한 가능성 있음)
- **사람 결정 필요**: 최종 상태 목록과 전이 규칙은 금융 규정 및 비즈니스 로직에 따라 결정되어야 하며, 본 조사에서는 후보를 제시하고 정확한 정의는 후속 기획 단계에서 확정해야 함.

### 2. 증거금과 환불 금액 기록 방식
**work-plan.md 11장(Subscription 도메인)**:
- Subscription에서 검토해야 할 값: 청약 수량, 청약 금액, 청약 일시, 증거금, 환불 금액, 청약 상태, 기타 필요한 값
- 정확한 필드 목록은 설계 단계에서 확정한다.

**확인한 내용**:
- 증거금: 투자자가 청약 시 납입해야 하는 금액 (청약 수량 × 공모가 또는 기타 기준)
- 환불 금액: 배정 후 미배정 수량에 대한 증거금 반환액 (예: 100주 청약, 30주 배정 시 70주 미배정분에 대한 환불)
- 기록해야 할 사항:
  * 증거금 납입 금액 및 일시
  * 환불 금액 및 일시 (배정 완료 후 발생)
  * 실제 청약에 사용된 금액 (증거금에서 환불 금액을 제외한 순 투자금)
- **사람 결정 필요**: 증거금과 환불 금액의 정확한 정의 및 기록 시점(청약 시점 vs 배정 시점)은 금융 규정 및 증권사 정책에 따라 결정되어야 하며, 본 조사에서는 기록 대상은 확인했으나 구체적인 계산 로직과 처리 시점은 후속 기획 단계에서 확정해야 함.

### 3. 동일 투자자·계좌·공모주 중복 청약 방지
**work-plan.md 22장(데이터 무결성)**:
- 금융 데이터이므로 잘못된 데이터가 들어가지 않도록 해야 한다.
- 동일한 투자 기록을 중복 생성할 가능성도 검토한다.
- 각 도메인의 중요한 불변조건을 테스트로 작성한다.

**확인한 내용**:
- 중복 청약 방지를 위한 방법 후보:
  * 고유 제약 조건: (투자자ID, 계좌ID, IPOID)에 대한 유니크 인덱스 생성
  * 애플리케이션 레벨 검증: 청약 생성 전 동일 투자자·계좌·공모주에 대한 기존 청약 존재 여부 확인
  * 상태 기반 제한: 특정 상태(예: 청약완료, 배정완료)에서는 중복 청약 허용하지 않음
- 데이터 무결성 관점에서 DB 수준의 유니크 제약 조건이 가장 신뢰성 높은 방안임
- **사람 결정 필요**: 중복 청약의 기준(투자자 단위 vs 계좌 단위 vs 투자자+계좌 단위)과 허용 예외(예: 취소 후 재청약 가능 여부)는 비즈니스 정책에 따라 결정되어야 하며, 본 조사에서는 방 necessity는 확인했으나 구체적인 구현 방식과 예외 사항은 후속 기획 단계에서 확정해야 함.

### 4. 청약 기록의 수정 가능 범위
**work-plan.md 36장(데이터 변경 추적)**:
- 투자 데이터는 사용자가 나중에 수정할 수 있다.
- 예: 청약 수량 100 → 200 또는 매도 수량 수정
- 수정 가능한 데이터와 수정하면 안 되는 데이터를 구분한다.
- 필요한 경우 변경 이력 구조를 검토한다.

**확인한 내용**:
- 수정 가능성 검토 대상:
  * 청약 수량: 청약 후 증가/감소 가능성 (예: 청약 기간 내 수정 허용)
  * 청약 금액: 수량 변경에 따라 자동 재계산 또는 직접 수정
  * 청약 일시: 일반적으로 수정 불가 (청약 발생 시점 기록)
  * 증거금: 금액 변경 시 재계산 필요
  * 환불 금액: 배정 후 자동 계산되어 수정 불가
  * 청약 상태: 상태 전이에 따라 자동 수정
- 금융 기록의 특성상 ciertos 필드는 수정 시 Audit trail이 필요함
- **사람 결정 필요**: 어떤 필드가 언제까지 수정 가능한지(예: 청약 마감 전까지만 수량 수정 가능)와 수정 시 필요한 승인 절차는 금융 규정 및 내부 정책에 따라 결정되어야 하며, 본 조사에서는 수정 가능성은 확인했으나 구체적인 수정 가능 필드, 시점 제한, 및 변경 추적 방식은 후속 기획 단계에서 확정해야 함.

### 5. 동시에 여러 청약 요청이 들어올 때 동시성 제어
**work-plan.md 45장(동시성)**:
- 향후 여러 요청이 동시에 발생할 가능성을 고려한다.
- 특히 다음은 데이터 정합성이 중요하다:
  - 잔여 배정 수량 계산
  - 매도 수량 검증
  - 수익 계산
- 동시에 여러 매도 요청이 들어오는 경우를 어떻게 처리할지 설계 단계에서 검토한다.

**확인한 내용**:
- 청약 시 동시성 문제 발생 시나리오:
  * 동일 투자자·계좌·공모주에 대한 중복 청약 시도 (질문 3과 관련)
  * 증거금 잔액 확인 및 차감 과정에서의 경쟁 조건
  * 공모주별 청약 한도 적용 시 경쟁 조건
- 동시성 제어 방법 후보:
  * 낙관적 락 (Optimistic Locking): 버전 컬럼을 사용하여 충돌 감지
  * 비관적 락 (Pessimistic Locking): SELECT FOR UPDATE를 통한 레코드 잠금
  * 트랜잭션 격리 수준: 적절한 격리 수준 설정 (예: READ_COMMITTED, SERIALIZABLE)
  * 애플리케이션 레벨 락: 분산 락 또는 뮤텍스 사용
- **사람 결정 필요**: 구체적인 동시성 제어 방식은 성능 요구사항과 데이터 정합성 중요도에 따라 결정되어야 하며, 본 조사에서는 동시성 제어 필요성은 확인했으나 적용 범위(전체 청약 프로세스 vs 특정 critical section)와 구현 방식은 후속 기획 단계에서 확정해야 함.

5. **work-pan 11장**: 정확한 필드 목록은 설계 단계에서 확정해야 함
6. **금융 데이터 특성상 증거와 ohne 추정 금지**: 특히 금융 규칙 관련 사항은 사람의 결정 필요

## 개발에 미치는 영향
1. **Subscription 엔티티 설계**: 상태 컬럼, 증거금/환불 금액 컬럼, 투자자·계좌·IPO 외부 키, 청약 수량/금액/일시 컬럼, 생성/수정 타임스탬프 포함 계획
2. **중복 방지 메커니즘**: DB 수준 유니크 제약 조건 또는 애플리케이션 레벨 검증 구현 필요
3. **증거금/환불 처리 로직**: 배정 완료 시 환불 계산 로직 및 금액 추적 필요
4. **변경 추적 기능**: 수정 가능한 필드에 대한 변경 이력 테이블 또는 감사 로그 구현 필요
5. **동시성 제어 메커니즘**: 트랜잭션 관리 및 락 전략을 서비슨 계층에 적용 필요
6. **테스트 전략**: 상태 전이 테스트, 중복 방지 테스트, 동시성 테스트, 수정 가능 범위 테스트 등 필요

## 결론
청약 기록 도메인은 투자자·계좌·IPO 관계를 기록하는 핵심 금융 도메인으로, 상태 관리, 금액 처리, 데이터 무결성, 변경 추적, 동시성 제어가 모두 중요한 요소이다. 조사 결과, 확인해야 할 사항은 많으나 금융 규정과 비즈니스 로직에 따른 사람의 결정이 필요한 사항이 다수 존재한다. 본 조사에서는 후보를 제시하고 불확실한 점을 명시했으며, 후속 기획 단계에서 정확한 정의가 이루어져야 한다. 특히 증거금과 환불 금액 처리, 상태 전이 규칙, 중복 청약 방지 기준은 금융 데이터의 정확성을 위해 사람의 명확한 결정이 선행되어야 구현을 진행할 수 있다.
