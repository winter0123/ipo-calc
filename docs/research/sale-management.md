# 분할 매도 기록 (sale-management) 조사 문서

## 조사 목적
Epic 8 `sale-management` 구현에 앞서, 분할 매도의 상태와 순서 표현 방식, 부분 취소·수정 시 잔여 수량 재계산 방법, 동시 매도 요청 시 배정 수량 초과 방지 메커니즘, 매도 기록의 삭제·보존 정책을 조사하여 안전한 금융 데이터 관리 기반을 마련한다.

## 조사 대상
- `Sale` 도메인 엔티티의 구조 및 필수 필드
- `Allocation`에서 `Sale`로의 관계 및 매도 순서 표현
- 부분 취소·수정 시 잔여 수량(배정수량-누적매도수량) 재계산 로직
- 동시 매도 요청 시 배정 수량 초과 방지 메커니즘
- 매도 기록의 삭제·보존 정책

## 확인한 내용

### 1. 분할 매도의 상태와 순서는 어떻게 표현해야 하는가
**work-plan-ipo-investment.md 13장(Sale 도메인)**:
- 매도는 한 번에 끝난다고 가정하지 않는다.
- 하나의 배정 결과에 여러 번의 매도가 있을 수 있다.
- 예시: 배정: 10주 → 매도 1: 3주, 매도 2: 4주, 잔여: 3주
- 따라서 다음 구조를 고려한다: Allocation → N Sale

**roadmap.md Epic 8 상세 (진행 전 필요한 조사)**:
- 분할 매도의 상태와 순서는 어떻게 표현해야 하는가(예: 매도 1, 매도 2... 순차 기록, 순서가 비즈니스적으로 의미 있는가)?

**확인한 내용**:
- 매도 순서는 비즈니스적으로 의미 있음 (첫 매도, 두 번째 매도 등으로 수익 계산 시 중요)
- 매도 순서 표현 방법:
  * 매도 일시 기준 순서 자동 정렬 (Creation timestamp 기준)
  * 명시적인 순서 번호 필드 추가 (sale_sequence: Integer)
  * 매도 일시와 순서 번호 병용 (일시 기준 정렬 + 동일 일시 시 순서 번호로 구분)
- 매도 상태 표현:
  * 작업 계획서 21장(상태값 설계)에서 제시한 상태 목록 참고: 청약 예정, 청약 진행 중, 청약 완료, 배정 완료, 일부 매도, 전량 매도, 보유 중
  * Sale 도메인에서는 매도 자체가 완료된 행위이므로 별도 상태 필드보다 매도 일시와 수량으로 상태 유추
  * 잔여 수량 기반으로 투자자 뷰에서 일부 매도/전량 매도/보유 중 상태 표시 가능
- **사람 결정 필요**: 매도 순서 표현 방법(자동 일시 기반 vs 명시적 순서 번호)과 매도 상태 표현 방식은 비즈니스 요구사항에 따라 결정되어야 함

### 2. 매도 기록을 부분 취소·수정할 때 잔여 수량(배정수량-누적매도수량)을 어떻게 재계산해야 하는가
**work-plan-ipo-investment.md 13장(Sale 도메인)**:
- 매도 정보에는 최소한 다음 항목을 검토한다:
  * 매도 수량
  * 매도 가격
  * 매도 금액
  * 매도 일시
  * 수수료
  * 세금
  * 기타 비용

**work-plan-ipo-investment.md 22장(데이터 무결성)**:
- 금융 데이터이므로 잘못된 데이터가 들어가지 않도록 해야 한다.
- 예를 들어: 매도 수량 > 배정 수량
- 또한: 매도 총수량 > 배정 수량 도 허용하지 않는다.

**work-plan-ipo-investment.md 36장(데이터 변경 추적)**:
- 투자 데이터는 사용자가 나중에 수정할 수 있다.
- 예: 청약 수량 100 → 200 또는 매도 수량 수정
- 수정 가능한 데이터와 수정하면 안 되는 데이터를 구분한다.
- 필요한 경우 변경 이력 구조를 검토한다.

**확인한 내용**:
- 잔여 수량 계산식: 잔여수량 = 배정수량 - Σ(매도수량)
- 부분 취소·수정 시 재계산 로직:
  * 매도 기록 수정 시: 새로운 잔여수량 = 배정수량 - (기존 누적매도수량 - 기존매도수량 + 새로운매도수량)
  * 매도 기록 삭제 시: 새로운 잔여수량 = 배정수량 - (기존 누적매도수량 - 삭제매도수량)
  * 매도 기록 추가 시: 새로운 잔여수량 = 배정수량 - (기존 누적매도수량 + 추가매도수량)
- 데이터 무결성 검증:
  * 개별 매도: 매도 수량 ≥ 0
  * 누적 검증: Σ(매도수량) ≤ 배정수량
  * 수정 후 재검증 필수
- 변경 추적 고려:
  * 매도 기록은 금융 기록이므로 단순한 수정보다 이력 추적이 필요할 수 있음
  * 수정 가능한 필드: 매도 가격, 매도 금액, 수수료, 세금, 기타 비용 (오류 수정 목적)
  * 수정 불가 필드: 매도 수량, 매도 일시 (핵심 거래 사실 변경 시 새로운 기록으로 처리 권장)
- **사람 결정 필요**: 매도 기록의 수정 가능 범위(어떤 필드를 언제 수정할 수 있는지)와 변경 이력 관리 방식은 금융 규정 및 비즈니스 정책에 따라 결정되어야 함

### 3. 동시에 여러 매도 요청이 들어올 때(예: 같은 배정에 대해 동시에 매도 2건) 배정 수량 초과를 어떻게 막는가
**work-plan-ipo-investment.md 45장(동시성)**:
- 향후 여러 요청이 동시에 발생할 가능성을 고려한다.
- 특히 다음은 데이터 정합성이 중요하다:
  * 잔여 배정 수량 계산
  * 매도 수량 검증
  * 수익 계산
- 동시에 여러 매도 요청이 들어오는 경우를 어떻게 처리할지 설계 단계에서 검토한다.

**확인한 내용**:
- 동시성 문제 시나리오:
  * 동일 배정에 대한 두 개의 동시 매도 요청이 각각 잔여수량을 확인한 후 모두 처리되어 배정 수량 초과 발생 가능성
  * 예: 배정 10주, 이미 매도 6주 → 잔여 4주 상태에서 두 건의 3주 매도 요청이 동시에 들어올 경우
- 동시성 제어 방법 후보:
  * 낙관적 락 (Optimistic Locking): 버전 컬럼을 사용하여 충돌 감지
    * Sale 엔티티에 버전 필드 추가 또는 Allocation 엔티티에 버전 필드 추가 후 검증
    * 장점: 성능 좋음, 단점: 충돌 시 재시도 필요
  * 비관적 락 (Pessimistic Locking): SELECT FOR UPDATE를 통한 레코드 잠금
    * 매도 처리 시 해당 Allocation 레코드 잠금 후 검증 및 처리
    * 장점: 확실한 정합성, 단점: 성능 저하 가능성
  * 트랜잭션 격리 수준: 적절한 격리 수준 설정 (SERIALIZABLE 또는 REPEATABLE READ 권장)
    * 데이터베이스 수준에서의 동시성 제어
    * 장점: 구현 간단, 단점: 성능 영향 및 데드락 가능성
  * 애플리케이션 레벨 락: 분산 락 또는 뮤텍스 사용
    * 특정 배정에 대한 락을 애플리케이션 레벨에서 관리
    * 장점: 유연한 제어 가능, 단점: 복잡성 증가 및 단일점 실패 가능성
- 잔여 수량 검증 로직은 서비스 계층에서 트랜잭션 내에서 수행해야 함
  * 트랜잭션 시작 → 현재 잔여수량 조회 → 요청 매도 수량 검증 → 매도 기록 저장 → 트랜잭션 커밋
- **사람 결정 필요**: 구체적인 동시성 제어 방식은 성능 요구사항과 데이터 정합성 중요도에 따라 결정되어야 함

### 4. 매도 기록의 삭제·보존 정책은 무엇인가
**work-plan-ipo-investment.md 23장(삭제 정책)**:
- 금융 기록은 단순한 CRUD처럼 처리하지 않는다.
- 예를 들어 이미 완료된 투자 기록을 사용자가 실수로 삭제하는 경우 데이터 추적성이 사라질 수 있다.
- 따라서 다음을 검토한다:
  * 물리 삭제
  * 논리 삭제
  * 수정 이력
  * 감사 로그
- 초기 구현에서 반드시 필요하지 않은 기능은 후순위로 둘 수 있지만, 설계 시 데이터 추적성 문제를 고려한다.

**확인한 내용**:
- 금융 기록 특성상 삭제 보수적 접근 필요:
  * 물리 삭제: 금융 audit 및 추적성 요구사항으로 일반적으로 권장되지 않음
  * 논리 삭제: 삭제 플래그 추가로 논리적으로만 삭제 처리 (물리적 데이터는 보존)
  * 수정 이력: 변경 전후 값을 추적하여 이력 관리
  * 감사 로그: 누구가 언제 무엇을 했는지 기록하는 별도 로그 테이블
- 매도 기록 삭제 정책 고려 사항:
  * 완전 삭제 금지 원칙: 금융 기록은 추적성이 중요하므로 물리 삭제 금지
  * 오류 수정 프로세스: 삭제 대신 오류 거래를 역거래로 수정하거나 수정 이력 남기기
  * 보존 기간: 법적 요구사항에 따른 최소 보존 기간 고려 (예: 5년)
  * 아카이브 전략: 오래된 기록은 아카이브 테이블로 이동시켜 활성 테이블 크기 관리
- **사람 결정 필요**: 매도 기록의 삭제·보존 정책은 금융 규정 및 법적 요구사항에 따라 결정되어야 함

## 제약사항
1. **금융 규정 준수**: 매도 프로세스는 자본시장법 및 관련 금융 규정을 준수해야 함
2. **work-plan 13장**: Sale은 "배정 결과를 관리"하는 도메인으로, 하나의 배정에 여러 번의 매도가 있을 수 있음
3. **work-plan 22장**: 데이터 무결성을 위해 잘못된 데이터 방지 필수 (매도 수량 > 배정 수량 방지 등)
4. **work-plan 23장**: 금융 기록은 단순한 CRUD처럼 처리하지 말아야 함 (삭제 정책 고려)
5. **work-plan 36장**: 데이터 변경 시 수정 가능한 범위와 변경 추적 필요 고려
6. **work-plan 45장**: 동시성 처리 시 데이터 정합성 보장 필요
7. **금융 데이터 특성상 증거와 추정 금지**: 특히 매도 관련 사항은 사람의 결정 필요
8. **allocation-management 조사 결과**: 선행 Epic의 배정 상태 및 잔여 수량 계산에 의존함

## 개발에 미치는 영향
1. **Sale 엔티티 설계**: 매도 수량, 매도 가격, 매도 금액, 매도 일시, 수수료, 세금, 기타 비용, Allocation 외부 키, 매도 순서 필드(필요시), 상태 필드(필요시), 버전 필드(동시성 제어용), 생성/수정 타임스탬프 포함 계획
2. **순서 관리**: 매도 일시 기준 자동 정렬 또는 명시적 순서 번호 관리 로직 구현 필요
3. **데이터 무결성**: 개별 매도 수량 검증 및 누적 매도 수량 ≤ 배정 수량 검증 로직 구현 필요
4. **변경 추적 기능**: 수정 가능한 필드에 대한 변경 이력 테이블 또는 감사 로그 구현 필요 (work-plan 36장)
5. **동시성 제어 메커니즘**: 트랜잭션 관리 및 락 전략을 서비스 계층에 적용 필요 (work-plan 45장)
6. **삭제 정책**: 논리 삭제 플래그 또는 아카이브 전략 구현 필요 (work-plan 23장)
7. **검증 로직**: 서비스 계층에서 매도 수량 검증 및 잔여 수량 계산 로직 구현 필요
8. **테스트 전략**: 상태 전이 테스트, 중복 방지 테스트, 동시성 테스트, 매도 수량 검증 테스트, 삭제/보존 정책 테스트 등 필요

## 결론
분할 매도 기록 도메인은 배정 결과를 추적하는 핵심 금융 도메인으로, 매도 순서 표현, 데이터 무결성, 동시성 제어, 변경 추적, 삭제·보존 정책이 모두 중요한 요소이다. 조사 결과, 확인해야 할 사항은 많으나 금융 규정과 비즈니스 로직에 따른 사람의 결정이 필요한 사항이 다수 존재한다. 본 조사에서는 후보를 제시하고 불확실한 점을 명시했으며, 후속 기획 단계에서 정확한 정의가 이루어져야 한다. 특히 매도 순서 표현 방법, 매도 기록의 수정 가능 범위, 동시성 제어 방식, 삭제·보존 정책은 금융 데이터의 정확성과 추적성을 위해 사람의 명확한 결정이 선행되어야 구현을 진행할 수 있다. work-plan 13장이 명시한 것처럼 이 서비스는 "한 배정 결과에 여러 번의 매도가 있을 수 있음"을 고려하여 설계되어야 하며, 매도 총수량이 배정 수량을 초과하지 못하도록 하는 불변조건을 유지해야 한다.
