# 공모주 청약 일정 자동 동기화 조사 문서

## 조사 목적
Epic 17 "공모주 청약 일정 자동 동기화" 구현을 위한 사전 조사. 공공 API(금융감독원 OpenDART, 한국거래소 KRX Data Marketplace)로부터 공모주 청약/상장/환불 일정을 주기적으로 수집하여 DB에 저장하고, 사용자가 청약 등록 시 직접 입력하지 않고 목록에서 선택할 수 있도록 하는 기능의 기술적 실현 가능성을 조사한다.

## 조사 대상
- 금융감독원 OpenDART API의 공모게시판·청약 달력 관련 엔드포인트 및 응답 필드
- 한국거래소 KRX Data Marketplace의 신규상장/공모 관련 데이터셋
- API 인증 방식 및 비용(무료/유료)
- 응답 데이터의 신선도 및 갱신 주기
- 기존 IPO 엔티티 필드와 API 응답 필드 매핑 분석
- 배치 동기화 설계 방안
- 구현 시 리스크 및 완화 방안

## 출처
- Master 사전조사 (2026-09-29, WebSearch로 확인) - 제공된 사실 기반
- backend/src/main/java/com/vibeaiteam/ipocatalog/ (Epic 5 - 기존 IPO 기준정보 관리)
- backend/src/main/resources/db/migration/ 중 IPO 관련 테이블 마이그레이션 파일
- docs/research/, docs/spec/, docs/architecture/ 폴더의 기존 Epic 문서 형식(ipo-catalog, dashboard-aggregation-api 등)

## 확인한 내용

### 1. API 후보별 실현 가능성 평가

#### 1-1. 금융감독원 OpenDART (opendart.fss.or.kr)
- **현재 확인된 사실**: 전자공시 API, 6개 API 그룹으로 나뉨. "공시정보" 그룹에 공시검색·기업개황 등이 포함됨.
- **미확인 사항**: "공모게시판" 청약일정 관련 세부 응답 필드(청약기간/환불일/상장예정일 등)의 정확한 API 경로, 요청 파라미터, 응답 스펙.
- **인증키 발급**: opendart.fss.or.kr/uss/umt/EgovMberInsertView.do에서 신청 가능 (무료로 보이나 발급 소요시간 미확인).
- **실현 가능성 평가**: 
  - 장점: 공식 금융감독원 제공 서비스, 무료 이용 가능성 높음
  - 단점: 공모게시판 청약일정 데이터 제공 여부 및 정확한 필드 구성 미확인
  - 결론: 1순위 후보이나 실제 개발가이드 문서 확인이 필요함

#### 1-2. 한국거래소 KRX Data Marketplace (openapi.krx.co.kr)
- **현재 확인된 사실**: 공식 시장 데이터 API 포털 존재 확인.
- **미확인 사항**: 신규상장/공모 전용 데이터셋 유무, 유료/무료 여부, 인증 방식, 데이터 상세 필드.
- **실현 가능성 평가**:
  - 장점: 주식시장 운영기관으로서 IPO 데이터 제공 가능성 높음
  - 단점: 구체적 데이터셋 존재 여부 및 비용 구조 미확인
  - 결론: 2순위 후보로 유지, 실제 데이터 카탈로그 확인이 필요함

#### 1-3. 민간 사이트 (38커뮤니케이션, 콕스톡 등) - 제외 권고
- **확인된 사실**: 공모주 일정을 사람이 보는 페이지로 제공하나 공식 API 계약이 없어 보임.
- **제외 사유**: 이 프로젝트가 이미 범위 밖으로 못박은 "외부 데이터 스크래핑"에 해당하므로 후보에서 제외.
- **참고**: docs/roadmap.md 1절(17행)에 "외부 데이터 스크래핑"이 MVP 범위 밖임이 명시됨.

### 4. 기존 IPO 엔티티 필드와 API 응답 필드 대조

| IPO 엔티티 필드 (Backend) | API로 자동 채움 가능성 | 비고 |
|--------------------------|----------------------|------|
| id (시스템 내부 ID)      | 불가                 | 자동 생성되는 PK |
| companyName (기업명)     | 가능                 | OpenDART의 corp_name 또는 유사 필드 예상 |
| ipoName (공모주명)       | 가능                 | 공모주명의 공식 표현 |
| stockCode (종목코드)     | 가능                 | 6자리 숫자 코드 (안정적 식별자 후보) |
| roundLabel (회차 구별)   | 조건부 가능          | API에서 제공하는 경우에만 |
| lowerBandPrice (희망저가) | 가능                 | 수요예측 결과에서의 밴드 하한 |
| upperBandPrice (희망고가) | 가능                 | 수요예측 결과에서의 밴드 상한 |
| fixedPrice (확정공모가)  | 가능                 | 수요예측 종료 후 확정값 |
| subscriptionStartDate (청약시작일) | 가능          | 핵심 대상 필드 중 하나 |
| subscriptionEndDate (청약종료일) | 가능          | 핵심 대상 필드 중 하나 |
| listingDate (상장일)     | 가능                 | 핵심 대상 필드 중 하나 |
| offeringShareCount (공모주식수) | 가능          | 총 공모 규모 |
| status (상태)            | 부분적 가능          | API에서 제공하는 상태 정보를 기반으로 매핑 필요 |
| deletedAt, createdAt, updatedAt | 불가          | 시스템 내부 관리 필드 |

**갭 분석**: 
- 현재 Master 사전조사로는 OpenDART의 "공모게시판" 청약일정 관련 세부 응답 필드가 정확하게 확인되지 않았음
- 따라서 위 표의 "가능" 표시는 가정이며, 실제 API 문서 확인 후 수정 필요
- 특히 청약일/환불일/상장일 필드의 정확한 매핑이 핵심 미확인 사항

### 5. 배치 동기화 설계 초안

#### 스케줄 주기
- 사용자 제안: 향후 2개월치를 2일마다 업데이트
- 검토 사항: 
  - 실제 IPO 일정 변경 빈도 (보통 사전 공지 후 변경 드묾)
  - API 호출 제한 정책 준수 여부
  - 서버 부하 고려
- 권장 안: 향후 3개월치를 1일 1회 업데이트 (API 정책 및 데이터 변경 특성 고려 시)

#### 중복/변경분 처리 전략
- **식별자 전략**: 
  - 1순위: 외부 API에서 제공하는 고유 종목코드 (예: KRX의 단축코드, DART의 고유번호)
  - 2순위: (companyName, subscriptionStartDate) 복합키 (OpenDART에서 stock_code가 NULL인 경우 적용)
  - 3순위: (ipoName, subscriptionStartDate, listingDate) 삼중키
- **동기화 로직**:
  1. API로부터 향후 3개월치 IPO 일정 데이터 수집
  2. 각 IPO 레코드에 대해 외부 식별자로 기존 레코드 조회
  3. 기존 레코드가 없으면 신규 등록
  4. 기존 레코드가 있으면 변경된 필드만 업데이트 (청약일/상장일 등)
  5. 삭제된 IPO는 논리적 삭제(deleted_at 설정) 처리 (실제 데이터 제거는 보수적으로 접근)
- **충돌 처리**: 
  - 동일 식별자에 서로 다른 데이터가 있는 경우, API 데이터를 우선으로 하되 중요 변경 사항은 알림 로그 기록

#### 실패 시 재시도/알림 방안
- **재시도 정책**: 
  - 1차 실패 후 5분 대기 후 재시도
  - 최대 3회 재시도 시도
  - 지수 백오프 적용 (5분 → 10분 → 20분)
- **알림 방안**:
  - 지속적 실패 시 (3회 재시도 후에도 실패) 관리자 알림 트리거
  - 실패 원인별 분류 (인증 오류, API 오류, 네트워크 오류, 파싱 오류 등)
  - 실패 시에도 기존 데이터는 보존하고, 신규 데이터만 반영하지 않음

## 불확실한 점
1. 금융감독원 OpenDART의 "공모게시판" 청약일정 관련 세부 API 엔드포인트 및 정확한 응답 필드
2. 한국거래소 KRX Data Marketplace의 신규상장/공모 관련 데이터셋 존재 여부 및 상세 스펙
3. 두 API 모두의 인증키 발급 절차 정확한 소요 시간 및 비용 구조
4. 응답 데이터의 신선도 (발표 시점부터 API 반영까지의 시간 지연)
5. API 호출 제한 정책 (rate limit) 및 제한 시 처리 방식
6. 실제 IPO 일정 데이터에서 제공되는 필드의 상세 목록 및 데이터 타입

## 개발에 미치는 영향
1. IPO 엔티티 설계 시 현재 모델의 모든 필드를 유지하되, 자동 동기화 기능을 통해 채울 수 있는 필드와 수동 입력이 필요한 필드를 명확히 구분해야 함
2. 배치 동기화 서비스는 별도 스케줄러 (예: Spring @Scheduled 또는 외부 크론 작업)로 구현하고, 실패 시 재시도 로직 및 알림 기능을 포함해야 함
3. 사용자 경험 측면에서 청약 등록 시 IPO 선택 목록은 자동으로 동기화된 데이터를 기반으로 하되, 수동 입력 옵션도 반드시 제공해야 함
4. 데이터 신뢰성을 위해 자동 동기화 전에 데이터 유효성 검증 로직을 적용하고, 비정상 값은 알림 후 무시하는 전략을 채택해야 함

## 결론
기술적으로 공모주 청약 일정 자동 동기화 기능은 금융감독원 OpenDART을 1순위 후보로 하여 구현 가능성이 높으나, **Master 사전조사만으로는 "청약일/환불일/상장일"을 구조화된 필드로 주는 공식 무료 API가 100% 확정되지 않았다**. 따라서 다음 조사 라운드에서 Master가 직접 OpenDART 개발가이드 페이지 원문을 확인해야 정확한 엔드포인트와 필드를 확인할 수 있다.

**1순위 추천 API**: 금융감독원 OpenDART (공모게시판 청약 달력 관련 엔드포인트)
**추가 조사 필요 사항**: 실제 OpenDART 개발가이드 문서에서 "공모게시판" 관련 API 경로, 요청 파라미터, 응답 필드(특히 종목명/청약일/환불일/상장일/공모가/주간사 등) 확인

문서에서 다루지 못한/추가 조사가 필요한 부분:
1. OpenDART 정확한 API 엔드포인트 및 인증 방식 상세 스펙
2. KRX Data Marketplace의 공모주 관련 데이터셋 존재 여부 및 이용 조건
3. API 응답 데이터의 실제 신선도 및 갱신 주기
4. 인증키 발급 소요 시간 및 주기적 갱신 필요 여부
5. 호출 제한 정책 및 제한 시 대처 방안

## 7. Master 후속 조사 — 2026-09-29, 사용자와 실시간 확인 (최종 결정 반영)

위 6절의 "불확실한 점"을 해소하기 위해 Master가 WebFetch로 실제 API 문서·페이지 원문을 직접 열람하고, 사용자와 실시간으로 후보를 하나씩 검증했다. **이 절이 최종 결론이며, 1~6절의 "미확인" 표시는 아래 내용으로 갱신된 것으로 본다.**

### 7.1 OpenDART — 실제로는 "공모게시판"이 아니라 "증권신고서-지분증권" API

- `opendart.fss.or.kr/intro/infoApiList.do` 확인 결과 **"공모게시판" 전용 API/카테고리는 존재하지 않는다.** 1~6절이 가정한 경로는 틀렸다.
- 실제로는 **API 그룹 `DS006`(증권신고서 주요정보) 하위의 "지분증권" API**(`opendart.fss.or.kr/guide/detail.do?apiGrpCd=DS006&apiId=2020054`)가 공모주 청약 관련 정보를 제공한다.
- **요청 파라미터**: `crtfc_key`(인증키), `corp_code`(회사고유번호, 8자리), `bgn_de`/`end_de`(검색 접수일자 범위, YYYYMMDD). **회사고유번호 기준 조회이므로, "앞으로 청약할 종목 전체 목록"을 얻으려면 먼저 DS001의 "공시검색" API로 최근 기간에 "증권신고서(지분증권)"를 제출한 회사들을 찾아야 하는 2단계 구조다.**
- **확인된 응답 필드** (일반사항 그룹): `sbd`(청약기일), `pymd`(납입기일), `sband`(청약공고일), `asand`(배정공고일), `asstd`(배정기준일). 증권의종류 그룹: `stksen`/`stkcnt`(증권종류/수량), `slprc`(모집(매출)가액 = 공모가), `slta`(모집총액). 인수인정보 그룹: `actnmn`(인수인명 = 주간사).
- **확인된 갭**: 이 API 응답에 **상장예정일(listing date) 필드가 없다.** DS001(공시정보), DS005(주요사항보고서, 36개 API 전수 확인) 어디에도 "신규상장"·"상장예정일" 관련 API/필드가 없었다.
- **결론**: OpenDART DS006은 **청약일·납입일·공모가·주간사를 확보하는 공식·무료 기본 소스로 채택한다.** 상장예정일·환불일·배정일은 DS006으로 채울 수 없다(7.3절로 이어짐).

### 7.3 최종 채택 — `api.ustockplus.com`(네이버 u+stock의 백엔드 API)을 갭 보완용으로 병행

사용자가 브라우저 개발자도구 네트워크 탭에서 실제 요청을 캡처해 제공했고, Master가 동일 요청을 서버에서 재현해 검증했다.

- **엔드포인트**: `GET https://api.ustockplus.com/v2/ipo/calendars?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD`
- **인증**: 불필요(로그인 없이 접근 가능). 단, `Origin: https://ustock.naver.com`, `Referer: https://ustock.naver.com/service/ipo`, **`x-app-device: WEB`** 세 헤더가 모두 없으면(2026-09-30 재확인: 앞의 둘만으로는 부족하고 세 번째가 필수, 조회 기간은 최대 89일) `LOGIN_REQUIRED`(`errorCode: I0003`) 오류를 반환한다(Master가 헤더 없이 직접 호출해 재현 확인). 두 헤더를 브라우저와 동일하게 보내면 `200 OK`로 정상 응답한다(Master가 curl로 재현 확인, 아래 응답 예시는 그 결과).
- **응답 구조**: `ipoCalendarResponses[]` 배열, 각 항목은 `stockCode`, `stockName`, `calendarStockType`, `startDate`, `endDate`, `extraInfo{finalOfferPrice, lockUpPromiseRatio, instCompetitiveness}`.
- **확인된 `calendarStockType` 값**: `EXAMINATION_REQUESTED`(심사청구), `DEMAND_FORECAST`(수요예측), `OFFER_SUBSCRIPTION`(청약), **`TO_BE_LISTED`(상장예정일)**, **`ALLOTMENT_DATE`(배정일)**, **`REFUND_DATE`(환불일)** — OpenDART DS006이 못 주는 필드를 전부 커버한다.
- **응답 헤더로 확인된 제약**: `access-control-allow-origin: https://ustock.naver.com`(CORS가 그 origin으로 고정 — 브라우저에서 다른 사이트가 직접 호출하면 CORS로 막히지만, **서버-to-서버 호출은 CORS의 적용을 받지 않는다**. 단 Origin/Referer 헤더로 "이 요청이 ustock.naver.com에서 왔는지"를 서버가 체크하고 있어, 그 체크를 헤더 값 지정으로 우회하는 셈이다). `x-ratelimit-burst-capacity: 120`, `x-ratelimit-replenish-rate: 15`(초당 15회 리필) — 트래픽 남용 방지 장치가 있다는 신호.
- **리스크 평가**: 로그인이나 토큰 탈취가 필요 없고 헤더 몇 개만 지정하면 되는 **낮은 기술적 난이도**이나, 이는 ustockplus/네이버가 자사 프론트엔드 전용으로 설계한 **비공식·미계약 API**다. 공식 문서·SLA가 없어 예고 없이 차단되거나 스펙이 바뀔 수 있고, 이용약관 밖의 사용이라는 점은 남아 있다.
- **사용자 최종 결정(2026-09-29)**: "OpenDART(DS006)을 기본 베이스로 가고, 없는 데이터만 네이버(ustockplus) 걸로 가자." — 즉 **하이브리드 채택**. OpenDART가 1차 소스(공식·안정적), ustockplus API는 OpenDART가 못 주는 갭(상장예정일·배정일·환불일)만 보완하는 2차 소스로 병행한다. 이 결정으로 사용자가 앞서 제안한 "환불일은 영업일 계산 로직으로 자체 산출" 아이디어는 채택하지 않고, 대신 REFUND_DATE 필드를 그대로 받는 쪽으로 정리됐다(계산 로직보다 실측 데이터가 더 정확하기 때문).
- **후속 설계 시 반드시 반영할 것**:
  1. ustockplus 호출부에 Origin/Referer 헤더를 상수로 고정하고, 요청 실패(스펙 변경·차단) 시 **OpenDART 데이터만으로도 서비스가 정상 동작해야 한다**(상장예정일 등 갭 필드는 null 허용, 사용자 수동 보완 가능하게 UI 설계).
  2. `x-ratelimit-*` 힌트를 지켜 배치 동기화 시 초당 15회를 넘지 않게 스로틀링한다.
  3. 이 소스가 비공식이라는 사실을 코드 주석·설계 문서에 명시하고, 장애·차단 시 즉시 감지할 수 있는 모니터링(응답 실패율 알림)을 둔다.
  4. `stockCode`가 OpenDART의 `corp_code`(회사고유번호)와 체계가 다르다(전자는 종목코드, 후자는 회사고유번호) — 두 소스를 같은 IPO 레코드로 병합하려면 **종목코드 기준 매핑 테이블 또는 회사명 매칭 로직**이 별도로 필요하다. 이것이 spec/architecture 단계의 핵심 설계 과제다.
