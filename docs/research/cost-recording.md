# 비용 기록 (cost-recording) 조사 문서

## 조사 목적
Epic 9 `cost-recording` 구현에 앞서, 매도와 취득 과정에 발생한 수수료·세금·기타 비용을 기록하고 수익 계산이 참조할 수 있는 근거로 남기는 방안을 조사하여 안전한 금융 데이터 관리 기반을 마련한다.

## 조사 대상
- 비용 입력 도메인 구조 및 필수 필드
- 매도별 또는 취득 관련 비용 연결 방식
- 비용 종류·금액·발생일시·통화 기록 방법
- 수수료·세금·기타 비용의 사용자 입력 처리
- 비용 합계 계산 및 중복 방지 메커니즘
- 비용 기록 수정·삭제 정책
- 비용이 없는 경우의 명시적 처리 방식

## 확인한 내용

### 1. 증권사별 청약·매도 수수료 정책과 유효기간은 어떻게 다루는가 (자동 결정 대상 아님, 사용자 입력 근거로만 사용)?
**roadmap.md Epic 9 상세 (진행 전 필요한 조사)**:
- 증권사별 청약·매도 수수료 정책과 유효기간은 어떻게 다루는가 (자동 결정 대상 아님, 사용자 입력 근거로만 사용)?

**work-plan-ipo-investment.md 26장(증권사 수수료)**:
- 증권사별 청약/매도 수수료가 다를 수 있으므로 하드코딩하지 않는다.
- 예를 들어: 증권사 A = 2,000원, 증권사 B = 0원 같은 값이 있더라도 실제 정책을 조사하고 유효기간을 고려해야 한다.
- 계좌 조건, 이벤트, 고객 등급, 수수료 정책 변경, 거래 채널별 차이도 고려한다.
- MVP에서는 사용자가 직접 비용을 기록하는 방식도 검토할 수 있다.

**profit-calculation-fees.md 조사 결과**:
- 2026-09-20 기준, 5대 증권사의 청약 및 매도 수수료 정보를 공식 페이지에서 모두 확인하지 못함.
- 필요한 경우 각 증권사에 직접 문의하여 최신 수수료표를 확보해야 함.

**확인한 내용**:
- 증권사별 수수료 정책은 복잡하며 유효기간이 존재하므로 자동 결정은 적절하지 않음.
- 사용자가 실제 발생한 수수료 금액을 직접 입력하도록 하는 방식을 채택해야 함.
- 수수료 유효기간은 비용 기록 자체에 발생일시를 기록함으로써 간접적으로 반영 가능.
- 계좌 조건, 이벤트, 고객 등급, 거래 채널 차이는 비용 입력 시 사용자가 판단하여 기록하도록 함.

### 2. 세금과 기타 비용의 범위는 어디까지인가?
**roadmap.md Epic 9 상세 (진행 전 필요한 조사)**:
- 세금과 기타 비용의 범위는 어디까지인가?

**work-plan-ipo-investment.md 15장(수익 계산의 기본 개념)**:
- 실제 계산에는 다음 요소가 영향을 줄 수 있다:
  ```
  매도금액
  - 취득 관련 비용
  - 매도 수수료
  - 세금
  - 기타 비용
  = 순수익
  ```

**work-plan-ipo-investment.md 27장(세금)**:
- 세금은 매우 중요한 영역이다.
- 세금 관련 내용은 AI가 기억에 의존하여 구현하지 않는다.
- 반드시 최신 공식 자료를 조사한다.
- 특히 다음을 구분해서 검토한다:
  * 어떤 거래에 어떤 세금이 붙는가?
  * 세율은 얼마인가?
  * 적용 기준은 무엇인가?
  * 거래 시점에 따라 달라지는가?
  * 예외 조건은 무엇인가?
  * 개인 투자자에게 어떤 규칙이 적용되는가?
- 세금 계산 로직이 확정되기 전에는 임의의 숫자를 코드에 넣지 않는다.

**profit-calculation-tax.md 조사 결과**:
- 주식등 양도소득세: 상장주식·비상장주식 등 주식의 **양도**가 과세 기준이 된다.
- 증권거래세: 주식 매도 시 증권거래세라는 별도 세목이 존재.
- 배당소득 관련 원천징수: 배당 지급이 발생한 경우에만 별도 소득 이벤트로 기록.
- 금융투자소득세: 2026년 적용 여부와 2027년 예정 제도는 이번 조사에서 최종 확인하지 못함.

**확인한 내용**:
- 세금 범위: 주식등 양도소득세, 증권거래세, 배당소득 관련 원천징수, 금융투자소득세(향후 검토 필요)
- 기타 비용 범위: transfer fees, clearing fees, 기타 거래 관련 비용
- 사용자 입력을 통해 실제 발생한 세금 및 비용 금액을 기록하도록 함.
- 세금 종류와 적용 근거를 함께 기록하여 향후 세법 변경 시 추적 가능하도록 함.

### 3. 계좌 조건·이벤트·고객 등급·거래 채널 차이가 비용에 미치는 영향을 어떻게 기록 구조에 반영하는가?
**roadmap.md Epic 9 상세 (진행 전 필요한 조사)**:
- 계좌 조건·이벤트·고객 등급·거래 채널 차이가 비용에 미치는 영향을 어떻게 기록 구조에 반영하는가?

**work-plan-ipo-investment.md 26장(증권사 수수료)**:
- 계좌 조건, 이벤트, 고객 등급, 수수료 정책 변경, 거래 채널별 차이도 고려한다.

**확인한 내용**:
- 계좌 조건 (예: 우대 계좌, VIP 등급): 비용 입력 시 사용자가 해당 조건을 고려하여 금액을 결정하도록 함.
- 이벤트 (예: 수수료 면제 이벤트): 비용 입력 시 사용자가 0원을 입력하거나 면제 사유를 메모로 남김.
- 고객 등급 (예: 일반, VIP, 프로): 비용 입력 시 사용자가 해당 등급에 적용된 수수료를 입력하도록 함.
- 거래 채널 (예: 온라인, 오프라인, 모바일 앱): 비용 입력 시 사용자가 해당 채널의 실제 비용을 입력하도록 함.
- 기록 구조에는 조건/채널/등급을 별도 필드로 두기보다, 사용자가 판단하여 최종 비용 금액을 입력하도록 함.
- 단, 참고용으로 조건/채널/등급 정보를 메모 필드에 기록할 수 있도록 옵션 제공 고려.

**work-plan-ipo-investment.md 26장(증권사 수수료)**:

**work-plan-ipo-investment.md 15장(수익 계산의 기본 개념)**:

**profit-calculation-fees.md 및 profit-calculation-tax.md 조사 결과**:
- 구체적인 수수료·세율 값을 확인할 수 없음.
- 각 증권사별, 세목별 정책이 복잡하고 자주 변경됨.

**확인한 내용**:

  * 이유 2: 사용자가 실제 발생한 비용을 가장 정확히 알 수 있음.
  * 이유 3: 정책 데이터 접근 및 유지가 복잡하여 초기 개발 단계에서는 부적합.
  * 이유 4: 사용자 입력을 통해 비용 발생 근거를 명확히 남길 수 있음.
- 향후 정책 데이터 기반 자동 결정으로 확장 가능성을 고려하여 입력 구조 설계 시 확장 여지 남김.
- 단, 사용자 입력이라도 세금 종류, 수수료 종류 등을 선택할 수 있도록 옵션 제공을 고려하여 데이터 정합성 유지.

## 제약사항
1. **금융 규정 준수**: 비용 기록은 자본시장법 및 관련 금융 규정을 준수해야 함 (작업 계획서 23장 삭제 정책 참조).
2. **roadmap Epic 9 상세**: 비용을 별도 도메인으로 분리해야 입력 근거와 책임 범위가 명확해진다.
3. **work-plan 13장(Sale 도메인)**: 매도 정보에는 수수료, 세금, 기타 비용 항목을 검토한다.
4. **work-plan 15장(수익 계산의 기본 개념)**: 취득 관련 비용, 매도 수수료, 세금, 기타 비용을 매도금액에서 차감하여 순수익을 계산한다.
5. **work-plan 23장(삭제 정책)**: 금융 기록은 단순한 CRUD처럼 처리하지 않아야 함.
6. **work-plan 22장(데이터 무결성)**: 잘못된 데이터 방지 필수 (음수 비용 방지 등).
7. **work-plan 27장(세금)**: 세금 관련 내용은 AI가 기억에 의존하여 구현하지 말고 반드시 최신 공식 자료를 조사해야 함.
8. **work-plan 26장(증권사 수수료)**: 증권사별 청약/매도 수수료가 다를 수 있으므로 하드코딩하지 않는다.
9. **금융 데이터 특성상 증거와 추정 금지**: 특히 비용 관련 사항은 사람의 결정 필요 (작업 계획서 38장 AI Agent가 하지 말아야 할 판단 참조).
10. **sale-management 조사 결과**: 선행 Epic의 매도 기록과 연결되어야 함.

## 개발에 미치는 영향
1. **비용 엔티티 설계**: 비용 종류, 금액, 발생일시, 통화, 매도 외부 키, 취득 관련 외부 키(선택적), 메모 필드, 생성/수정 타임스탬프 포함 계획.
2. **매도와의 연결**: 매도 1:N 비용 관계 또는 취득 1:N 비용 관계 고려 (작업 계획서 13장 매도 정보에 수수료/세금/기타 비용 직접 포함 방식과 비교).
3. **데이터 무결성**: 비용 금액 ≥ 0 검증 로직 구현 필요.
4. **사용자 입력 검증**: 비용 입력 시 필수 항목 확인 및 금액 유효성 검증 로직 구현 필요.
5. **비용 합계 계산**: 매도별 또는 취득 관련 비용 합계 계산 로직 구현 필요 (작업 계획서 15장 수익 계산 참조).
6. **수정 및 삭제 정책**: 금융 기록 특성 고려한 수정 가능 범위 및 삭제 정책 구현 필요 (작업 계획서 23장 참조).
7. **테스트 전략**: 비용 입력 테스트, 합계 계산 테스트, 수정 테스트, 삭제 테스트, 데이터 무결성 테스트 등 필요.
8. **수익 계산 연동**: 비용 합계가 수익 계산에 올바르게 반영되는지 인터페이스 테스트 필요.

## 결론
비용 기록 도메인은 매도와 취득 과정에 발생한 수수료·세금·기타 비용을 사용자 입력을 통해 기록하고 수익 계산이 참조할 수 있는 근거로 남기는 핵심 금융 도메인으로, 사용자 입력 중심 접근이 MVP 관점에서 적절하다. 조사 결과, 증권사별 수수료 정책과 세금 체계가 복잡하고 자주 변경되어 자동 결정이 어렵며, 사용자가 실제 발생한 비용을 가장 정확히 알 수 있다는 사실을 확인하였다. 따라서 비용 기록은 사용자 입력을 기본으로 하되, 비용 종류, 발생일시, 매도/취득 연결 정보 등을 함께 저장하여 데이터의 정확성과 추적성을 보장해야 한다. 향후 정책 데이터 기반 자동 결정으로의 확장 가능성을 고려하여 설계 시 확장 여지를 남겨야 하며, 금융 기록으로서의 특성상 삭제보다는 논리 삭제 또는 수정 이력 관리 방식을 채택해야 한다. 구체적인 비용 금액이나 세율은 확정하지 않으며, 사용자 입력 값을 그대로 기록하는 방식을 채택한다.
