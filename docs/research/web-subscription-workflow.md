# 웹 구독 워크플로우 조사 문서

## 조사 목적
Epic 14 `web-subscription-workflow` 구현에 앞서, 청약/배정 등록 화면의 입력 필드 및 오류 표현 방식, 상태 화면 표현, 입력 규칙, 접근성 및 반응형 기준, 그리고 청약→배정으로 이어지는 주요 흐름의 E2E 테스트 범위를 조사하여 사용자 친화적이고 안전한 웹 인터페이스 기반을 마련한다.

## 확인한 내용

### 1. 입력 필드와 오류 표현은 어떻게 해야 하는가 (청약/배정 등록 화면)?
**중요(범위 정정): 이 서비스는 실시간 청약·주문·결제를 대행하지 않는다.** work-plan-ipo-investment.md와 로드맵 Epic 14 제외 범위("자동 청약·주문, 증권사 API 연동, 배정 예측")에 따르면, 사용자는 실제 증권사에서 이미 완료한 청약·배정 결과를 **사후에 직접 입력해 기록**하는 것이다. 따라서 청약 등록 화면은 투자자 선택, 증권계좌 선택, 공모주 선택, 청약 수량/증거금 등 "실제로 발생한 값"을 입력하는 기록 화면이며, 배정 등록 화면도 증권사가 통지한 배정 결과(배정 수량 등)를 사용자가 직접 입력하는 화면이다(시스템이 자동 계산·처리하지 않음). 오류 표현은 필드별 인라인 검증과 함께 제출 시 통합 오류 메시지를 보여야 하며, 중복 기록 시도, 배정 수량이 청약 수량을 초과하는 등의 데이터 무결성 오류는 사용자가 이해할 수 있는 한국어 메시지로 표현해야 한다.

### 2. 청약·배정 상태의 화면 표현은 어떻게 해야 하는가?
청약 기록 상태는 시각적으로 구분하여 표시해야 한다 (청약 기록됨, 배정 대기 - 아직 배정 결과 미입력, 배정 완료 - 배정 결과 입력됨). 배정 결과 화면은 배정 수량과 잔여 수량(배정수량-매도수량, sale-management 참고)을 함께 보여줘야 한다. 상태 전이는 사용자가 "배정 결과 입력" 버튼을 눌러 직접 트리거하는 것이며(시스템이 자동으로 상태를 바꾸지 않음), 이미 입력된 기록을 수정할 때는 확인 다이얼로그를 통해 의도치 않은 변경을 방지해야 한다.

### 3. 날짜·수량·금액 입력 규칙은 무엇인가?
날짜는 반드시 미래 날짜 선택 방지 및 표준 형식(YYYY-MM-DD)으로 표현해야 한다. 수량 입력은 정수만 허용하며 최소값 1 이상, 해당 공모주의 최소 청약 단위 배수를 적용해야 한다. 금액 입력은 원 단위 정수로 처리하되 천단위 콤마 표시와 함께 입력 시 자동 포맷팅을 적용해야 한다. 증거금 및 환불 금액은 음수 값을 허용하지 않으며, 계산 결과가 0인 경우도 적절히 처리해야 한다. 모든 입력 필드는 최대 길이 및 형식 검증을 통해 비정상적인 데이터 입력을 사전에 방지해야 한다.

### 4. 접근성과 반응형 기준은 무엇을 따라야 하는가?
접근성은 WCAG 2.1 AA 수준을 기본으로 따르며, 특히 색상 대비 비율 4.5:1 이상, 스크린 리더를 위한 적절한 라벨링 및 aria-label 사용, 키보드 내비게이션 완전 지원, 포커스 표시 명확성을 준수해야 한다. 반응형 설계는 모바일 첫 접근 방식을 기본으로 하며, 필수 입력 필드는 화면 너비에 따라 우선순위를 조정하고 복잡한 테이블은 가로 스크롤 또는 카드 형태로 변환해야 한다. 금융 거래 특성상 중요한 확인 단계는 모바일에서도 전체 화면 다이얼로그로 제공하여 오입력을 최소화해야 한다.

### 5. 청약→배정으로 이어지는 주요 흐름의 E2E 테스트 범위는 어디까지인가?
E2E 테스트 범위는 사용자 로그인부터 청약 기록 입력까지의 전체 흐름을 포함해야 한다: 공모주 선택 → 투자자·증권계좌 선택 → 청약 수량·증거금 등 실제 값 입력 → 기록 저장 확인. 배정 기록 흐름은 별도로 테스트하며, 기존 청약 기록 조회 → 배정 결과(배정 수량 등) 입력 → 저장 확인을 포함해야 한다. 중복 기록 방지, 배정 수량이 청약 수량을 초과하는 입력값 검증, 기록 수정/취소 흐름도 반드시 테스트 범위에 포함해야 한다. 테스트 데이터는 테스트 전용 공모주 및 계좌를 사용한다.

## 결론
웹 IPO·청약·배정 입력 화면은 실시간 거래를 처리하는 것이 아니라 사용자가 실제 증권사에서 이미 완료한 청약·배정 결과를 사후에 정확히 기록하는 화면이므로, 입력 검증과 데이터 무결성(배정 수량이 청약 수량을 초과하지 않는지 등)에 세심한 주의를 기울여야 한다. 청약 기록부터 배정 기록까지의 흐름을 직관적으로 안내하되, 금융 기록의 정확성을 위한 확인 단계를 포함해야 한다. 접근성과 반응형 기본 표준을 준수하되, 오입력으로 인한 데이터 불일치를 방지하는 데 초점을 맞춘 설계를 해야 한다.
