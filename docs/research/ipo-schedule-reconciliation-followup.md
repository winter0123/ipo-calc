# 연구: 공모주 일정 정정·철회 후속 (2026-11-10 기준)

> 읽기 전용 조사. 코드·운영 데이터 수정 금지. 공식 OpenDART API 직접 조회 결과(Master 확인) 기준.

## 1. 운영 공개 API 집계 (2026-11-10)

공개 GET(`/api/ipos`) 응답을 프로그램으로 집계한 결과 37건이다.

- 상장일 < 오늘(2026-11-10): 11건
- 상장일 == 오늘: 1건 (동원파츠, id=29)
- 상장일 > 오늘: 6건
- 상장일 null: 19건

원 API는 `syncSource`/`deletedAt`/`withdrawnReceiptNo`를 반환하지 않으므로 해당 값은 미확인으로 기록한다(추측 금지). 실DB 접속이 없으므로 "운영DB 일치"라고 쓰지 않고, 공개 API 일정 기준으로만 말한다. 나머지 36건은 공식 일정 대조를 실시하지 않았으므로 추가 보정 근거가 없다.

## 2. SimwonAmericaCorp. (id=20) 공식 공시 확인

- corpCode: 02038432
- 원공시: rcept_no=20261012000149, report_nm=증권신고서(지분증권), rm=철
- 철회신고서: rcept_no=20261030000200, report_nm=철회신고서, rm=빈값
- DS006(회사/기간조회) 응답 일반사항: 원공시 1건만. sbd=2026년11월05일, pymd=2026년11월09일

## 3. DS001/DS006 동작 사실

- DS001은 지분증권 필터(`isEquitySecuritiesReport()`: report_nm 정규화 후 "증권신고서(지분증권)" 포함)가 선행한다. 철회신고서는 이름이 달라 제외되고, 원공시(rm=철)는 보존된다.
- DS006은 rcept_no 지정 조회가 아니라 회사/기간 조건 조회다. Simwon 실응답은 원공시 1건뿐이었다.
- "DS006에 원공시·철회신고서가 섞여 있어 원공시를 선택해야 한다"는 상황은 Simwon 실응답의 원인이 아니다. 원공시 receipt 일치 선택분기는 방어 보완일 뿐이다.

## 4. 확정 원인

기존 배포 코드가 원공시의 rm=철을 처리하지 않아 철회로 인식하지 못하고 계속 upsert한 것이 원인이다.

## 5. 제약·미해결

- 운영 쓰기·배포 승인은 아직 받지 않았다. 근거 확인과 문서 정정은 승인 대기 사안이 아니다.
- syncSource/deletedAt/withdrawnReceiptNo는 배포 후 동기화·배치 실행 결과로만 확인 가능하다.
- 나머지 36건 대조 필요 여부는 미결.
