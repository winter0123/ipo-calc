# 계좌 관리 메뉴·폼 편집 흐름 (account-manage-edit-flow) 조사 문서

## 조사 목적
증권사당 계좌관리 1개 계약과 "메뉴·폼 동시 노출" 버그를 하나의 명확한 상태로 정리하기 위한 현황 조사. 2026-11-11 기준 코드 대조 결과.

## 기존 구현 현황
- **UI 상태**: `SecuritiesManage`가 `panel(create|edit|null)` + `expandedKey(문자열|null)` 두 state를 독립으로 관리 → 폼과 메뉴가 동시에 보일 수 있음.
- **메뉴**: `AccountActionGroup`이 계좌별 수정·삭제 + 회사 계좌추가 1개. 번호 미입력 계좌도 수정·삭제 버튼 노출.
- **채움 동작**: "계좌추가"는 항상 새 계좌 생성 폼 → 미입력 활성 계좌가 있어도 새 미입력 계좌가 또 생길 수 있음.
- **수정 폼**: 기존 번호가 있으면 입력칸 없이 마스킹 안내만. 번호 교체 불가. 삭제 버튼 없음(삭제는 메뉴).
- **서버**: `PATCH /securities-accounts/{id}` — `accountNumber` 미전달=무변경, 공백=400, 기존 암호문 존재=409("이미 계좌번호가 등록되어 있습니다"), `null` 지우기 미지원.
- **동시성**: 투자자 행 `PESSIMISTIC_WRITE` 락 + refresh로 stale read 방지. `deactivate`는 청약 이력(취소 포함) 있으면 409.
- **브로커**: `BrokerSyncService.preview/confirm`, `ApiCredentialService.register/replace`, `ApiCredentialAssembler.toResponse` 모두 자격증명 테이블이 아니라 `SecuritiesAccount.accountNumber`를 매번복호화해 읽음. 토큰 서비스는 토큰만 캐시, 계좌번호 캐시 없음 → 번호 변경 직후에도 다음 호출에 새 번호 사용(오래된 번호 캐시 위험 없음).

## 핵심 결론
1. 메뉴/폼은 `View = idle|menu|create|edit` 단일 state로 상호배타. 계좌관리 토글은 메뉴만 토글(폼이 열려 있으면 폼을 닫고 메뉴로 전환).
2. 미입력(번호 없는) 활성 계좌가 있으면 계좌추가 → 그 계좌(가장 오래된 createdAt, id 명시)를 채우는 edit(채우기) 폼. 없으면 새 계좌 생성 폼.
3. 미입력 상태 메뉴에는 계좌추가만. 번호 있는 계좌별로 수정 + 회사 계좌추가 1개. 삭제는 메뉴에서 제거하고 수정 폼으로 이동.
4. 수정 폼: 기존 번호는 빈 입력칸 + 마스킹 안내(기본값·서버값으로 마스킹 사용 금지). 빈칸 저장=번호 무변경, 10~16자리=정규화/암호화 교체(id·청약/매도 이력·연결 유지).
5. 번호 교체/최초 입력 저장 시 ConfirmDialog "계좌번호가 바뀌어도 기존 청약·매도 이력은 같은 계좌에 남는다" 확인 전 PATCH 0회, 취소 시 입력 유지, 확인 후 1회. 첫 번호 입력에도 동일 적용.
6. 서버 409 최초 1회 제한 제거(사용자 명시 승인). 번호 지우기(null)는 미지원 유지(공백=400).
7. 미입력 채우기 폼도 기존 id 편집이므로 저장/취소/삭제 동일 제공. 삭제는 ConfirmDialog + 409 청약 참조 보호 재사용.

## 제약사항
- DB 스키마·Flyway·의존성 변경 금지. 마스터 문서(current-status 등) 편집 금지.
- 평문 계좌번호는 화면 컴포넌트 상태·입력값으로만 다룬다. 로그·예외·리포트에 평문 금지.
- 기존 409 삭제(청약 이력) 보호는 유지. 제거 대상은 "기존 번호가 있을 때 교체" 409뿐.
