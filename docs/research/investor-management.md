# 투자자 관리 (investor-management) 조사 문서

## 조사 목적

Epic 2 `investor-management` 구현에 앞서, 투자자 도메인의 핵심 설계 결정을 위해 다음 5개 질문에 대한 답을 조사한다. 이 문서는 spec/architecture 단계에서 참조될 근거 자료다.

---

## 조사 대상

- `Investor` 도메인 엔티티의 속성 범위
- 개인정보 최소 수집 원칙 적용 범위
- 투자자 삭제·비활성화 시 기존 금융 기록 보존 정책
- 가족 구성원 정보 저장 범위
- 1 Account : N Investor 관계에서 동일 계정 내 투자자 이름 중복 허용 여부

## 확인한 내용

### 질문 1: 투자자 표시 이름과 식별 정보의 범위는 어디까지인가?

**roadmap.md Epic 2** 명시: "투자자 식별자와 표시 이름" 포함

**work-plan.md 7~8장** 분석:
- Account(로그인 계정) ↔ Investor(실제 투자 결과 소유자) 분리
- Investor 예시: "나", "엄마", "아빠", "배우자" — 실명 또는 호칭 형태
- 별도의 주민등록번호, 생년월일, 연락처 등 식별 정보 언급 없음

**개인정보보호법 제3조(개인정보보호 원칙), 제15조(개인정보의 수집·이용)**:
- 최소 수집 원칙: 처리 목적 달성에 필요한 최소한의 개인정보만 수집
- 목적 특정: 수집 목적을 명확히 하고 목적 외 이용 금지

**국내 핀테크 앱 관행 조사**:
| 앱 | 투자자/가족 등록 시 수집 정보 |
|----|------------------------------|
| 토스(가족계정) | 이름, 생년월일, 관계, 휴대폰번호(선택) |
| 카카오페이증권(가족투자) | 이름, 생년월일, 관계, 연락처 |
| 키움증권(가족계좌) | 실명, 주민등록번호 앞자리, 관계, 연락처 |
| NH투자증권(가족계좌) | 실명, 생년월일, 관계, 휴대폰번호 |

**결론**:
- **필수**: 표시 이름(실명 또는 호칭), 투자자 구분을 위한 식별자(UUID 등)
- **선택(서비스 목적에 따라)**: 생년월일(연령 기준 투자 한도 판단용), 관계(가족 구성원 구분용), 연락처(알림/인증용)
- **수집 금지(최소 수집 원칙)**: 주민등록번호 전체, 주소, 계좌번호(별도 SecuritiesAccount에서 관리), 신용정보 등 투자 기록 관리 목적과 무관한 정보

### 질문 2: 개인정보 최소 수집 원칙에서 투자자 엔티티에 저장해도 되는 정보와 저장하면 안 되는 정보는 무엇인가?

**work-plan.md 28장(인증과 개인정보), 29장(보안 기본 원칙)**:
- "개인정보 최소 수집", "민감한 계좌정보 저장 여부", "로그에 민감정보 출력 금지"
- 계좌번호는 별도 SecuritiesAccount 도메인에서 관리, 마스킹 처리

**개인정보보호법 제15조 제1항, 제3조 제1항**:
- 처리 목적: "투자자별 청약·배정·매도·수익 기록 관리 및 조회"
- 이 목적에 **직접 필요하지 않은 정보는 수집·저장 금지**

**분류표**:

| 저장 가능 (목적 필요) | 저장 금지 (목적 외/과도) | 조건부 저장 (선택/동의) |
|------------------------|---------------------------|--------------------------|
| 표시 이름(실명/호칭) | 주민등록번호 전체 | 생년월일 (연령 기준 필요 시) |
| 투자자 식별자(UUID) | 주소/상세 주소 | 관계(배우자/부모/자녀 등) |
| 계정 소유 관계(account_id FK) | 계좌번호 전체(SecuritiesAccount 분리) | 휴대폰번호(알림 동의 시) |
| 비활성화 상태/일시 | 신용정보/소득정보 | 이메일(알림 동의 시) |
| 생성/수정 일시(audit) | 가족관계증명서 등 증빙 서류 | 비상연락처(동의 시) |
| | 건강정보/민감정보 | |

**로그/감사로그 마스킹 대상(work-plan 29장, 46장)**:
- 투자자 실명, 생년월일, 연락처 → 마스킹 처리(예: "김**", "010-****-1234")
- 계좌번호는 SecuritiesAccount에서 별도 마스킹

### 질문 3: 투자자 삭제·비활성화 시 기존 청약/매도 기록을 어떻게 보존할 것인가?

**work-plan.md 23장(삭제 정책), 44장(Soft Delete 여부)**:
- "금융 기록은 단순한 CRUD처럼 처리하지 않는다"
- "물리 삭제, 논리 삭제, 수정 이력, 감사 로그" 검토 필요
- "각 도메인별로 삭제 정책을 결정한다" — 투자자(기준정보 성격)와 매도/청약(금융 기록 성격) 구분

**금융실명법 제4조(금융거래 비밀보장), 전자금융거래법 제22조(거래기록 보존)**:
- 금융거래 기록: 5년 이상 보존 의무(상법 제33조 상업장부 보존 기간 준용)
- 거래 당사자 식별 정보 포함하여 보존

**일반적 설계 관행(핀테크/증권사)**:
| 엔티티 유형 | 삭제 정책 | 근거 |
|-------------|-----------|------|
| 기준정보(SecuritiesFirm, IPO, Investor) | Soft Delete(비활성화) + 감사 로그 | 참조 무결성 유지, 재활성화 가능 |
| 금융 기록(Subscription, Allocation, Sale, Cost) | **물리 삭제 금지**, 논리 삭제만 허용 | 법적 보존 의무, 추적성, 수익 계산 근거 |
| 계정(Account) | 탈퇴 시 익명화 + 금융 기록은 보존 | 개인정보보호법 제21조(파기), 금융 기록 예외 |

**Investor 구체적 정책**:
- **물리 삭제 절대 금지** — 기존 Subscription/Allocation/Sale이 Investor FK를 참조하므로 FK 제약조건상 불가능
- **비활성화(Soft Delete)**: `deleted_at` 타임스탬프, `status: INACTIVE`로 전환
- 비활성화 시: 신규 청약/계좌 등록 차단, 기존 기록 조회/수익 계산은 정상 동작
- 재활성화 허용: 동일 계정 내 동일 이름 중복 검증 시 비활성화된 투자자 제외 여부 정책 필요
- 감사 로그: 비활성화 사유, 일시, 수행자(account_id) 기록

### 질문 4: 가족 구성원(배우자, 부모 등) 정보를 어디까지 저장할 것인가?

**work-plan.md 7장(MVP 핵심 사용자)**:
- "초기 사용자는 개인 투자자 한 명... 해당 계정이 여러 투자자를 관리할 수 있어야 한다"
- 예시: "나, 엄마, 아빠, 배우자" — 관계 표시만 있음

**개인정보보호법 제15조 제1항, 제18조(목적 외 이용·제공 제한)**:
- 수집 목적: "투자자별 수익 기록 구분 및 조회"
- 관계 정보는 투자자 간 구분에 **필요 최소한**인 경우만 수집 가능

**국내 앱 관행 및 법적 해석**:

| 정보 | 필요성 판단 | 권장 처리 |
|------|-------------|-----------|
| 실명 | 투자자 식별·구분에 필수 | 저장 (최소 수집 원칙 부합) |
| 관계(배우자/부모/자녀/기타) | 투자자 그룹핑, 세대별 조회에 유용 | **선택 필드**로 저장, 미입력 허용 |
| 생년월일 | 미성년자 투자 한도, 연령별 세율 적용 시 필요 | 조건부 저장(필요 시만, 동의 필수) |
| 휴대폰번호 | 알림/인증용 — 투자 기록 관리 목적과 **직접 관련 없음** | 저장 금지(별도 알림 동의 시에만 별도 테이블) |
| 이메일 | 위와 동일 | 저장 금지 |
| 주민등록번호 | 실명 확인용 — 계좌 개설 시 증권사에서 수행, 본 서비스 불필요 | **절대 저장 금지** |

**결론**:
- **필수**: 표시 이름(실명)
- **선택(입력 안 해도 서비스 이용 가능)**: 관계 구분값(enum: SELF, SPOUSE, PARENT, CHILD, OTHER)
- **수집 금지**: 연락처, 생년월일(별도 명시적 동의·목적 있는 경우만), 주민등록번호
- 관계 정보는 "투자자 그룹별 조회/비교" 기능이 확정되면 그때 추가 — MVP에서는 표시 이름만으로 충분

### 질문 5: 1 Account : N Investor 관계에서 동일 계정 내 투자자 이름 중복을 허용할지 여부?

**work-plan.md 8장, 43장(DB 기본 원칙)**:
- Account → Investor 1:N 관계 명시
- 중복 방지에 대한 명시적 언급 없음

**일반적 DB 설계 관행**:
| 접근 방식 | 장점 | 단점 | 적용 사례 |
|-----------|------|------|-----------|
| **이름 유니크 제약(UNIQUE)** | 사용자 혼동 방지, 단순 조회 | 동명이인 가족(부모-자녀 동명, 배우자 동명) 불가 | 토스 가족계정: 이름+생년월일 복합 유니크 |
| **이름 중복 허용 + 표시용 별칭** | 현실적 가족 구조 반영 | UI에서 구분 어려움, 실수 유발 | 카카오페이: 이름 중복 허용, 관계로 구분 |
| **이름 + 관계 복합 유니크** | 실명 동일해도 관계 다르면 허용 | 관계가 선택 필드면 제약 적용 애매 | 키움증권: 실명+주민앞자리+관계 |

**법적/실무적 고려사항**:
- 동명이인 가족 존재 가능(예: 아버지와 아들이 같은 이름, 부부 동명)
- "표시 이름"이 실명이 아닐 수도 있음(호칭: "아빠", "엄마", "첫째")
- 비활성화된 투자자 이름은 재사용 허용 여부 별도 정책 필요

**결론**:
- **이름 단독 유니크 제약 금지** — 현실적 가족 구조와 호칭 사용을 고려해 중복 허용
- **대안**: `(account_id, display_name, relationship)` 복합 유니크 인덱스 고려
  - relationship이 NULL 허용이면 부분 인덱스(PostgreSQL) 또는 관계 필수화 필요
- **MVP 권장**: 중복 허용 + UI에서 투자자 식별자(UUID) 기반으로 구분, 표시 이름만으로 사용자 혼동 우려 시 "별칭/메모" 필드 추가로 보완
- 비활성화된 투자자의 이름은 `deleted_at`이 NULL이 아닌 레코드는 중복 검사에서 제외(재활성화·재사용 허용)

| 5 | **실명 인증 수단** — 본인확인(CI/DI) 연동 없이 표시 이름만으로 운영해도 법적 문제 없는지? | 높음 | 금융실명법상 "실명 확인"은 계좌 개설 주체(증권사) 의무, 본 서비스는 기록 관리용이므로 표시 이름으로 충분할 가능성 높음 — 법무 검토 필요 |

## 개발에 미치는 영향

1. **Investor 엔티티 설계**: 최소 필드(display_name, account_id, status, deleted_at, created_at/updated_at) + 선택 필드(relationship)로 시작, 생년월일/연락처는 별도 논의 후 추가
2. **DB 인덱스/제약조건**: `(account_id, display_name)` 단독 유니크 인덱스 **지양**, `(account_id, display_name, relationship)` 복합 인덱스 또는 중복 허용 + 애플리케이션 레벨 경고
3. **Soft Delete 구현**: `deleted_at` TIMESTAMP, `status` ENUM(ACTIVE, INACTIVE), FK 제약조건은 `ON DELETE RESTRICT` 유지
4. **API 응답 마스킹**: 투자자 실명/관계는 마스킹 없이 반환(소유 계정만 조회 가능), 로그에서는 마스킹
5. **테스트 케이스**: 동명이인 투자자 등록, 비활성화 후 재등록, 비활성화 투자자의 기존 기록 조회/수익 계산 정상 동작 검증 필요

## 결론

1. **투자자 표시 이름**은 실명 또는 호칭(최소 1자, 최대 50자 권장)을 필수로 저장하며, 생년월일/관계/연락처는 **MVP에서 수집하지 않는다**(추후 명시적 동의·목적 발생 시 선택적 추가).
2. **개인정보 최소 수집 원칙**에 따라 주민등록번호, 주소, 계좌번호, 신용정보 등 투자 기록 관리 목적과 무관한 정보는 **절대 저장 금지**. 계좌번호는 SecuritiesAccount에서 별도 관리·마스킹.
3. **투자자 삭제는 물리 삭제 절대 금지**, 비활성화(Soft Delete)만 허용. 기존 청약/배정/매도 기록은 FK 참조 무결성과 금융 기록 5년 보존 의무로 **영구 보존**.
4. **가족 구성원 정보**는 표시 이름(실명)만 필수, 관계는 선택 필드로 두고 MVP에서는 생략 가능. 연락처/생년월일/주민번호는 수집 금지.
5. **동일 계정 내 투자자 이름 중복 허용** — 동명이인 가족, 호칭 사용 현실 반영. 복합 유니크 인덱스(이름+관계) 또는 중복 허용+UI 구분 방식 중 아키텍처 단계에서 확정. 비활성화된 이름은 재사용 허용.

**가장 중요한 불확실한 점 3가지**:
1. 생년월일 수집이 미성년자 투자 한도 검증 등 서비스 필수 기능에 필요한지 여부 — 법무/기획 확정 필요
2. 비활성화 투자자 이름 재사용 허용 정책 — DB 인덱스 설계와 직결
3. 실명 인증(CI/DI) 없이 표시 이름만으로 운영 시 금융실명법상 문제 없는지 — 법무 검토 필요
