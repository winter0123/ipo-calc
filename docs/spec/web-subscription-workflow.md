## 1. 청약 등록 화면

### 화면 목적
사용자가 투자자, 증권계좌, 공모주를 선택하고 청약 수량·증거금·청약일시를 입력하여 청약을 등록한다. 청약 등록은 별도 화면으로 운영된다(D-W14-001).

### 사용하는 API
- `GET /investors` (D-W14-003) — 투자자 드롭다운용 목록 조회
- `GET /securities-accounts` (D-W14-003) — 증권계좌 드롭다운용 목록 조회
- `GET /ipos` (D-W14-003) — 공모주 드롭다운용 목록 조회
- `POST /subscriptions` (D-W14-003) — 청약 등록
  - 요청: `{ investorId, securitiesAccountId, ipoId, quantity, depositAmount, subscribedAt, memo? }`
  - 응답 201: 청약 등록 성공
  - 응답 400: 유효성 오류
  - 응답 404: 투자자/증권계좌/공모주를 찾을 수 없음
  - 응답 409: 중복 청약

### 폼 필드

| 필드명 | 타입 | 필수 | 프론트엔드 유효성 검사 규칙 |
|--------|------|------|-----------------------------|
| investorId | select | 예 | 투자자 드롭다운에서 선택 — 필수 |
| securitiesAccountId | select | 예 | 증권계좌 드롭다운에서 선택 — 필수 |
| ipoId | select | 예 | 공모주 드롭다운에서 선택 — 필수 |
| quantity | number | 예 | 0 초과 정수만 검증 (D-W14-002). 최소 청약 단위 등 증권사별 규칙은 강제하지 않음 |
| depositAmount | number | 예 | 0 이상 정수만 검증 (subscription-management spec 기준 — 증거금 0원도 유효, D-W14-002) |
| subscribedAt | datetime-local | 예 | 청약일시 선택 — 필수 |
| memo | textarea | 아니오 | 선택 사항, 입력 시 빈 문자열 허용 |

### 화면 상태

| 상태 | 설명 | UI 동작 |
|------|------|---------|
| 초기 (idle) | 폼이 비어 있고 입력을 대기하는 상태 | 모든 필드 빈 값, 드롭다운 로딩 중, 에러 메시지 숨김 |
| 로딩 (loading) | 드롭다운 조회 또는 API 호출 중 | 제출 버튼 비활성화, 스피너 표시 |
| 성공 (success) | 201 응답 수신 | 성공 메시지 표시, 청약 목록 화면으로 이동 |
| 에러 (error) | 400/404/409 응답 또는 네트워크 오류 | 필드 아래 인라인 에러 메시지 표시 |

### 에러 처리

| 에러 유형 | 필드 | 인라인 에러 메시지 |
|-----------|------|-------------------|
| 404 Not Found (투자자 미존재) | investorId | "투자자를 찾을 수 없습니다." |
| 404 Not Found (증권계좌 미존재) | securitiesAccountId | "증권계좌를 찾을 수 없습니다." |
| 404 Not Found (공모주 미존재) | ipoId | "공모주를 찾을 수 없습니다." |
| 409 Conflict (중복 청약) | 전체 폼 | "이미 동일한 조건의 청약이 존재합니다." |
| 400 Bad Request | 해당 필드 | API 응답의 에러 메시지를 매핑하여 표시 |
| 네트워크 오류 | 전체 폼 | "네트워크 연결을 확인해 주세요." |
| quantity 0 이하 | quantity | "0 초과 정수를 입력해 주세요." |
| depositAmount 음수 | depositAmount | "0 이상 정수를 입력해 주세요." |

### 성공 후 이동 경로
- 청약 등록 성공(201) → 청약 목록 화면으로 이동
- 등록된 청약이 목록에 즉시 표시되는지 확인

## 2. 청약 목록 화면

### 화면 목적
사용자의 전체 청약 목록을 조회하고, 배정 여부(미배정/배정완료)로 필터링한다. 미배정 청약에서 "배정 입력" 버튼을 통해 배정 등록 화면으로 진입한다(D-W14-001).

### 사용하는 API
- `GET /investment-history?investorId=...` (D-W14-003, Epic 11) — 청약 목록 조회
  - 응답에 `allocation` 필드가 `null`이면 미배정, 아니면 배정완료

### 화면 구성
- **필터 버튼**: 미배정 / 배정완료 / 전체 (기본값: 전체)
- **청약 카드 목록**: 각 청약 항목에 다음 정보 표시
  - 공모명, 증권계좌, 청약수량, 청약일시, 배정 여부
- **"배정 입력" 버튼**: 미배정(`allocation: null`) 청약에만 표시

### 폼 필드
이 화면은 목록 조회/필터 화면이므로 별도의 입력 폼이 없다. 필터링은 버튼 클릭으로 처리한다.

| 요소 | 설명 |
|------|------|
| 필터 버튼 그룹 | 미배정 / 배정완료 / 전체 |
| 청약 카드 | 각 청약의 요약 정보 표시 |
| 배정 입력 버튼 | 미배정 청약 카드에만 표시 |

### 화면 상태

| 상태 | 설명 | UI 동작 |
|------|------|---------|
| 초기 (idle) | 화면 로드 시 | 목록 로딩 중(스피너) |
| 로딩 (loading) | `GET /investment-history` 호출 중 | 스피너 표시, 목록 빈 상태 |
| 성공 (success) | 200 응답 수신 | 청약 카드 목록 표시, 필터 버튼 활성화 |
| 에러 (error) | 네트워크 오류 또는 API 에러 | 에러 메시지 표시, 재시도 버튼 제공 |

### 에러 처리

| 에러 유형 | 필드 | 인라인 에러 메시지 |
|-----------|------|-------------------|
| 네트워크 오류 | 전체 화면 | "네트워크 연결을 확인해 주세요." |
| 404 (투자자 미존재) | 전체 화면 | "투자자 정보를 찾을 수 없습니다." |
| API 기타 에러 | 전체 화면 | "청약 목록을 불러오는 데 실패했습니다." |

### 성공 후 이동 경로
- "배정 입력" 버튼 클릭 → 배정 등록 화면으로 이동 (선택된 청약의 subscriptionId를 전달)
- 필터 변경 시 목록이 즉시 필터링되어 갱신됨

## 3. 배정 등록 화면

### 화면 목적
선택된 청약의 청약수량을 참고 표시하며, 배정수량·배정일시·배정방식·배정단가·비고를 입력하여 배정을 등록한다(D-W14-004). 배정 등록은 별도 화면으로 운영된다(D-W14-001).

### 사용하는 API
- `POST /allocations` (D-W14-003) — 배정 등록
  - 요청: `{ subscriptionId, allocatedQuantity, allocatedAt, allocationMethod?, allocationPrice?, note? }`
  - 응답 201: 배정 등록 성공
  - 응답 400: 유효성 오류 (배정수량>청약수량 등)
  - 응답 404: 청약을 찾을 수 없음
  - 응답 409: 중복 배정

### 폼 필드

| 필드명 | 타입 | 필수 | 프론트엔드 유효성 검사 규칙 |
|--------|------|------|-----------------------------|
| subscriptionId | hidden/display | 예 | 선택된 청약의 ID — 표시만 하고 수정 불가 |
| referenceQuantity | number | 아니오 | 선택된 청약의 청약수량을 **참고 표시**만 (읽기 전용) |
| allocatedQuantity | number | 예 | 0 초과 정수만 검증 (D-W14-002). 서버가 배정수량>청약수량 검증을 수행하므로 프론트는 UX 보조만 제공 (D-W14-004) |
| allocatedAt | datetime-local | 예 | 배정일시 선택 — 필수 |
| allocationMethod | select | 아니오 | 배정방식 선택 — 선택 사항 (API에서 `?`로 명시) |
| allocationPrice | number | 아니오 | 배정단가 입력 — 선택 사항 (API에서 `?`로 명시). 0 초과 정수만 검증 |
| note | textarea | 아니오 | 비고 — 선택 사항 |

### 참고 표시 (D-W14-004)
- 선택된 청약의 `quantity`(청약수량)를 폼 상단에 참고 표시로 보여준다.
- 프론트는 청약수량을 기준으로 `allocatedQuantity`가 초과되지 않는지 **UX 보조**로 안내할 수 있으나, 최종 검증은 서버가 수행한다.
- 서버 400 응답(배정수량>청약수량) 시 해당 에러 메시지를 인라인 에러로 그대로 표시한다.

### 화면 상태

| 상태 | 설명 | UI 동작 |
|------|------|---------|
| 초기 (idle) | 폼이 초기화된 상태 | 청약 참고 정보 표시, 모든 필드 빈 값, 에러 메시지 숨김 |
| 로딩 (loading) | API 호출 중 | 제출 버튼 비활성화, 스피너 표시 |
| 성공 (success) | 201 응답 수신 | 성공 메시지 표시, 청약 목록 화면으로 이동 |
| 에러 (error) | 400/404/409 응답 또는 네트워크 오류 | 필드 아래 인라인 에러 메시지 표시 |

### 에러 처리

| 에러 유형 | 필드 | 인라인 에러 메시지 |
|-----------|------|-------------------|
| 404 Not Found (청약 미존재) | subscriptionId | "선택된 청약을 찾을 수 없습니다." |
| 409 Conflict (중복 배정) | 전체 폼 | "이미 동일한 청약에 대한 배정이 존재합니다." |
| 400 Bad Request (배정수량>청약수량) | allocatedQuantity | 서버 응답 메시지를 그대로 표시 (예: "배정수량은 청약수량을 초과할 수 없습니다.") |
| 400 Bad Request | 해당 필드 | API 응답의 에러 메시지를 매핑하여 표시 |
| 네트워크 오류 | 전체 폼 | "네트워크 연결을 확인해 주세요." |
| allocatedQuantity 0 이하 | allocatedQuantity | "0 초과 정수를 입력해 주세요." |
| allocationPrice 0 이하 | allocationPrice | "0 초과 정수를 입력해 주세요." |

### 성공 후 이동 경로
- 배정 등록 성공(201) → 청약 목록 화면으로 이동
- 목록에서 해당 청약의 배정 상태가 "배정완료"로 갱신되는지 확인

## 4. 공통 섹션

### 4.1 수정/삭제 확인 다이얼로그
- **수정**: 모든 수정(PATCH) 동작 전에 확인 다이얼로그를 표시한다.
  - 내용: "정말로 이 항목을 수정하시겠습니까?" + 변경 전/후 값 요약
  - 확인/취소 버튼 제공
- **삭제**: 모든 삭제(DELETE, 논리 삭제) 동작 전에 확인 다이얼로그를 표시한다.
  - 내용: "정말로 이 항목을 삭제하시겠습니까? (논리 삭제됩니다)"
  - 확인/취소 버튼 제공
- **조사 결론 유지**: 확인 다이얼로그는 반드시 존재하며, 우회하지 않는다.

### 4.2 수정 이력 UI 없음 (D-W14-005)
- 이 프로젝트에는 수정 이력을 표시하는 UI를 만들지 않는다.
- 백엔드에 별도 변경 이력 테이블이 없으므로 프론트에도 "수정 이력 보기" 같은 화면을 제공하지 않는다.
- 단순 수정 폼(현재 값을 불러와 덮어쓰기)만 제공한다.

### 4.3 접근성 기준 (D-W13-005)
- **기준**: WCAG 2.1 AA 준수
- **검증 도구**: `axe-core` 브라우저 확장/CI 통합 단일 채택
- **필수 요소**:
  - 모든 폼 필드에 `<label>` 요소 연결
  - 에러 메시지에 `aria-live="polite"` 속성 적용
  - 포커스 관리: 에러 발생 시 첫 번째 에러 필드로 자동 포커스
  - 색상만으로 에러를 전달하지 않음(아이콘/텍스트 병행)
  - 키보드 네비게이션 지원(Tab, Enter, Escape)
  - `aria-invalid` 및 `aria-describedby` 속성 사용

### 4.4 반응형 브레이크포인트 (D-W13-004)

| 브레이크포인트 | 최소 너비 | 적용 대상 |
|---------------|-----------|-----------|
| 모바일 | 640px | 폼 전체 폭 100%, 단일 컬럼 레이아웃 |
| 태블릿 | 768px | 2열 레이아웃 가능(필드 그룹화) |
| 데스크톱 | 1024px | 전체 폭 제한, 양쪽 여백 확보 |

- CSS 미디어 쿼리: `@media (min-width: 640px)`, `@media (min-width: 768px)`, `@media (min-width: 1024px)`
- 모바일 우선(mobile-first) 접근

## 5. 수용 기준 (Acceptance Criteria)

### AC-001: 청약 등록 성공
**Given** 유효한 investorId, securitiesAccountId, ipoId, quantity, depositAmount, subscribedAt가 입력됨  
**When** `POST /subscriptions` 요청을 보냄  
**Then** 201 응답을 받음  
**And** 청약 목록 화면으로 이동함  

### AC-002: 청약 등록 실패 (0 이하 수량)
**Given** quantity가 0 이하인 값이 입력됨  
**When** `POST /subscriptions` 요청을 시도함  
**Then** 서버 호출 전 프론트 유효성 검사가 실패함  
**And** "0 초과 정수를 입력해 주세요." 에러 메시지가 표시됨  

### AC-003: 청약 등록 실패 (음수 증거금)
**Given** depositAmount가 음수인 값이 입력됨 (0은 유효한 값이므로 허용)  
**When** `POST /subscriptions` 요청을 시도함  
**Then** 서버 호출 전 프론트 유효성 검사가 실패함  
**And** "0 이상 정수를 입력해 주세요." 에러 메시지가 표시됨  

### AC-004: 청약 등록 실패 (404)
**Given** 존재하지 않는 investorId, securitiesAccountId 또는 ipoId가 입력됨  
**When** `POST /subscriptions` 요청을 보냄  
**Then** 404 응답을 받음  
**And** 해당 필드 아래에 "~을/를 찾을 수 없습니다." 에러 메시지가 표시됨  

### AC-005: 청약 등록 실패 (중복)
**Given** 이미 동일한 조건의 청약이 존재함  
**When** `POST /subscriptions` 요청을 보냄  
**Then** 409 응답을 받음  
**And** "이미 동일한 조건의 청약이 존재합니다." 에러 메시지가 표시됨  

### AC-006: 청약 등록 실패 (서버 유효성 오류)
**Given** 서버가 거부하는 유효성 오류가 발생함  
**When** `POST /subscriptions` 요청을 보냄  
**Then** 400 응답을 받음  
**And** API 응답의 에러 메시지가 인라인으로 표시됨  

### AC-007: 청약 등록 성공 후 목록 이동
**Given** 청약 등록이 성공적으로 완료됨  
**When** 201 응답을 수신함  
**Then** 청약 목록 화면으로 자동 이동함  
**And** 새로 등록된 청약이 목록에 표시됨  

### AC-008: 청약 목록 로딩
**Given** 청약 목록 화면에 진입함  
**When** `GET /investment-history` 요청이 시작됨  
**Then** 로딩 상태가 표시됨  
**And** 응답 수신 후 청약 카드 목록이 채워짐  

### AC-009: 미배정 청약 필터링
**Given** 전체 청약 목록이 표시됨  
**When** "미배정" 필터 버튼을 클릭함  
**Then** `allocation`이 `null`인 청약만 목록에 표시됨  

### AC-010: 배정완료 필터링
**Given** 전체 청약 목록이 표시됨  
**When** "배정완료" 필터 버튼을 클릭함  
**Then** `allocation`이 `null`이 아닌 청약만 목록에 표시됨  

### AC-011: 미배정 청약에서 배정 입력 버튼 표시
**Given** 미배정(`allocation: null`) 청약이 목록에 표시됨  
**When** 해당 청약 카드를 확인함  
**Then** "배정 입력" 버튼이 표시됨  

### AC-012: 배정 입력 버튼 클릭 시 배정 등록 화면 이동
**Given** 미배정 청약의 "배정 입력" 버튼을 클릭함  
**When** 클릭하면  
**Then** 배정 등록 화면으로 이동하고 선택된 청약의 subscriptionId가 전달됨  

### AC-013: 배정 등록 성공
**Given** 유효한 allocatedQuantity, allocatedAt이 입력되고 referenceQuantity가 참고 표시됨  
**When** `POST /allocations` 요청을 보냄  
**Then** 201 응답을 받음  
**And** 청약 목록 화면으로 이동함  

### AC-014: 배정 등록 실패 (배정수량>청약수량)
**Given** allocatedQuantity가 referenceQuantity(청약수량)보다 큰 값이 입력됨  
**When** `POST /allocations` 요청을 보냄  
**Then** 400 응답을 받음  
**And** 서버 응답 메시지가 allocatedQuantity 필드 아래 인라인 에러로 표시됨  
**And** 프론트에서 서버 검증 로직을 재구현하지 않음  

### AC-015: 배정 등록 실패 (404)
**Given** 존재하지 않는 subscriptionId에 대해 배정 등록을 시도함  
**When** `POST /allocations` 요청을 보냄  
**Then** 404 응답을 받음  
**And** "선택된 청약을 찾을 수 없습니다." 에러 메시지가 표시됨  

### AC-016: 배정 등록 실패 (중복)
**Given** 이미 동일한 청약에 대한 배정이 존재함  
**When** `POST /allocations` 요청을 보냄  
**Then** 409 응답을 받음  
**And** "이미 동일한 청약에 대한 배정이 존재합니다." 에러 메시지가 표시됨  

### AC-017: 수정/삭제 확인 다이얼로그
**Given** 청약 또는 배정 항목의 수정/삭제 버튼을 클릭함  
**When** 버튼을 클릭하면  
**Then** 확인 다이얼로그가 표시됨  
**And** "정말로 수정/삭제하시겠습니까?" 내용이 포함됨  
**And** 확인을 누르지 않으면 수정/삭제가 수행되지 않음  

### AC-018: 수정 이력 UI 없음
**Given** 청약 또는 배정 항목을 수정함  
**When** 수정 완료 후  
**Then** "수정 이력" 화면이나 링크가 존재하지 않음  
**And** 단순 수정 폼(현재 값 덮어쓰기)만 제공됨  

### AC-019: 접근성 검증 통과
**Given** 모든 화면이 렌더링됨  
**When** `axe-core`로 접근성 검사를 수행함  
**Then** WCAG 2.1 AA 기준을 통과함  
**And** `aria-live`, `aria-invalid`, `aria-describedby` 속성이 올바르게 적용됨  

### AC-020: 반응형 레이아웃
**Given** 다양한 화면 크기에서 화면이 렌더링됨  
**When** 브라우저 너비를 640px, 768px, 1024px로 변경함  
**Then** 각 브레이크포인트에 맞는 레이아웃이 적용됨  
**And** 모바일(640px)에서는 단일 컬럼, 태블릿(768px)에서는 2열, 데스크톱(1024px)에서 전체 레이아웃  

### AC-021: 네트워크 오류 처리
**Given** 네트워크 연결이 끊어진 상태  
**When** `POST /subscriptions` 또는 `POST /allocations` 요청을 보냄  
**Then** 네트워크 오류가 감지됨  
**And** "네트워크 연결을 확인해 주세요." 메시지가 표시됨  

### AC-022: 배정 등록 시 참고 표시
**Given** 배정 등록 화면에 진입함  
**When** 선택된 청약의 정보가 로드됨  
**Then** 청약수량(referenceQuantity)이 읽기 전용으로 참고 표시됨  
**And** 사용자가 해당 값을 수정할 수 없음  

### AC-023: 배정 등록 성공 후 목록 갱신
**Given** 배정 등록이 성공적으로 완료됨  
**When** 201 응답을 수신하고 청약 목록 화면으로 이동함  
**Then** 해당 청약의 배정 상태가 "배정완료"로 표시됨

## 6. E2E 테스트 범위

### 6.1 기본 플로우 (Happy Path)

#### 시나리오 1: 청약 등록 → 목록에서 미배정 확인 → 배정 등록 → 배정완료 확인 전체 플로우
1. **청약 등록**: `POST /subscriptions`에 유효한 investorId, securitiesAccountId, ipoId, quantity, depositAmount, subscribedAt 입력 → 201 응답 확인
2. **목록 로드**: `GET /investment-history?investorId=...` 요청 → 청약 카드가 목록에 표시됨 확인
3. **미배정 확인**: "미배정" 필터 적용 → 방금 등록한 청약이 미배정 상태로 표시됨 확인
4. **배정 입력**: 미배정 청약의 "배정 입력" 버튼 클릭 → 배정 등록 화면으로 이동
5. **배정 등록**: `POST /allocations`에 allocatedQuantity, allocatedAt 입력 → 201 응답 확인
6. **최종 확인**: 청약 목록 화면에서 해당 청약이 "배정완료"로 표시되는지 검증

#### 시나리오 2: 배정 등록 시 참고 표시
1. 배정 등록 화면 진입
2. 선택된 청약의 quantity가 referenceQuantity로 읽기 전용 표시되는지 확인
3. allocatedQuantity 입력 시 청약수량이 초과되지 않는지 UX 보조 확인

#### 시나리오 3: 필터 전환
1. 청약 목록 화면에서 "전체" → "미배정" → "배정완료" 순으로 필터 버튼 클릭
2. 각 필터에 맞는 청약 카드만 표시되는지 검증

### 6.2 에러 케이스

#### 시나리오 4: 청약 등록 실패 (중복)
1. 동일한 조건으로 `POST /subscriptions`를 두 번 보냄
2. 첫 번째는 201, 두 번째는 409 응답 확인
3. "이미 동일한 조건의 청약이 존재합니다." 메시지 표시 검증

#### 시나리오 5: 배정 등록 실패 (배정수량>청약수량)
1. 배정 등록 화면에서 allocatedQuantity를 referenceQuantity보다 크게 입력
2. `POST /allocations` 요청 → 400 응답 확인
3. 서버 응답 메시지가 인라인 에러로 표시되는지 확인
4. 프론트에서 서버 검증 로직을 재구현하지 않았는지 확인

#### 시나리오 6: 청약 등록 실패 (404)
1. 존재하지 않는 ipoId로 `POST /subscriptions` → 404 응답 확인
2. "공모주를 찾을 수 없습니다." 메시지 표시 검증

#### 시나리오 7: 네트워크 오류
1. 네트워크를 차단한 상태에서 `POST /subscriptions` 또는 `POST /allocations` 요청
2. "네트워크 연결을 확인해 주세요." 메시지 표시 검증

### 6.3 확인 다이얼로그 테스트

#### 시나리오 8: 수정 확인 다이얼로그
1. 청약 또는 배정 항목의 수정 버튼 클릭
2. 확인 다이얼로그가 표시되는지 검증
3. 취소를 선택하면 수정되지 않는지 확인
4. 확인을 선택하면 수정이 적용되는지 확인

#### 시나리오 9: 삭제 확인 다이얼로그
1. 청약 또는 배정 항목의 삭제 버튼 클릭
2. 확인 다이얼로그가 표시되는지 검증
3. "논리 삭제" 내용이 포함되어 있는지 확인
4. 취소를 선택하면 삭제되지 않는지 확인

### 6.4 접근성 테스트

#### 시나리오 10: axe-core 접근성 검증
1. 청약 등록, 청약 목록, 배정 등록 화면 각각에서 `axe-core` 스캔 수행
2. WCAG 2.1 AA 위반 사항이 없는지 검증
3. `aria-live`, `aria-invalid`, `aria-describedby` 속성 올바른 적용 확인

### 6.5 반응형 테스트

#### 시나리오 11: 다양한 화면 크기
1. 640px(모바일), 768px(태블릿), 1024px(데스크톱)에서 각 화면 렌더링 확인
2. 레이아웃이 각 브레이크포인트에 맞게 적용되는지 검증

### 6.6 유효성 검증 테스트

#### 시나리오 12: 최소 청약 단위 미적용 확인
1. 청약 등록 시 quantity에 1 입력 후 제출
2. "최소 청약 단위 배수" 에러가 발생하지 않는지 확인
3. 서버에서 0 초과 정수만 허용하는지 백엔드 검증에 의존하며 프론트에서 추가 규칙을 강제하지 않음 확인

#### 시나리오 13: 수량/증거금 필드 유효성 검증
1. quantity에 0 입력 → 프론트 유효성 검사로 서버 호출 전에 차단됨 확인
2. depositAmount에 0 입력 → 유효한 값으로 정상 처리됨 확인 (증거금 0원 허용)
3. depositAmount에 음수 입력 → 차단됨 확인

### 6.7 테스트 환경
- **테스트 도구**: Playwright (E2E)
- **API mocking**: 실제 엔드포인트 호출 포함
- **DB 상태 변경**: 실제 DB 상태 변경을 포함한 통합 테스트
- **세션 관리**: JSESSIONID 쿠키 기반 세션 시뮬레이션
- **확인 다이얼로그**: Playwright에서 다이얼로그 상호작용 시뮬레이션
