## 1. 로그인 화면

### 화면 목적
사용자가 이메일과 비밀번호로 인증하여 계정에 접속한다. 인증 성공 시 서버가 JSESSIONID 쿠키를 설정하고, 프론트는 해당 세션을 기반으로 후속 요청을 수행한다.

### 사용하는 API
- `POST /auth/login` (D-W13-001)
  - 요청: `{ email: string, password: string }`
  - 응답 200: 세션 쿠키(JSESSIONID) 설정됨
  - 응답 401: 인증 실패

### 폼 필드

| 필드명 | 타입 | 필수 | 프론트엔드 유효성 검사 규칙 |
|--------|------|------|---------------------------|
| email | text (이메일) | 예 | 이메일 형식 검증 (regex), 필수 입력 |
| password | password | 예 | 최소 8자 이상, 비어 있으면 안 됨 |

### 화면 상태

| 상태 | 설명 | UI 동작 |
|------|------|---------|
| 초기 (idle) | 폼이 비어 있고 입력을 대기하는 상태 | 모든 필드 빈 값, 에러 메시지 숨김 |
| 로딩 (loading) | API 호출 중 | 제출 버튼 비활성화, 스피너 표시 |
| 성공 (success) | 200 응답 수신 | 리디렉션(대시보드 또는 이전 페이지) |
| 에러 (error) | 401 응답 또는 네트워크 오류 | 이메일/비밀번호 필드 아래 인라인 에러 메시지 표시 |

### 에러 처리

| 에러 유형 | 필드 | 인라인 에러 메시지 |
|-----------|------|-------------------|
| 401 Unauthorized | 전체 폼 | "이메일 또는 비밀번호가 올바르지 않습니다." |
| 네트워크 오류 | 전체 폼 | "네트워크 연결을 확인해 주세요." |
| 이메일 형식 오류 | email | "올바른 이메일 형식을 입력해 주세요." |
| 필수 필드 누락 | 해당 필드 | "필수 입력 항목입니다." |

### 성공 후 이동 경로
- 로그인 성공 → 대시보드(`/dashboard`)로 리디렉션
- 이전 접근 페이지가 있으면 해당 페이지로 리디렉션 (리다이렉트 URL 우선)

## 2. 회원가입 화면

### 화면 목적
신규 사용자가 이메일, 비밀번호, 이름을 입력하여 계정을 생성한다. 회원가입 성공 후 투자자 등록 화면으로 자동 이동한다.

### 사용하는 API
- `POST /accounts` (D-W13-001)
  - 요청: `{ email: string, password: string, name: string }`
  - 응답 201: `{ accountId: number, email: string }`
  - 응답 409: 이미 존재하는 이메일 (중복)
  - 응답 400: 유효성 오류

### 폼 필드

| 필드명 | 타입 | 필수 | 프론트엔드 유효성 검사 규칙 |
|--------|------|------|---------------------------|
| email | text (이메일) | 예 | 이메일 형식 검증(regex), 필수 입력 |
| password | password | 예 | 최소 8자 이상 72자 이하, 영문/숫자/특수문자 중 2종류 이상 포함 (account-authentication spec 기준 — 정확한 정책은 Epic 1 D-001 최종 결정에 따름, 프론트는 서버와 동일한 규칙으로 1차 검증) |
| name | text | 예 | 필수 입력, 2자 이상 50자 이하 |

### 화면 상태

| 상태 | 설명 | UI 동작 |
|------|------|---------|
| 초기 (idle) | 폼이 비어 있고 입력을 대기하는 상태 | 모든 필드 빈 값, 에러 메시지 숨김 |
| 로딩 (loading) | API 호출 중 | 제출 버튼 비활성화, 스피너 표시 |
| 성공 (success) | 201 응답 수신 | 투자자 등록 화면으로 자동 이동 |
| 에러 (error) | 409/400 응답 또는 네트워크 오류 | 필드 아래 인라인 에러 메시지 표시 |

### 에러 처리

| 에러 유형 | 필드 | 인라인 에러 메시지 |
|-----------|------|-------------------|
| 409 Conflict (이메일 중복) | email | "이미 사용 중인 이메일입니다." |
| 400 Bad Request | 해당 필드 | API 응답의 에러 메시지를 매핑하여 표시 |
| 네트워크 오류 | 전체 폼 | "네트워크 연결을 확인해 주세요." |
| 이메일 형식 오류 | email | "올바른 이메일 형식을 입력해 주세요." |
| 비밀번호 조건 미충족 | password | "비밀번호는 최소 8자 이상이어야 합니다." |
| 이름 필수 누락 | name | "이름을 입력해 주세요." |

### 성공 후 이동 경로
- 회원가입 성공(201) → 투자자 등록 화면(`/investors/register`)으로 자동 이동
- API 응답 `{ accountId, email }`의 accountId를 후속 요청에 활용

## 3. 투자자 등록 화면

### 화면 목적
회원가입을 완료한 사용자가 최초 1회 또는 설정에서 추가로 투자자 정보를 등록한다. display_name과 relationship(선택)을 입력하여 투자자 레코드를 생성한다.

### 사용하는 API
- `POST /investors` (D-W13-001, investor-management.md 참고)
  - 요청: `{ display_name: string, relationship?: string (enum: SELF, SPOUSE, PARENT, CHILD, OTHER) }`
  - 응답 201: `{ id, display_name, account_id, status, deleted_at, created_at, updated_at }`
  - 응답 400: 유효성 오류

### 폼 필드

| 필드명 | 타입 | 필수 | 프론트엔드 유효성 검사 규칙 |
|--------|------|------|---------------------------|
| display_name | text | 예 | 필수 입력, 1-50자, 특수문자 허용(한글, 영문, 특수문자) |
| relationship | select | 아니오 | 선택값: SELF, SPOUSE, PARENT, CHILD, OTHER — 미선택 시 빈 값 |

### 화면 상태

| 상태 | 설명 | UI 동작 |
|------|------|---------|
| 초기 (idle) | 폼이 비어 있고 입력을 대기하는 상태 | display_name 빈 값, relationship 미선택 |
| 로딩 (loading) | API 호출 중 | 제출 버튼 비활성화, 스피너 표시 |
| 성공 (success) | 201 응답 수신 | 성공 메시지 표시 후 대시보드(`/dashboard`)로 이동 |
| 에러 (error) | 400 응답 또는 네트워크 오류 | 필드 아래 인라인 에러 메시지 표시 |

### 에러 처리

| 에러 유형 | 필드 | 인라인 에러 메시지 |
|-----------|------|-------------------|
| 400 Bad Request (빈 이름) | display_name | "표시 이름은 필수입니다." |
| 400 Bad Request (50자 초과) | display_name | "표시 이름은 50자 이하여야 합니다." |
| 400 Bad Request (유효하지 않은 relationship) | relationship | "유효한 관계를 선택해 주세요." |
| 네트워크 오류 | 전체 폼 | "네트워크 연결을 확인해 주세요." |

### 성공 후 이동 경로
- 투자자 등록 성공(201) → 대시보드(`/dashboard`)로 이동
- 투자자 ID(`id`)를 이후 증권계좌 등록 시 `investorId`로 활용

### 참고
- 투자자 등록은 회원가입 후 최초 1회 또는 설정에서 추가 등록 가능
- 동일 계정 내에서 동명이인 투자자 등록 허용(D-I-001/AC-011)

## 4. 증권계좌 등록 화면

### 화면 목적
인증된 사용자가 증권사를 선택하고 계좌번호를 입력하여 증권계좌를 등록한다. 계좌번호는 입력 시 하이픈 자동 삽입을 지원하며, 서버가 마스킹된 계좌번호를 응답으로 반환한다.

### 사용하는 API
- `GET /securities-firms` (D-W13-001, Epic 3에서 확정)
  - 증권사 목록 조회 — 드롭다운 옵션 제공용
- `POST /securities-accounts` (D-W13-001)
  - 요청: `{ investorId: number, securitiesFirmId: number, accountNumber: string, accountName?: string, isDefault?: boolean }`
  - 응답 201: 마스킹된 `accountNumber` 포함 응답 (`{ ...accountNumber: "****-****-****-1234", ... }`)
  - 응답 400: 유효성 오류
  - 응답 404: 투자자 또는 증권사를 찾을 수 없음

### 폼 필드

| 필드명 | 타입 | 필수 | 프론트엔드 유효성 검사 규칙 |
|--------|------|------|---------------------------|
| securitiesFirmId | select | 예 | 증권사 목록 드롭다운 — 필수 선택 |
| accountNumber | text | 예 | 필수 입력, 입력 시 하이픈 자동 삽입(예: 0000-0000-0000-0000) |
| accountName | text | 아니오 | 선택 사항, 입력 시 빈 문자열 허용 |
| isDefault | checkbox | 아니오 | 기본 계좌 여부 체크박스, 미체크 시 false |

### 계좌번호 마스킹 표시 (D-W13-002)
- 서버 응답(`POST /securities-accounts` 201)으로 받은 `accountNumber`는 이미 뒷 4자리만 노출되고 나머지가 마스킹된 문자열(예: `****-****-****-1234`)이다.
- 프론트엔드는 서버가 보내주는 마스킹된 문자열을 **그대로 표시**하며, 별도의 마스킹 로직을 구현하지 않는다.
- **입력 시 하이픈 자동 삽입**만 프론트 책임: 사용자가 숫자만 입력하면 자동으로 4자리마다 하이픈이 삽입된다.

### 화면 상태

| 상태 | 설명 | UI 동작 |
|------|------|---------|
| 초기 (idle) | 폼이 비어 있고 입력을 대기하는 상태 | 모든 필드 초기값, 에러 메시지 숨김, 증권사 목록 로드 대기 |
| 로딩 (loading) | API 호출 중 (증권사 목록 조회 또는 계좌 등록) | 제출 버튼 비활성화, 스피너 표시 |
| 성공 (success) | 201 응답 수신 | 마스킹된 계좌번호 표시, 성공 메시지, 대시보드(`/dashboard`)로 이동 |
| 에러 (error) | 400/404 응답 또는 네트워크 오류 | 필드 아래 인라인 에러 메시지 표시 |

### 에러 처리

| 에러 유형 | 필드 | 인라인 에러 메시지 |
|-----------|------|-------------------|
| 404 Not Found (투자자 미존재) | 전체 폼 | "투자자 정보를 찾을 수 없습니다." |
| 404 Not Found (증권사 미존재) | securitiesFirmId | "선택한 증권사를 찾을 수 없습니다." |
| 400 Bad Request | 해당 필드 | API 응답의 에러 메시지를 매핑하여 표시 |
| 네트워크 오류 | 전체 폼 | "네트워크 연결을 확인해 주세요." |

### 성공 후 이동 경로
- 증권계좌 등록 성공(201) → 대시보드(`/dashboard`)로 이동
- 서버 응답에 포함된 마스킹된 `accountNumber`를 화면에 표시

### 하이픈 자동 삽입 구현
- 사용자가 숫자만 입력하면 4자리마다 하이픈(`-`)이 자동 삽입됨
- 예: `0000000000000000` → `0000-0000-0000-0000`
- 마스킹 로직은 프론트에서 하지 않으며, 입력 서식 지원만 수행

## 5. 공통 섹션

### 5.1 세션 인증 처리 방식 (D-W13-003)

- **쿠키**: Spring 기본값 `JSESSIONID`를 그대로 사용한다. 커스텀 쿠키 이름이나 별도 경로 설정을 하지 않는다.
- **프론트엔드 책임**: 쿠키를 직접 다루지 않는다. `fetch`/`axios`에 `credentials: 'include'`를 설정하여 브라우저의 기본 쿠키 처리에 위임한다.
- **인증 흐름**:
  1. `POST /auth/login` 호출 → 서버가 `Set-Cookie: JSESSIONID=...` 응답
  2. 브라우저가 자동으로 쿠키를 저장
  3. 이후 모든 API 요청에 `credentials: 'include'`로 자동 쿠키 포함 전송
  4. 로그아웃 시 서버가 쿠키를 무효화

### 5.2 증권계좌 등록 화면의 계좌번호 마스킹 (D-W13-002)

- **원칙**: 서버가 이미 마스킹한 계좌번호를 프론트가 그대로 표시한다.
- **프론트 책임 범위**: 입력 시 하이픈 자동 삽입(입력 서식 지원)만 수행
- **금지**: 프론트에서 별도의 마스킹 로직(은행별 패턴 등)을 구현하지 않는다.
- **응답 처리**: `POST /securities-accounts`의 201 응답에서 `accountNumber` 필드를 그대로 UI에 렌더링한다.

### 5.3 접근성 기준 (D-W13-005)

- **기준**: WCAG 2.1 AA 준수
- **검증 도구**: `axe-core` 브라우저 확장/CI 통합 단일 채택 (Lighthouse 조합 등 복잡한 다중 도구는 MVP 범위 밖)
- **필수 요소**:
  - 모든 폼 필드에 `<label>` 요소 연결
  - 에러 메시지에 `aria-live="polite"` 속성 적용
  - 포커스 관리: 에러 발생 시 첫 번째 에러 필드로 자동 포커스
  - 색상만으로 에러를 전달하지 않음(아이콘/텍스트 병행)
  - 키보드 네비게이션 지원(Tab, Enter, Escape)
  - `aria-invalid` 및 `aria-describedby` 속성 사용

### 5.4 반응형 브레이크포인트 (D-W13-004)

| 브레이크포인트 | 최소 너비 | 적용 대상 |
|---------------|-----------|-----------|
| 모바일 | 640px | 폼 전체 폭 100%, 단일 컬럼 레이아웃 |
| 태블릿 | 768px | 2열 레이아웃 가능(필드 그룹화) |
| 데스크톱 | 1024px | 전체 폭 제한, 양쪽 여백 확보 |

- CSS 미디어 쿼리: `@media (min-width: 640px)`, `@media (min-width: 768px)`, `@media (min-width: 1024px)`
- 모바일 우선(mobile-first) 접근

## 6. 수용 기준 (Acceptance Criteria)

### AC-001: 로그인 성공
**Given** 유효한 이메일과 비밀번호가 입력됨  
**When** `POST /auth/login` 요청을 보냄  
**Then** 200 응답을 받고 세션 쿠키가 설정됨  
**And** 대시보드(`/dashboard`)로 리디렉션됨  

### AC-002: 로그인 실패 (잘못된 인증 정보)
**Given** 잘못된 이메일 또는 비밀번호가 입력됨  
**When** `POST /auth/login` 요청을 보냄  
**Then** 401 응답을 받음  
**And** "이메일 또는 비밀번호가 올바르지 않습니다." 에러 메시지가 표시됨  

### AC-003: 로그인 실패 (네트워크 오류)
**Given** 네트워크 연결이 끊어진 상태  
**When** `POST /auth/login` 요청을 보냄  
**Then** 네트워크 오류가 감지됨  
**And** "네트워크 연결을 확인해 주세요." 메시지가 표시됨  

### AC-004: 회원가입 성공
**Given** 유효한 이메일, 비밀번호, 이름이 입력됨  
**When** `POST /accounts` 요청을 보냄  
**Then** 201 응답을 받고 `{ accountId, email }`를 수신함  
**And** 투자자 등록 화면으로 자동 이동함  

### AC-005: 회원가입 실패 (이메일 중복)
**Given** 이미 등록된 이메일이 입력됨  
**When** `POST /accounts` 요청을 보냄  
**Then** 409 응답을 받음  
**And** "이미 사용 중인 이메일입니다." 에러 메시지가 표시됨  

### AC-006: 회원가입 실패 (필수 필드 누락)
**Given** 필수 필드(email, password, name) 중 하나 이상이 비어있음  
**When** `POST /accounts` 요청을 보냄  
**Then** 400 응답을 받음  
**And** 해당 필드 아래에 유효성 에러 메시지가 표시됨  

### AC-007: 투자자 등록 성공
**Given** 인증된 상태에서 유효한 display_name이 입력됨  
**When** `POST /investors` 요청을 보냄  
**Then** 201 응답을 받고 투자자 정보 수신함  
**And** 대시보드(`/dashboard`)로 이동함  

### AC-008: 투자자 등록 실패 (빈 표시 이름)
**Given** display_name이 빈 문자열인 상태  
**When** `POST /investors` 요청을 보냄  
**Then** 400 응답을 받음  
**And** "표시 이름은 필수입니다." 에러 메시지가 표시됨  

### AC-009: 투자자 등록 실패 (50자 초과)
**Given** display_name이 50자를 초과함  
**When** `POST /investors` 요청을 보냄  
**Then** 400 응답을 받음  
**And** "표시 이름은 50자 이하여야 합니다." 에러 메시지가 표시됨  

### AC-010: 증권계좌 등록 성공
**Given** 인증된 상태에서 유효한 securitiesFirmId, accountNumber가 입력됨  
**When** `POST /securities-accounts` 요청을 보냄  
**Then** 201 응답을 받고 마스킹된 accountNumber를 수신함  
**And** 대시보드(`/dashboard`)로 이동함  

### AC-011: 증권계좌 등록 실패 (404)
**Given** 존재하지 않는 investorId 또는 securitiesFirmId가 입력됨  
**When** `POST /securities-accounts` 요청을 보냄  
**Then** 404 응답을 받음  
**And** 해당 에러 메시지가 표시됨  

### AC-012: 계좌번호 하이픈 자동 삽입
**Given** 사용자가 숫자를 입력함  
**When** accountNumber 필드에 숫자를 타이핑함  
**Then** 4자리마다 하이픈이 자동 삽입됨  
**And** 마스킹 로직은 프론트에서 수행되지 않음  

### AC-013: 세션 쿠키 자동 전송
**Given** 로그인 후 세션이 설정됨  
**When** 후속 API 요청(`POST /investors`, `POST /securities-accounts`)을 보냄  
**Then** `credentials: 'include'` 설정에 의해 JSESSIONID 쿠키가 자동 전송됨  
**And** 프론트가 쿠키를 직접 조작하지 않음  

### AC-014: 접근성 검증 통과
**Given** 모든 화면이 렌더링됨  
**When** `axe-core`로 접근성 검사를 수행함  
**Then** WCAG 2.1 AA 기준을 통과함  
**And** `aria-live`, `aria-invalid`, `aria-describedby` 속성이 올바르게 적용됨  

### AC-015: 반응형 레이아웃
**Given** 다양한 화면 크기에서 화면이 렌더링됨  
**When** 브라우저 너비를 640px, 768px, 1024px로 변경함  
**Then** 각 브레이크포인트에 맞는 레이아웃이 적용됨  
**And** 모바일(640px)에서는 단일 컬럼, 태블릿(768px)에서는 2열, 데스크톱(1024px)에서 전체 레이아웃  

### AC-016: 회원가입 후 투자자 등록 자동 이동
**Given** 회원가입이 성공적으로 완료됨  
**When** 201 응답을 수신함  
**Then** 투자자 등록 화면(`/investors/register`)으로 자동 이동함  
**And** 이동을 수동으로 확인할 수 있는 버튼은 제공하지 않음(자동 이동)  

### AC-017: 투자자 등록 후 증권계좌 등록 흐름
**Given** 투자자 등록이 완료됨  
**When** 대시보드에서 증권계좌 등록 버튼을 클릭함  
**Then** 증권계좌 등록 화면(`/securities-accounts/register`)으로 이동함  
**And** 투자자 ID가 자동으로 폼에 pre-fill됨  

### AC-018: 증권계좌 마스킹된 계좌번호 표시
**Given** 증권계좌 등록이 성공적으로 완료됨  
**When** 201 응답에서 마스킹된 accountNumber를 수신함  
**Then** 화면에 마스킹된 계좌번호(예: `****-****-****-1234`)가 그대로 표시됨  
**And** 프론트에서 별도 마스킹 변환을 수행하지 않음  

### AC-019: 회원가입 시 비밀번호 조건 검증
**Given** 8자 미만의 비밀번호가 입력됨  
**When** 회원가입 폼 제출 시도  
**Then** 400 응답 전 서버 호출 전에 프론트 유효성 검사가 실패함  
**And** "비밀번호는 최소 8자 이상이어야 합니다." 에러 메시지 표시  

### AC-020: 증권사 목록 드롭다운 로딩
**Given** 증권계좌 등록 화면 진입  
**When** `GET /securities-firms` 요청이 시작됨  
**Then** 드롭다운이 로딩 상태를 표시함  
**And** 응답 수신 후 증권사 옵션이 드롭다운에 채워짐

## 7. E2E 테스트 범위

### 7.1 기본 플로우 (Happy Path)

#### 시나리오 1: 회원가입 → 투자자 등록 → 증권계좌 등록 완료 흐름
1. **회원가입**: 유효한 이메일/비밀번호/이름으로 `POST /accounts` → 201 응답 확인
2. **투자자 등록**: `POST /investors`에 display_name 입력 → 201 응답 확인
3. **증권계좌 등록**: `GET /securities-firms`로 증권사 목록 로드 → `POST /securities-accounts`에 계좌 정보 입력 → 201 응답 확인, 마스킹된 계좌번호 표시 확인
4. **최종 확인**: 대시보드(`/dashboard`)에 정상적으로 이동했는지 검증

#### 시나리오 2: 로그인 → 대시보드 접속
1. **로그인**: `POST /auth/login`으로 인증 → 200 응답, 세션 쿠키 설정 확인
2. **대시보드**: `/dashboard`에 정상 접속하는지 검증

### 7.2 에러 케이스

#### 시나리오 3: 로그인 실패 흐름
1. 잘못된 비밀번호로 `POST /auth/login` → 401 응답 확인
2. 인라인 에러 메시지 표시 검증
3. 대시보드로 리디렉션되지 않는지 확인

#### 시나리오 4: 회원가입 중복 이메일
1. 이미 등록된 이메일로 `POST /accounts` → 409 응답 확인
2. "이미 사용 중인 이메일입니다." 메시지 표시 검증

#### 시나리오 5: 투자자 등록 실패 (빈 이름)
1. display_name을 빈 문자열로 `POST /investors` → 400 응답 확인
2. 인라인 에러 메시지 표시 검증

#### 시나리오 6: 증권계좌 등록 404 에러
1. 존재하지 않는 investorId로 `POST /securities-accounts` → 404 응답 확인
2. "투자자 정보를 찾을 수 없습니다." 메시지 표시 검증

### 7.3 접근성 테스트

#### 시나리오 7: axe-core 접근성 검증
1. 로그인, 회원가입, 투자자 등록, 증권계좌 등록 화면 각각에서 `axe-core` 스캔 수행
2. WCAG 2.1 AA 위반 사항이 없는지 검증
3. `aria-live`, `aria-invalid`, `aria-describedby` 속성 올바른 적용 확인

### 7.4 반응형 테스트

#### 시나리오 8: 다양한 화면 크기
1. 640px(모바일), 768px(태블릿), 1024px(데스크톱)에서 각 화면 렌더링 확인
2. 레이아웃이 각 브레이크포인트에 맞게 적용되는지 검증

### 7.5 세션 인증 테스트

#### 시나리오 9: 세션 쿠키 자동 전송
1. 로그인 후 후속 API 요청에서 `credentials: 'include'`가 적용되는지 확인
2. `JSESSIONID` 쿠키가 자동으로 전송되는지 네트워크 탭에서 확인
3. 프론트가 쿠키를 직접 다루지 않는지 확인

### 7.6 계좌번호 마스킹 테스트

#### 시나리오 10: 계좌번호 하이픈 자동 삽입
1. accountNumber 필드에 숫자를 입력할 때 4자리마다 하이픈이 자동 삽입되는지 확인
2. 서버 응답의 마스킹된 계좌번호가 그대로 표시되는지 확인
3. 프론트가 별도 마스킹 로직을 사용하지 않는지 확인

### 7.7 테스트 환경
- **테스트 도구**: Playwright (E2E)
- **API mocking**: 실제 엔드포인트 호출 포함
- **DB 상태 변경**: 실제 DB 상태 변경을 포함한 통합 테스트
- **세션 관리**: JSESSIONID 쿠키 기반 세션 시뮬레이션
