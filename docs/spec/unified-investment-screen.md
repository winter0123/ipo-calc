# 청약·매도 통합 관리 화면 spec (unified-investment-screen)

> 화면명: **`청약·매도 관리`**, 제안 경로 `/ipos/:ipoId/manage`. 목표: 공모주 1건의 청약·배정·매도 전 과정을 화면 이동 없이 한 화면에서 입력·수정·삭제한다. 2026-11-12 Master 보정.

## 사용자 목표

- 공모주(IPO) 하나 + 현재 투자자 + 증권계좌(1개 자동선택 / 여러 개면 구분선택 / 번호 없는 계좌도 허용)를 고정하고, 그 쌍의 기록을 한 URL에서 관리한다.
- 청약 정보 1건·배정 결과 1건·매도 내역 N건. 식별 단위 = 투자자×IPO×실계좌(부분 유니크).
- 청약 먼저 입력 / 매도부터 사후 등록, 두 방식을 같은 화면에서 모두 제공한다. 기존 청약/배정은 POST가 아니라 **불러와서 PATCH**로 처리.

## 화면 구조

1. 고정 헤더: 공모주명·종목코드·공모가·청약일·현재 투자자.
2. 증권계좌 select: 1개면 자동선택, 여러 개면 선택(증권사·계좌명), 번호 없는 계좌도 선택 가능. 계좌 변경 시 미저장 입력이 있으면 인라인 경고 → 취소 시 현재 유지 / 확인 시 새 문맥 재조회 + 입력 초기화(다른 계좌에 dirty 금액이 묻지 않게).
3. 청약 섹션(1건): 수량/증거금/청약일(실제 청약기간 날짜 버튼 — `subscriptionPeriodDates`)/메모. 기록 없으면 첫 입력, 있으면 원본 로드 → PATCH.
4. 배정 섹션(1건): 배정수량/비고. 없으면 사후 입력 가능, 있으면 PATCH. 총액은 서버 계산 표시.
5. 매도 섹션(N건): 누적 리스트(매도일·수량·단가·공모주수수료·세금 및 기타·상태) + "+매도 추가" → 인라인 1행 → 저장하면 누적. 건별 수정/삭제(현재 페이지에서).
6. 하단 요약: 배정수량 / Σ매도수량 / 잔여 / 상태. (예: 10주 배정 → 3주 12,000 + 4주 13,500 + 3주 11,000 = 잔여 0.) 매출과 수익을 혼동하지 않고 `saleMath` 구분 유지.

## Acceptance Criteria

- AC-1 `/ipos/:ipoId/manage` 한 URL에서 증권계좌 선택을 바꾸면 그 계좌의 (투자자, IPO, 계좌) 기록이 다시 조회·표시된다. 다른 URL로 이동하지 않는다.
- AC-2 청약 없는 상태에서 매도 섹션으로 매도를 먼저 등록할 수 있다. 화면상 가능하되, 저장 시 서버가 (investor, ipo, account)로 기존 ACTIVE 청약을 먼저 찾고 없으면 청약(배정수량만큼)·배정을 자동 생성/재사용한다(`SaleService.resolveAllocationId`). 배정 섹션도 동일하게 신규 생성/재사용한다.
- AC-3 첫 청약 저장에 매도 날짜·단가를 요구하지 않는다. 섹션별 독립 저장이며, 하나의 거대한 필수 폼이 아니다.
- AC-4 기록이 있으면 원본을 불러와 PATCH로만 수정한다. 재POST 저장은 없다.
- AC-5 매도 저장/수정/삭제 후 누적 리스트·잔여·상태가 갱신된다. 매도 추가 저장 후 **상세 재조회 완료 전에는 다음 "+매도 추가"를 잠근다**. 성공 시 인라인 폼을 닫고 입력을 초기화하며, 다시 열면 그 시점의 잔여·수수료 기본값(0원)으로 재계산한다. 부분 실패는 그 섹션에만 표시하고 다른 섹션의 입력은 유지.
- AC-6 배정수량을 이미 매도한 수량보다 작게 줄일 수는 없다(**같은 수량은 허용** — 서버 `updatedAllocatedQuantity < soldQuantity` 조건, AllocationService.update:281-284). 매도 있는 배정은 취소 불가(cancel:324-326). 프론트는 서버 메시지 그대로 표시.
- AC-7 청약 수량은 배정받은 수량보다 작게 줄일 수 없다(같은 수량 허용, `SubscriptionService.update:136-142`).
- AC-8 계좌/투자자/IPO 전환 시 미저장 입력이 있으면 경고: 취소=현재 유지, 확인=새 문맥 재조회+입력 초기화.
- AC-9 진입점(목록·일정·상세·할 일·이력 액션·대시보드)은 모두 통합 화면 한 경로로 향한다. 기존 `/subscriptions/register`·`/sales/register`·`/allocations/register`는 같은 화면으로 리다이렉트(`replace`, `state.from` 보존)하고, 문맥(`ipoId`/`subscriptionId`)이 없으면 목록 안내를 표시한다. `subscriptionId` 리다이렉트는 권한 확인된 상세(소유권 검증 — 타인 기록은 403/404)에서 IPO/투자자/계좌를 정확히 매핑해 manage 문맥으로 보낸다. 현재 선택된 투자자가 그 기록의 투자자와 다르면 글로벌 투자자를 임의로 바꾸지 않고 안내만 표시하며, 타인의 기록은 노출하지 않는다.
- AC-10 '수정' 라벨이 신규 생성 폼으로 연결되지 않는다. 기록이 있는 경우 '수정'은 원본을 불러오는 경로다.
- AC-11 통합 화면의 로그인/투자자 게이트는 현 보안 의미와 동일하게 유지 — 관리 경로(`/ipos/:ipoId/manage`)만 선별 scope 등록하고 공개 상세(`/ipos/:ipoId`)의 보호는 바꾸지 않는다.
- AC-12 공모주수수료 기본 2,000원, 해당 배정에 ACTIVE 매도가 이미 있으면 0원(`useSaleForm.ts:397-398`) 보존. 실제 수수료는 사용자가 수정 가능하고, 서버는 하드과금(고정 부과)하지 않는다.
- AC-13 편집 원본은 이력 요약이 아니라 개별 GET으로 읽는다: `GET /subscriptions/{id}`(quantity·depositAmount·subscribedAt·memo), `GET /allocations/{id}`(allocatedQuantity·allocatedAmount·allocatedAt·note), `GET /sales/{id}`(quantity·price·amount·saleDate·fee·tax·otherCost). `InvestmentHistoryItem`에는 `depositAmount`/`memo`가 없고(types.ts:51-66), saleSummary에는 `price`가 없다(types.ts:40-49). **매도 단가를 amount÷quantity로 추정하지 않고 원본 `price`를 쓴다.** 잔여·sales 목록·상태(remainingQuantity)는 `GET /investment-history/{id}`를 그대로 쓴다. 연결 id는 (`investorId`+`ipoId`+`securitiesAccountId`) 정확 필터 size:1 조회 후 응답의 `subscriptionStatus === 'ACTIVE'`를 검증한다 — 서버 이력 조회는 `deletedAt IS NULL`만 반환(구독 cancel 시 deletedAt 설정)하므로 현재 데이터에서 활성 누락 원인이 아니며, 조합 ACTIVE 부분 유니크(V7)와도 충돌하지 않는다. 비활성 유입이 발견될 때만 전건 검토로 전환한다(API/DB 변경 없음).
- AC-14 이중 클릭/응답 유실: 저장 버튼은 isPending 동안 잠그고, 실패 후 자동 POST 재전송은 하지 않는다. 응답을 못 받으면(서버 성공/클라이언트 실패) 재조회해 목록/잔여를 보여 주되, 동일 일자·수량·단가의 정상 분할 매도와 구분할 수 없어 어떤 요청이 성공했는지 100% 식별 불가함을 명시한다. 사용자가 목록을 확인하고 직접 결정(필요 시 중복 삭제)한다. 영구 중복 방지는 현 API로 보장되지 않으며, idempotency 키 도입은 이 계획의 필수 요건이 아니다.
- AC-15 미저장/조회 에러/동시성/0 배정: 섹션별 조회·저장 오류는 그 섹션에만 표시하고 다른 섹션 입력은 유지한다. 다른 곳에서 먼저 등록/삭제해 서버가 400/409를 반환하면 그대로 표시하고 재조회로 동기화한다. allocatedQuantity=0이면 잔여=0이라 매도 추가 불가이며, 기존 건의 수정/삭제는 유지한다.
- AC-16 매도 PATCH는 사용자가 실제 변경한 필드만 포함한다 — price/amount/fee/tax/otherCost의 null과 `0`을 무심코 덮어쓰지 않는다(서버는 null=무변경, `Sale.updateDetails`). `price`가 null인 기존 기록은 단가 미입력 상태로 원본 금액(amount/amount null 포함)을 보존하고, amount÷quantity 재계산으로 값을 추정·저장하지 않는다. 사용자가 단가를 새로 입력한 경우에만 새 price를 보낸다(그때 amount도 그 값으로).
- AC-17 매도/배정 사후 등록으로 서버가 청약을 자동 생성하면(`AllocationService.register`): quantity=배정수량, depositAmount=0, subscribedAt=생성 시각, memo='매도/배정 등록에서 자동 생성된 청약 연결 기록'. 이 값들은 실제 청약 사실이 아니며 청약기간 밖일 수 있다. 화면은 기존 memo 마커로 "사후 등록으로 자동 생성된 청약" 가능성을 표시하고 사용자가 나중에 실제 값으로 수정할 수 있게 한다. 기간 외 기존 subscribedAt은 보존하며 강제로 다른 날짜로 바꾸지 않고, 새 청약은 실제 청약기간 날짜 버튼을 쓴다. 사용자가 이미 입력한(인라인) 값은 자동 생성 안내로 덮어쓰지 않고 안내만 표시한다. 사용자 데이터 변경/일괄 보정은 없다.

## 엣지 케이스

- 배정 전 매도 등록: 화면에서 가능하다. 저장 시 서버가 기존 청약을 찾고, 없으면 청약·배정을 자동 생성/재사용한다(`resolveAllocationId`).
- 매도 있는 배정 취소/수량감소: 서버 400/409를 그대로 표시.
- 삭제: 현 논리 취소 규칙(status=CANCELLED + deletedAt) 유지. 자식→부모 순서(매도→배정→청약) — 청약에 배정 있으면 청약 취소 불가(배정 먼저), 배정에 매도 있으면 배정 취소 불가(매도 먼저).
- 부분 실패: 청약 저장 성공 → 배정 저장 실패 → 청약은 ACTIVE로 남고 "배정만 실패" 표시, 배정 재시도는 같은 청약에 POST /allocations.
- 첫 진입(기록 없음): 청약 먼저 입력도, 매도/배정부터 사후 등록도 같은 화면에서 가능하다(서버 자동 생성/재사용). 사후 등록으로 만들어지는 청약은 실제 청약 기록이 아니라는 안내를 표시한다(AC-17).
- 사후 자동 생성 청약(memo 마커 존재): 안내만 표시하고 기존 subscribedAt은 보존(기간 외도 유지), depositAmount=0 원본 그대로. 사용자가 수정하려면 수정 폼으로.
- 납입·공모가 미확정(fixedPrice null): 증거금 자동계산 생략(기존 관례 유지).

## 비범위

- 새 DB 통합 테이블, 이력 물리 삭제, 새 금융 계산 정책, 탭 분리 UI, 복합 API 필수화는 금지.
- 배포·운영 조회는 이 계획 범위 밖.
