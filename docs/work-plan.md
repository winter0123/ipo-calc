# 공모주 투자 수익 관리 서비스

# AI 개발 작업 계획서

> 이 문서는 AI Agent가 본 프로젝트를 개발할 때 따라야 하는 **상위 작업 계획 및 개발 기준 문서**이다.
>
> AI Agent는 이 문서의 내용을 임의로 축약하거나 추측하여 구현하지 않는다.
>
> 이 문서에서 결정되지 않은 사항은 임의로 확정하지 말고,
>
> 1. 조사해야 할 사항을 식별하고,
> 2. 필요한 경우 조사 Task를 생성하고,
> 3. 조사 결과를 문서화하고,
> 4. 사람에게 결정이 필요한 사항은 명확하게 남긴 뒤,
> 5. 결정된 내용에 따라서 구현한다.
>
> 특히 금융 데이터, 세금, 수수료, 외부 데이터, 투자 수익 계산과 관련된 내용은 추측하여 구현해서는 안 된다.

# 1. 문서의 목적

이 문서는 공모주 투자 수익 관리 서비스를 개발하기 위한 전체 방향을 정의한다.

AI 개발팀은 이 문서를 기준으로 요구사항 분석, 외부 정보 조사, 제품 기획, 아키텍처 설계, 테스트 설계, 구현, QA, 코드 리뷰, 보안 검토를 수행한다.

이 문서 자체가 최종 상세 설계서는 아니다.

실제 개발 과정에서 다음 문서를 추가로 생성할 수 있다.

```text
docs/
├── work-plan.md
├── research-[topic].md
├── spec-[feature].md
├── architecture-[feature].md
├── work-log-[feature].md
├── handoff-[feature].md
└── agent-conflicts.md
```

각 단계에서 필요한 상세 내용은 별도 문서로 분리한다.

# 2. 서비스 한 줄 정의

사용자가 하나의 로그인 계정으로 여러 투자자를 관리하고,
각 투자자의 여러 증권사 계좌에서 발생한 공모주 청약, 배정, 매도, 수수료 및 최종 수익을 지속적으로 기록하고 조회할 수 있는 서비스이다.

---

# 3. 해결하려는 문제

공모주 투자에서는 한 사람이 하나의 계좌만 사용하는 것이 아닐 수 있다.

예를 들어 한 사용자가 다음과 같이 투자할 수 있다.

```text
로그인 사용자
├── 본인
│   ├── 미래에셋 계좌
│   ├── 한국투자 계좌
│   └── 키움 계좌
│
├── 부모
│   ├── 미래에셋 계좌
│   └── NH 계좌
│
└── 배우자
    └── 삼성증권 계좌
```

동일한 공모주에 대해서도 투자자와 증권사 계좌가 다르면 결과가 달라질 수 있다.

예:

```text
공모주 A

본인 / 증권사 A
- 청약 100주
- 배정 2주
- 2주 매도
- 수익 +30,000원

부모 / 증권사 B
- 청약 200주
- 배정 5주
- 3주 매도
- 2주 보유
- 실현수익 +40,000원
- 평가손익 별도
```

따라서 단순하게

```text
IPO → 수익
```

만 저장하는 구조로는 부족하다.

최소한 다음 관계를 추적할 수 있어야 한다.

```text
로그인 계정
    ↓
투자자
    ↓
증권사 계좌
    ↓
공모주 청약
    ↓
배정
    ↓
매도
    ↓
수수료/비용
    ↓
수익
```

# 4. 핵심 목표

이 서비스의 핵심 목표는 다음과 같다.

## 4.1 투자 내역의 지속적인 기록

과거에 어떤 공모주에 참여했는지 잊지 않고 기록할 수 있어야 한다.

## 4.2 투자 결과의 정확한 추적

단순히 매도금액만 기록하는 것이 아니라,

```text
청약
→ 배정
→ 매도
→ 수수료
→ 세금/비용
→ 순수익
```

과정을 추적할 수 있어야 한다.

## 4.3 투자자별 결과 비교

같은 공모주에 대해 여러 투자자의 결과가 다를 수 있으므로 투자자별로 구분해야 한다.

## 4.4 증권사별 결과 확인

어떤 증권사에서 공모주 투자를 했을 때 결과가 좋았는지 확인할 수 있어야 한다.

단, 단순한 평균이나 순위를 무조건 제공하는 것이 아니라 실제 기록을 기반으로 조회해야 한다.

## 4.5 기간별 수익 확인

월별, 연도별 등의 기간 기준으로 투자 성과를 조회할 수 있어야 한다.

## 4.6 향후 자동화

향후 공모주 일정이나 금융 정보를 외부 데이터로부터 자동으로 받아올 수 있는 구조를 고려한다.

단, 자동화는 MVP 이후 단계에서 진행할 수 있다.

# 7. MVP의 핵심 사용자

초기 사용자는 개인 투자자 한 명이라고 가정한다.

단, 해당 계정이 여러 투자자를 관리할 수 있어야 한다.

예:

```text
User Account
│
├── Investor: 나
├── Investor: 엄마
├── Investor: 아빠
└── Investor: 배우자
```

MVP에서는 복잡한 조직/회사/관리자 권한 시스템을 만들 필요가 없다.

다만 향후 확장을 고려하여 로그인 계정과 실제 투자자를 분리한다.

---

# 8. 계정과 투자자의 차이

이 구분은 매우 중요하다.

## Account

서비스에 로그인하는 주체이다.

예:

```text
user@example.com
```

## Investor

실제 투자 결과의 소유자이다.

예:

```text
나
엄마
아빠
배우자
```

즉:

```text
1 Account
    ↓
N Investor
```

구조를 기본으로 고려한다.

---

# 9. 증권사와 계좌의 차이

증권사 자체와 실제 증권계좌를 분리한다.

예:

```text
SecuritiesFirm
- 한국투자증권

SecuritiesAccount
- 한국투자증권 1234-5678
```

한 명의 투자자가 여러 증권사 계좌를 가질 수 있다.

```text
Investor
├── SecuritiesAccount A
├── SecuritiesAccount B
└── SecuritiesAccount C
```

동일한 증권사에 여러 계좌가 있을 가능성도 고려한다.

따라서

```text
Investor → SecuritiesFirm
```

만으로 끝내지 않는다.

초기 설계에서는 다음 구조를 우선 검토한다.

```text
Investor
    ↓
SecuritiesAccount
    ↓
SecuritiesFirm
```

---

# 10. 공모주 IPO 도메인

IPO는 공모주 자체의 정보를 나타낸다.

예:

```text
기업명: ABC
공모주명: ABC
공모가: 20,000원
청약 시작일: ...
청약 종료일: ...
상장일: ...
```

IPO 자체의 정보와 특정 투자자의 청약 기록을 반드시 분리한다.

즉:

```text
IPO
```

와

```text
Subscription
```

은 같은 의미가 아니다.

---

# 11. Subscription 도메인

Subscription은 특정 투자자/계좌가 특정 IPO에 실제로 청약한 기록이다.

예:

```text
Investor A
+
SecuritiesAccount A
+
IPO A
=
Subscription
```

Subscription에서 검토해야 할 값:

* 청약 수량
* 청약 금액
* 청약 일시
* 증거금
* 환불 금액
* 청약 상태
* 기타 필요한 값

정확한 필드 목록은 설계 단계에서 확정한다.

---

# 12. Allocation 도메인

청약 후 실제 배정 결과를 관리한다.

예:

```text
청약 수량: 100
배정 수량: 3
```

또한 균등/비례 배정 등의 세부 정보가 실제 서비스 요구사항에 필요한지 조사한다.

Allocation은 Subscription과 연결된다.

개념적으로:

```text
Subscription
    ↓
Allocation
```

---

# 13. Sale 도메인

매도는 한 번에 끝난다고 가정하지 않는다.

하나의 배정 결과에 여러 번의 매도가 있을 수 있다.

예:

```text
배정: 10주

매도 1
- 3주
- 50,000원

매도 2
- 4주
- 55,000원

잔여
- 3주
```

따라서 다음 구조를 고려한다.

```text
Allocation
    ↓
N Sale
```

매도 정보에는 최소한 다음 항목을 검토한다.

* 매도 수량
* 매도 가격
* 매도 금액
* 매도 일시
* 수수료
* 세금
* 기타 비용

---

# 14. 미매도 주식

배정받은 모든 주식을 즉시 매도하지 않을 수 있다.

예:

```text
배정 10주
매도 6주
잔여 4주
```

잔여 4주는 아직 실현수익이 발생하지 않은 주식일 수 있다.

따라서 향후 다음 개념을 고려해야 한다.

```text
실현손익
평가손익
보유수량
미매도수량
```

MVP에서 미실현 평가손익을 지원할지는 별도 결정 사항이다.

무조건 구현하지 않는다.

---

# 15. 수익 계산의 기본 개념

수익 계산은 가장 중요한 영역 중 하나이다.

단순히 다음과 같이 계산해서는 안 된다.

```text
매도금액 - 청약금액
```

실제 계산에는 다음 요소가 영향을 줄 수 있다.

```text
매도금액
- 취득 관련 비용
- 매도 수수료
- 세금
- 기타 비용
= 순수익
```

정확한 공식은 금융/세금 정책 조사 후 확정한다.

AI Agent는 근거 없이 임의의 수익 계산식을 확정하지 않는다.

---

# 16. 수익률

수익률 계산도 정의가 필요하다.

예:

```text
순수익 / 실제 투자금
```

같은 단순한 방식이 있을 수 있지만,

실제 청약에서는 예치금/증거금/환불금/보유기간 등이 존재할 수 있다.

따라서 수익률의 정확한 정의를 먼저 정한다.

다음 질문을 반드시 검토한다.

* 투자금은 무엇을 의미하는가?
* 청약 증거금을 투자금으로 볼 것인가?
* 실제 배정에 사용된 금액을 기준으로 할 것인가?
* 환불금은 어떻게 처리할 것인가?
* 자금이 묶인 기간을 고려할 것인가?
* 연환산 수익률이 필요한가?

정의되지 않은 계산식을 임의로 구현하지 않는다.

---

# 17. 예상 수익 계산 기능

향후 사용자가 청약 전에 예상 수익을 계산할 수 있도록 한다.

입력 예:

```text
공모가
예상 배정수량
예상 매도가
예상 수수료
예상 세금
예상 자금 사용기간
```

출력 예:

```text
예상 투자금
예상 매도금액
예상 비용
예상 순수익
예상 수익률
```

이 기능은 실제 투자 결과가 아니라 예상값이라는 점을 UI에서 명확하게 표현해야 한다.

# 18. 은행 이자와 비교

사용자가 동일한 자금을 은행 예금 등에 넣는 것과 공모주 투자 결과를 비교할 수 있는 기능을 고려한다.

예:

```text
공모주 예상 순수익
vs
은행 예상 이자
```

그러나 이를 구현하기 위해서는 다음 사항을 먼저 조사한다.

* 비교할 금융상품 범위
* 금리 데이터 출처
* 세후 이자 여부
* 투자기간
* 복리/단리
* 예금/적금 차이

초기에는 단순 비교 기능으로 시작할 수 있다.

# 21. 상태값 설계

각 도메인의 상태값은 문자열을 무분별하게 사용하지 않는다.

예:

```text
청약 예정
청약 진행 중
청약 완료
배정 완료
일부 매도
전량 매도
보유 중
```

실제 상태 목록은 사용 시나리오와 데이터 모델링을 바탕으로 정의한다.

상태 전이가 가능한 경우 전이 규칙도 문서화한다.

---

# 22. 데이터 무결성

금융 데이터이므로 잘못된 데이터가 들어가지 않도록 해야 한다.

예를 들어:

```text
매도 수량 > 배정 수량
```

같은 입력은 허용해서는 안 된다.

또한:

```text
매도 총수량 > 배정 수량
```

도 허용하지 않는다.

동일한 투자 기록을 중복 생성할 가능성도 검토한다.

각 도메인의 중요한 불변조건을 테스트로 작성한다.

---

# 23. 삭제 정책

금융 기록은 단순한 CRUD처럼 처리하지 않는다.

예를 들어 이미 완료된 투자 기록을 사용자가 실수로 삭제하는 경우 데이터 추적성이 사라질 수 있다.

따라서 다음을 검토한다.

* 물리 삭제
* 논리 삭제
* 수정 이력
* 감사 로그

초기 구현에서 반드시 필요하지 않은 기능은 후순위로 둘 수 있지만, 설계 시 데이터 추적성 문제를 고려한다.

---

# 24. 외부 데이터 자동 수집

향후 공모주 일정 및 관련 정보를 자동으로 가져오는 기능을 고려한다.

단, 무조건 특정 사이트를 스크래핑한다고 가정하지 않는다.

먼저 조사한다.

```text
어떤 데이터가 필요한가?
↓
공식 API가 있는가?
↓
공개 데이터가 있는가?
↓
사용 가능한 API가 있는가?
↓
사용 약관이 허용하는가?
↓
상업적/개인적 사용이 가능한가?
↓
호출 제한은 무엇인가?
↓
데이터 신뢰성은 어떠한가?
```

조사 결과를 문서로 남긴다.

---

# 25. 외부 데이터가 불가능한 경우

외부 자동 수집이 기술적 또는 법적/정책적 이유로 적절하지 않은 경우 반드시 대체 방안을 검토한다.

예:

```text
자동 수집
↓
불가능

대안:
- 사용자 직접 입력
- 공식 API 사용
- CSV 가져오기
- 관리자 데이터 등록
- 다른 합법적인 데이터 공급원
```

AI Agent는 외부 사이트를 단순 스크래핑하여 문제를 해결하려고 하지 않는다.

---

# 26. 증권사 수수료

증권사별 청약/매도 수수료가 다를 수 있으므로 하드코딩하지 않는다.

예를 들어:

```text
증권사 A = 2,000원
증권사 B = 0원
```

같은 값이 있더라도 실제 정책을 조사하고 유효기간을 고려해야 한다.

또한 다음도 고려한다.

* 계좌 조건
* 이벤트
* 고객 등급
* 수수료 정책 변경
* 거래 채널별 차이

MVP에서는 사용자가 직접 비용을 기록하는 방식도 검토할 수 있다.

---

# 27. 세금

세금은 매우 중요한 영역이다.

세금 관련 내용은 AI가 기억에 의존하여 구현하지 않는다.

반드시 최신 공식 자료를 조사한다.

특히 다음을 구분해서 검토한다.

* 어떤 거래에 어떤 세금이 붙는가?
* 세율은 얼마인가?
* 적용 기준은 무엇인가?
* 거래 시점에 따라 달라지는가?
* 예외 조건은 무엇인가?
* 개인 투자자에게 어떤 규칙이 적용되는가?

세금 계산 로직이 확정되기 전에는 임의의 숫자를 코드에 넣지 않는다.

# 28. 인증과 개인정보

로그인 정보와 투자 정보는 보호해야 한다.

초기 구현 시 최소한 다음을 검토한다.

* 비밀번호 저장 방식
* 인증 방식
* 세션/JWT 등 인증 구조
* 권한 확인
* 다른 사용자 데이터 접근 차단
* 개인정보 최소 수집
* 민감한 계좌정보 저장 여부
* 로그에 민감정보 출력 금지

특히 다른 로그인 사용자의 투자 데이터를 조회할 수 없어야 한다.

# 30. Backend 설계 원칙

Spring Boot Backend는 다음 관심사를 적절히 분리한다.

예:

```text
controller
application/service
domain
repository
infrastructure
```

실제 패키지 구조는 아키텍처 단계에서 결정한다.

Controller에 핵심 비즈니스 로직을 몰아넣지 않는다.

Entity와 API DTO를 무분별하게 동일 객체로 사용하지 않는다.

외부 API 모델과 내부 도메인 모델을 필요에 따라 분리한다.

# 31. Frontend 설계 원칙

React + TypeScript 기반으로 구현한다.

기능별 책임을 분리하고, 기존 프로젝트의 FSD 방향과 일관성을 유지한다.

예:

```text
entities/
features/
widgets/
pages/
shared/
```

실제 구조는 기능 요구사항과 현재 프로젝트 구조를 확인한 후 결정한다.

컴포넌트 하나에 데이터 조회, 상태관리, 비즈니스 로직, UI를 모두 넣지 않는다.

# 32. API 설계 원칙

같은 입력은 검증한다.

# 33. 테스트 원칙

테스트를 구현 마지막에 몰아서 작성하지 않는다.

요구사항이 정의되면 Acceptance Criteria를 먼저 작성한다.

예:

```text
Given
투자자 A가 공모주 X에 100주를 청약했다.

When
배정 결과가 3주로 등록된다.

Then
배정 수량은 3주이다.
```

그리고:

```text
Given
3주가 배정되었다.

When
2주를 매도한다.

Then
잔여 수량은 1주이다.
```

잘못된 입력도 테스트한다.

예:

```text
Given
배정 수량이 3주이다.

When
4주를 매도하려 한다.

Then
요청은 실패해야 한다.
```

# 34. 수익 계산 테스트

수익 계산은 핵심 비즈니스 로직으로 보고 별도의 테스트를 충분히 작성한다.

최소한 다음 상황을 검토한다.

```text
1. 전량 매도
2. 일부 매도
3. 여러 번 분할 매도
4. 수수료 존재
5. 세금 존재
6. 비용 없음
7. 손실 발생
8. 수익 발생
9. 미매도 잔여 주식 존재
10. 잘못된 수량 입력
```

실제 공식이 확정되면 공식에 맞는 테스트 데이터를 명시한다.

# 35. 금액 데이터 처리

금액 계산에 부동소수점 타입을 무분별하게 사용하지 않는다.

금액 계산에서는 정밀도와 반올림 규칙을 명확하게 정의한다.

Java에서는 금액 처리에 적절한 타입과 반올림 전략을 검토한다.

수익 계산에서 다음 사항도 명시한다.

* 소수점 처리
* 반올림
* 버림
* 올림
* 원 단위 처리

규칙이 결정되기 전에는 임의로 구현하지 않는다.

# 36. 데이터 변경 추적

투자 데이터는 사용자가 나중에 수정할 수 있다.

예:

```text
청약 수량 100 → 200
```

또는

```text
매도 수량 수정
```

수정 가능한 데이터와 수정하면 안 되는 데이터를 구분한다.

필요한 경우 변경 이력 구조를 검토한다.

다음 기능은 요구사항이 추가로 확정되기 전까지 임의로 구현하지 않는다.

* 자동 증권사 로그인
* 증권사 계좌 자동 연동
* 자동 주문/매매
* 실제 증권사 API를 통한 매매
* 자동 세금 신고
* 자동 투자 추천
* AI 투자 추천
* 투자 수익을 근거로 한 투자 의사결정 추천
* 실시간 주가 시스템
* 모바일 앱
* 고급 포트폴리오 분석

서비스의 핵심은 **기록과 조회 및 정확한 수익 계산**이다.

# 39. 요구사항 충돌 처리

두 문서 또는 두 요구사항이 충돌하면 임의로 하나를 선택하지 않는다.

예:

```text
AGENTS.md
vs
feature 문서
```

또는

```text
제품 기획
vs
아키텍처 설계
```

충돌이 발견되면:

1. 충돌 내용을 기록
2. 어떤 요구사항이 우선인지 확인
3. 필요한 경우 `docs/agent-conflicts.md`에 기록
4. 사람의 결정을 기다림

# 43. 데이터베이스 기본 원칙

```text
SecuritiesAccount

```

# 44. Soft Delete 여부

투자 데이터와 기준 데이터에 동일한 삭제 정책을 적용하지 않는다.

예:

```text
SecuritiesFirm
```

같은 기준정보와

```text
Sale
```

같은 금융 기록은 성격이 다르다.

각 도메인별로 삭제 정책을 결정한다.

# 45. 동시성

# 50. 첫 번째 개발 단계

현재 Master Lead가 수행해야 할 첫 번째 큰 작업은 **무작정 코드를 작성하는 것**이 아니다.

우선 다음을 해야 한다.

### 1. 현재 프로젝트 확인

읽어야 하는 파일:

```text
AGENTS.md
README.md
docs/work-plan.md
```

프로젝트의 현재 Git 상태도 확인한다.

```bash
git status --short --branch
git log --oneline -10
git diff --stat
```

### 2. 현재 기술 환경 확인

Backend:

```text
Java version
Spring Boot version
Gradle version
PostgreSQL
```

Frontend:

```text
React version
TypeScript version
package manager
```

등을 확인한다.

### 3. 현재 구현 상태 확인

아직 없는 기능과 이미 존재하는 기능을 구분한다.

### 4. 요구사항 누락 확인

작업 계획에서 아직 결정되지 않은 내용을 식별한다.

### 5. 조사 Task 정의

다음과 같은 조사를 별도 Task로 만들 수 있다.

```text
IPO 데이터 제공처 조사
증권사 수수료 조사
세금 조사
은행 금리 데이터 조사
```

### 6. 제품 요구사항 구체화

MVP 기준으로 어떤 기능을 먼저 만들 것인지 정리한다.

### 7. 아키텍처 설계

요구사항과 조사 결과를 기반으로 설계한다.

### 8. 구현

설계가 확정된 후에 실제 코드 작성을 시작한다.

# 52. 완료 기준

MVP가 완료되었다고 판단하려면 최소한 다음을 만족해야 한다.

## 기능

* 로그인 계정이 존재한다.
* 여러 투자자를 등록할 수 있다.
* 투자자별 증권계좌를 등록할 수 있다.
* IPO 정보를 등록/조회할 수 있다.
* 청약을 기록할 수 있다.
* 배정 결과를 기록할 수 있다.
* 매도를 기록할 수 있다.
* 여러 번의 분할 매도를 처리할 수 있다.
* 관련 비용을 기록할 수 있다.
* 최종 수익을 계산할 수 있다.
* 투자자별 조회가 가능하다.
* 증권사별 조회가 가능하다.
* 기간별 조회가 가능하다.

* 다른 사용자의 데이터가 노출되지 않는다.
* 잘못된 매도 수량을 저장할 수 없다.
* 금액 계산의 정밀도 문제가 없다.

## 테스트

* 핵심 도메인 로직 테스트가 있다.
* 수익 계산 테스트가 있다.
* 주요 API 테스트가 있다.
* 주요 예외 상황 테스트가 있다.

## 품질

* 코드 리뷰가 완료된다.
* 보안 검토가 완료된다.
* QA가 완료된다.
* 실행 방법이 문서화된다.

# 54. 커밋 원칙

의미 있는 단위로 커밋한다.

예:

```text
feat: add investor domain
feat: add securities account management
feat: add IPO subscription tracking
test: add subscription validation tests
```

한 커밋에 서로 관계없는 기능을 섞지 않는다.

자동 생성 파일이나 불필요한 파일을 커밋하지 않는다.

Secret을 커밋하지 않는다.

# 60. 최종 개발 원칙 요약

이 프로젝트에서 가장 중요한 원칙은 다음과 같다.

### 1. 먼저 이해하고 나서 구현한다.

### 2. 모르는 금융 규칙을 추측하지 않는다.

### 3. 데이터의 출처를 확인한다.

### 4. 요구사항에 없는 기능을 임의로 추가하지 않는다.

### 5. 금융 데이터의 정확성과 추적 가능성을 우선한다.

### 6. 핵심 비즈니스 로직은 테스트로 보호한다.

### 7. 투자자별 데이터가 섞이지 않도록 한다.

### 8. 하나의 공모주와 하나의 청약 기록을 동일한 개념으로 취급하지 않는다.

### 9. 하나의 배정에 여러 매도가 발생할 수 있음을 고려한다.

### 10. 미매도 주식과 실현손익/평가손익의 차이를 고려한다.

### 11. 외부 데이터와 세금/수수료 정책은 최신 정보를 조사한 후 결정한다.

### 12. 큰 변경은 사람이 최종 결정한다.

### 13. AI Agent는 작업 과정을 문서화한다.

### 14. 테스트 없이 핵심 금융 계산을 완료 처리하지 않는다.

### 15. 프로젝트의 목적은 AI Agent를 시연하는 것이 아니라 실제로 사용할 수 있는 공모주 투자 관리 서비스를 만드는 것이다.
