### 사전 조건

이 스크립트는 백엔드와 프론트 개발 서버가 이미 떠 있다고 가정한다. 직접 띄우려면:

1. **Postgres 컨테이너 기동 + 슬롯 DB reset**: `docker compose up -d`로 Postgres를 띄우고, `scripts/db-slot.sh reset <n>`으로 슬롯 DB를 초기화한다.
2. **백엔드 기동**: 가입 직후 로그인하는 흐름을 쓰므로 `APP_SIGNUP_MODE=OPEN`을 함께 지정한다(기본값은 비공개 운영용 `APPROVAL`). 빈 포트를 골라 `DB_NAME=vibe_slot_<n> DB_PASSWORD=... APP_ENCRYPTION_KEY=<32바이트 Base64> SERVER_PORT=<포트>` 환경변수와 함께 `backend/`에서 `./gradlew bootRun`을 실행한다.
3. **프론트 기동**: `ui/`에서 `/api-proxy`를 백엔드로 프록시하는 임시 vite 설정(`vite.scan.config.ts`)으로 프론트를 띄운다. `tools/accessibility-scan/run-scan.sh`가 하는 방식(빈 포트 선택 → 임시 vite config 작성 → `VITE_API_BASE_URL=/api-proxy pnpm exec vite --config vite.scan.config.ts` 실행)을 그대로 참고할 수 있다.
4. **BASE_URL 지정**: 프론트 주소를 `tools/e2e/.base-url` 파일에 넣거나 `BASE_URL` 환경변수로 전달한다. 스크립트는 `BASE_URL` 환경변수가 있으면 그것을, 없으면 `.base-url` 파일 내용을 쓴다.

- 비밀번호는 서버 규칙을 통과하는 `testpassword123!`를 쓴다.
- 시나리오 하나가 예외로 죽어도 try/catch로 FAIL 처리하고 나머지는 계속 돌린다.

- 회원가입 201 → `/investors/register` 이동 확인
- 투자자 등록 201 → `/dashboard` 이동, investorId=8
- 마스킹 계좌번호 표시: `"등록 완료: ***************3456"` (뒷 4자리 `3456`만 노출, 전체 번호 미노출)
- 최종 URL=`/dashboard`

### E2E-2 (FAIL): 로그인 → 대시보드 접속

- **기대(spec)**: `POST /auth/login` 200 → 세션 쿠키 설정 → `/dashboard` 리디렉션 (AC-001)
- **실제**: `POST /auth/login` 상태=**200**, 본문=**"" (빈 본문)**, 화면에 **"네트워크 연결을 확인해 주세요."** 표시, URL=`/login` (이동 없음)
- **원인**: 프론트엔드 `apiFetch`(`ui/src/shared/api/client.ts:48`)는 2xx 응답을 `response.json()`으로 파싱한다. 로그인 200 응답의 본문이 비어 있어 `response.json()`이 SyntaxError를 던지고, 이것이 mutation의 onError로 연결돼 "네트워크 연결을 확인해 주세요."가 표시된다. `onSuccess`(리디렉션)는 호출되지 않는다.
- **판단**: 제품이 spec과 다름. 셀렉터/대기 실수가 아니라 실제 응답 상태·본문·화면 텍스트를 그대로 관측한 결과.

### E2E-3 (PASS): 잘못된 비밀번호 로그인 실패

- `POST /auth/login` 상태=**401**
- 인라인 에러: **"이메일 또는 비밀번호가 올바르지 않습니다."** 표시
- URL=`/login` (이동 없음)

### E2E-4 (FAIL): 중복 이메일 회원가입

- **기대(spec)**: "이미 사용 중인 이메일입니다." (마침표 포함, AC-005)
- **실제**: 화면에 **"이미 사용 중인 이메일입니다"** (마침표 없음) 표시, `POST /accounts` 상태=**409**, URL=`/signup`
- **원인**: 백엔드의 409 응답 메시지가 "이미 사용 중인 이메일입니다" (마침표 없음)이며, 프론트엔드 `getFormErrorMessage`(`ui/src/features/signup/SignupForm.tsx:37-48`)는 메시지에 '409'/'Conflict'가 없으면 백엔드 메시지를 그대로 표시한다. spec이 요구하는 마침표가 없다.
- **판단**: 제품이 spec과 다름 (메시지 미세 차이: 마침표 유무). 실제 화면 텍스트를 그대로 읽어 spec 문자열과 정확히 비교한 결과.

### E2E-5 (PASS): 투자자 등록 빈 표시 이름

- displayName 빈 문자열 제출 → 인라인 에러 **"표시 이름은 필수입니다."** 표시
- `POST /investors` **0건** 발생 (클라이언트 유효성 검사가 서버 호출 전에 차단)
- URL=`/investors/register` (이동 없음)

### E2E-6 (FAIL): 존재하지 않는 investorId 증권계좌 등록

- **기대(spec)**: `POST /securities-accounts` 404 → "투자자 정보를 찾을 수 없습니다." (AC-011, 시나리오 6)
- **실제**: `POST /securities-accounts` 상태=**400** (404 아님), 화면에 **"존재하지 않는 투자자입니다"** 표시, URL=`/securities-accounts/register/999999`
- **원인**: 백엔드가 존재하지 않는 investorId에 대해 404가 아니라 400을 반환하고, 메시지도 다르다. 프론트엔드 `getFormErrorMessage`(`ui/src/features/securities-account-register/SecuritiesAccountRegisterForm.tsx:48-72`)에는 404 → "투자자 정보를 찾을 수 없습니다." 매핑이 있지만, 백엔드가 400을 주어 매핑이 동작하지 않는다.
- **판단**: 제품이 spec과 다름 (상태 코드 400 vs 404, 메시지 불일치). 실제 응답 상태와 화면 텍스트를 그대로 관측한 결과.

## FAIL 원인 분류

| ID | 분류 | 근거 |
|----|------|------|
| E2E-2 | 제품 ≠ spec | `POST /auth/login` 200 + 빈 본문 → `apiFetch`의 `response.json()` SyntaxError → "네트워크 연결을 확인해 주세요." 표시, 리디렉션 없음. 응답 상태·본문·화면 텍스트 모두 실측값. |
| E2E-4 | 제품 ≠ spec | 화면 실제 텍스트 "이미 사용 중인 이메일입니다" (마침표 없음) vs spec "이미 사용 중인 이메일입니다." (마침표 있음). 409 상태는 정상. |
| E2E-6 | 제품 ≠ spec | `POST /securities-accounts` 400 반환 (spec은 404), 메시지 "존재하지 않는 투자자입니다" (spec은 "투자자 정보를 찾을 수 없습니다."). |

세 FAIL 모두 스크립트의 셀렉터/대기 실수가 아니라 제품이 spec과 다른 것이다. 제품 코드를 수정하지 않았고 단언을 약하게 만들지 않았다.

1. `login()`의 `url: page.url`이 함수 참조를 저장해 `attempt.url()` 호출 시 오류 → `page.url()`로 즉시 호출해 문자열 저장.
2. 시나리오 하나가 멈춰도 전체가 죽지 않도록 시나리오별 120초 타임아웃 + 브라우저 사망 시 자동 재실행 추가.

## 참고

- E2E-2가 FAIL이므로 E2E-5·E2E-6의 인증은 로그인 대신 회원가입 폴백으로 세션을 맺었다 (스크립트의 `authenticate()` 폴백). 시나리오 5·6이 측정하려는 대상(투자자 등록 유효성 검사, 증권계좌 404 처리)에는 영향이 없다.
- 증권계좌 등록 성공 시 마스킹 계좌번호는 화면 인라인이 아니라 `alert()` 다이얼로그로 표시된다 (`SecuritiesAccountRegisterForm.tsx:38`). spec은 "화면에 표시"라고만 하고 있으므로 스크립트는 다이얼로그 텍스트를 읽어 마스킹 여부를 확인했다.
- 이 보고서의 결과는 실행 시점의 프론트엔드(`ui/`)·백엔드 상태를 반영한다. 제품 코드를 수정하지 않았다.

## 발견 사항

**E2E-2는 실제 사용자 로그인 불가로 이어지는 제품 결함이다.** `POST /auth/login`이 200을 반환하더라도 응답 본문이 비어 있으면 프론트엔드 `apiFetch`(`ui/src/shared/api/client.ts:48`)가 `response.json()`에서 SyntaxError를 던지고, 이것이 mutation의 onError로 연결돼 "네트워크 연결을 확인해 주세요." 메시지만 표시된 채 `/dashboard` 리디렉션이 일어나지 않는다. `apiFetch`는 204 No Content에 대해서만 빈 본문을 예외 처리하고, 로그인 200 응답의 빈 본문은 처리하지 못한다. 따라서 백엔드가 로그인 성공 시 본문 없이 200만 반환하는 현재 상태에서는, 실제 사용자가 정상적인 계정·비밀번호로 로그인해도 로그인 화면에 머무르며 "네트워크 연결을 확인해 주세요."만 보게 된다. 회원가입(E2E-1)과 잘못된 비밀번호 로그인(E2E-3)은 정상 동작하지만, 정상 로그인 경로가 막혀 있어 제품 차원의 수정(백엔드가 로그인 200 응답에 JSON 본문을 포함하거나, 프론트엔드 `apiFetch`가 빈 본문 200을 처리)이 필요하다.
